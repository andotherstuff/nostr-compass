## Releases

### Nostr Java v2.0.8: subscription isolation and portable NIP-44

A gift-wrap query against a relay holding five events was returning zero, two, or six events at random, because [Nostr Java](https://github.com/tcheeric/nostr-java), a Java library for talking to relays and encrypting Nostr payloads, delivered every inbound frame to every listener on the connection. [Version 2.0.8](https://github.com/tcheeric/nostr-java/releases/tag/v2.0.8) routes `EVENT`, `EOSE`, and `CLOSED` to the subscription those frames name, so one query's end-of-stored-events signal can no longer close another. Connection-scoped frames such as `NOTICE`, `OK`, and `AUTH` still reach every listener.

[NIP-44](/en/topics/nip-44/) (payload encryption) in the same [release](https://github.com/tcheeric/nostr-java/releases/tag/v2.0.8) no longer needs a JCE provider registered in the process. Encryption used to work only after a key had been generated in that JVM, which registered BouncyCastle as a side effect, and it failed on Android, where adding a provider named "BC" is a no-op. Both cipher paths now use BouncyCastle's lightweight ChaCha20 engine, and key generation no longer mutates process-wide JCE state. Callers that relied on the library to register the provider must register it themselves. The [NIP-44 JCE-provider dependence](https://github.com/tcheeric/nostr-java/issues/537) is the issue this closes.

### NoorNote v1.3.6: profile statuses and classified listings

[NoorNote](https://github.com/77elements/noornote) is a Nostr client for desktop, web, and Android. A week after [1.3.4 added encrypted community joins](/en/newsletters/2026-08-19-newsletter/#noornote-134-joining-encrypted-communities-from-an-invite-link), [version 1.3.6](https://github.com/77elements/noornote/releases/tag/v1.3.6) shows [NIP-38](/en/topics/nip-38/) (user statuses) under a profile's [NIP-05](/en/topics/nip-05/) (domain-verified) name: the optionally expiring kind `30315` addressable events that carry a one-line general or music status. Clicking that line sets the viewer's own status.

[Classified listings](https://github.com/77elements/noornote/releases/tag/v1.3.6) from [NIP-99](/en/topics/nip-99/) (kind `30402` marketplace offers) now render throughout the app, so the marketplace addon is needed only to buy and sell. Private petname notes on profiles also show in warning orange, with a filled note icon and an orange avatar ring.

### nostrord v2.9.0: relay-scoped group state and media

Leaving a [NIP-29](/en/topics/nip-29/) (relay-managed groups) group on one host used to suppress the same group id on every other relay, because [nostrord](https://github.com/nostrord/nostrord), a cross-platform client for relay-hosted communities, keyed its leave and delete markers by bare id. [Leave and delete markers scoped per relay](https://github.com/nostrord/nostrord/pull/253) keep those suppressions on the host that produced them, so a group that shares an id across two relays is no longer left or dropped as a pair. A join that the relay rejects as already a member now counts as success and clears the local marker, which had been an absorbing state: the self-heal cleared one slot while cold start restored the other.

[Version 2.9.0](https://github.com/nostrord/nostrord/releases/tag/v2.9.0) also renders [markdown image embeds](https://github.com/nostrord/nostrord/pull/254) that other clients write as `![alt](url)`, instead of showing the markdown punctuation around an already-detected URL. Direct messages pick up [NIP-17](/en/topics/nip-17/) (gift-wrapped private DMs) [kind `15` file rumors](https://github.com/nostrord/nostrord/pull/275), so an encrypted attachment sent from Jumble is downloaded, decrypted, and shown, and outbound attachments are encrypted before upload. This tag now ships the [NIP-4e encryption-key work covered last week](/en/newsletters/2026-08-19-newsletter/#nostrord-implements-an-unmerged-encryption-key-proposal). The proposal remains unmerged, and nostrord says its implementation follows deployed Jumble behavior where that behavior differs from the draft.

### Nail v0.1.0: an Android client and a key-free arrival watcher

[Nail](https://github.com/formstr-hq/nail) is the Formstr team's mail bridge and web client, [introduced last week](/en/newsletters/2026-08-19-newsletter/#nail-brings-email-onto-nostr-as-gift-wrapped-events), which carries email as kind `1301` rumors inside kind `1059` [NIP-59](/en/topics/nip-59/) (gift wrap) envelopes. [v0.1.0](https://github.com/formstr-hq/nail/releases/tag/v0.1.0) is its first tagged release and adds a mobile surface: an [Android app for mailstr](https://github.com/formstr-hq/nail/pull/12) built on Capacitor around the existing client, plus [Zapstore publishing configuration and mobile screenshots](https://github.com/formstr-hq/nail/pull/13). The app is listed on Zapstore as `com.formstr.mail`.

The interesting part is how the app learns that mail has arrived. Reading a message needs the private key, but the arrival of a p-tagged gift wrap is itself the "you have new mail" signal, and that needs only public data. Nail's [notifier crate](https://github.com/formstr-hq/nail/blob/main/notifier/src/lib.rs) is built on that observation: it holds no key material and never decrypts, subscribing per relay for `{kinds:[1059], #p:[owner]}`, deduplicating arrivals by event id, and calling back once per new wrap. It carries its own Tokio runtime on a dedicated thread and is exposed to Kotlin through UniFFI, so the Android [poll worker](https://github.com/formstr-hq/nail/blob/main/mobile/android/app/src/main/java/com/formstr/mail/notify/MailPollWorker.kt) connects, reads to end-of-stored-events, posts a notification per new wrap, and disconnects rather than holding a socket open or running a foreground service.

That worker also documents a protocol trap other clients will hit. NIP-59 backdates each gift wrap's `created_at` by up to two days to frustrate timing analysis, so a message that has just arrived can carry a timestamp two days old. A `since` watermark therefore excludes freshly delivered mail at the relay filter, which is why notifications silently never fired. Nail now fetches roughly the last two days by wall clock and decides novelty purely by event id, with a bounded seen-set and a seeded-backlog marker in `SharedPreferences` so a first run does not announce old mail. The rest of the release is relay and client repair: [relay handling](https://github.com/formstr-hq/nail/pull/9), a [user-agent fix](https://github.com/formstr-hq/nail/pull/11), and [alias defaults with a mobile compose fix](https://github.com/formstr-hq/nail/pull/10).

### MDK v0.9.14 and v0.9.15: KeyPackage selection, epoch-gap recovery, and split relay roles

[MDK](https://github.com/marmot-protocol/mdk) is the Rust implementation of [Marmot](/en/topics/marmot/), the [NIP-104](/en/topics/nip-104/) (MLS group messaging over Nostr) protocol, and it ships the MarmotKit bindings other clients build on. Two releases landed in the window, and both concentrate on the join and recovery paths that decide whether a group stays usable.

Invitation now depends on choosing the right key material. [v0.9.14](https://github.com/marmot-protocol/mdk/releases/tag/v0.9.14) [prioritizes setup KeyPackage publication](https://github.com/marmot-protocol/mdk/pull/1493) and [batches and prewarms member KeyPackages](https://github.com/marmot-protocol/mdk/pull/1494) so an invite is not waiting on a fetch, and [v0.9.15](https://github.com/marmot-protocol/mdk/releases/tag/v0.9.15) [selects the newest valid KeyPackage for group invites](https://github.com/marmot-protocol/mdk/pull/1550) rather than whichever arrives first. A stale KeyPackage produces a member who cannot decrypt, so the selection rule is the difference between a working invite and a silent failure.

Recovery got the same treatment. v0.9.15 [arms epoch-gap recovery before every publish gate](https://github.com/marmot-protocol/mdk/pull/1524) and [reports epoch passages to the stall detector](https://github.com/marmot-protocol/mdk/pull/1532), so a client that has fallen behind the group's epoch repairs itself before it tries to publish instead of writing into a state nobody else shares. An [empty admin policy is now classified as admin depletion](https://github.com/marmot-protocol/mdk/pull/1523), which turns a group with no reachable administrator into a named condition rather than an unexplained refusal, and v0.9.14 [added bounded sync and catch-up failure telemetry](https://github.com/marmot-protocol/mdk/pull/1488) to make those stalls visible at all.

Two changes matter for relay operators and multi-account users. v0.9.15 [separates directory discovery from operational relays](https://github.com/marmot-protocol/mdk/pull/1537), so the relays used to find people are no longer the relays carrying group traffic, and v0.9.14 [publishes profiles with account-owned relays](https://github.com/marmot-protocol/mdk/pull/1495) through `marmot-uniffi`. [External-signer accounts can now sign out and wipe](https://github.com/marmot-protocol/mdk/pull/1528), closing a case where a remote-signer account could not be fully removed. [Account-scoped invite policies for direct bots](https://github.com/marmot-protocol/mdk/pull/1542) and [large-group pressure scenarios](https://github.com/marmot-protocol/mdk/pull/1511) round out the pair, and both releases publish MarmotKit iOS and macOS XCFrameworks with SwiftPM checksums pinned to the exact MDK commit.

### Zeus v13.2.0: wallet-connect budgets, races, and secret rotation

[Zeus](https://github.com/ZeusLN/zeus) is a mobile Bitcoin and Lightning wallet whose Nostr surface is [NIP-47](/en/topics/nip-47/) (wallet connect). [v13.2.0](https://github.com/ZeusLN/zeus/releases/tag/v13.2.0) carries a dense run of fixes on that surface, most of them about a connection's spending budget meaning what it says. Pending payments now [count against the connection budget](https://github.com/ZeusLN/zeus/pull/4305), settled payments missing from the payments list [debit it anyway](https://github.com/ZeusLN/zeus/pull/4334), and [routing and melt fees are included](https://github.com/ZeusLN/zeus/pull/4340). Each of those gaps let a connection spend past its stated cap.

Concurrency and identity got the rest. `pay_invoice` handling is [serialized to prevent shared-store races](https://github.com/ZeusLN/zeus/pull/4303), `pay_invoice` activity records [upsert safely and reconcile their persistence](https://github.com/ZeusLN/zeus/pull/4343), `sign_message` now [awaits the signature so it returns the right one](https://github.com/ZeusLN/zeus/pull/4308), and the client secret is [rotated and persisted on relay change](https://github.com/ZeusLN/zeus/pull/4341). [`lookup_invoice`, `list_transactions`, and backend invoice lookup](https://github.com/ZeusLN/zeus/pull/4294) were repaired together. The release also ships LDK 24-word seed phrases, an embedded LND bump, and a Cashu CDK upgrade, none of which touch a Nostr surface.

### NYM: post-quantum private messages and threads in channels

[NYM](https://github.com/Spl0itable/NYM) is a lightweight ephemeral chat client on Nostr bridged with Bitchat, and it shipped sixteen tagged releases in the window. Three carry the substance. [v3.73.530](https://github.com/Spl0itable/NYM/releases/tag/v3.73.530) adds Bluetooth mesh in supporting browsers, putting the mesh transport behind a web client rather than a native app. [v3.74.533](https://github.com/Spl0itable/NYM/releases/tag/v3.74.533) adds quantum-resistant encryption to private messages and group chats, and [v3.74.542](https://github.com/Spl0itable/NYM/releases/tag/v3.74.542) moves that scheme to its second version; a client choosing its own post-quantum envelope is interoperable only with itself, so the tradeoff is confidentiality against reach. [v3.75.543](https://github.com/Spl0itable/NYM/releases/tag/v3.75.543) adds message threads in channels, private messages, and group chats, and moves the premium bot onto post-quantum encrypted messages. [v3.74.543](https://github.com/Spl0itable/NYM/releases/tag/v3.74.543) repairs a private-message interoperability break with Bitchat. The remaining eleven releases are bug-fix and performance passes.

### diVine 1.0.22: relay and signer lifecycles that end when the session does

[diVine](https://github.com/divinevideo/divine-mobile) is a short-form looping video client with restored Vine archives. [1.0.22](https://github.com/divinevideo/divine-mobile/releases/tag/1.0.22) is largely a cleanup of connections and subscriptions that outlived their session. Signing out [no longer leaves a relay connection open forever](https://github.com/divinevideo/divine-mobile/pull/7957), and a separate fix stops it [leaving the signer connected forever](https://github.com/divinevideo/divine-mobile/pull/7973) over [NIP-46](/en/topics/nip-46/) (remote signing). Subscription slots are [released after bounded reads](https://github.com/divinevideo/divine-mobile/pull/8007), and temporary relay authentication [handles fire-and-forget publishes](https://github.com/divinevideo/divine-mobile/pull/7718) rather than assuming a receipt.

The [NIP-04](/en/topics/nip-04/) (legacy encrypted DMs) path got two fixes with visible symptoms: terminal duplicates are [no longer retried](https://github.com/divinevideo/divine-mobile/pull/7891), and a DM's `created_at` is [bounded so it cannot freeze the unread badge](https://github.com/divinevideo/divine-mobile/pull/8005), which is the same class of trap Nail hit from the other direction. A [deleted list no longer returns on the next relay sync](https://github.com/divinevideo/divine-mobile/pull/8034), and [recipients can remove unwanted badges](https://github.com/divinevideo/divine-mobile/pull/7640) rather than carrying whatever anyone awarded them.

### Chama v6.0.1: a 32-bit timer that emptied every browser escrow

[Chama](https://github.com/jesuspirate/chama) is a Nostr-native peer-to-peer escrow client pairing Fedimint ecash with 2-of-3 Shamir secret sharing. [v6.0.1](https://github.com/jesuspirate/chama/releases/tag/v6.0.1) fixes a money-path defect with a narrow cause and a wide blast radius. Locking sats into an ecash escrow hands the mint a deadline after which unredeemed notes return to the funder, and Chama set that deadline to 90 days. Fedimint's browser build passes timer values as a 32-bit number, 90 days in milliseconds does not fit, and the value wrapped negative, which the browser read as "immediately".

Every escrow note created in a browser was therefore returned to its funder the instant it was minted, while the trade still published its lock and still displayed as funded, [according to the release notes](https://github.com/jesuspirate/chama/releases/tag/v6.0.1). That is the part worth reading twice: the Nostr-visible trade state stayed correct while the value behind it had already unwound, so no participant reading the event stream could tell. Escrows created outside a browser build were unaffected.
