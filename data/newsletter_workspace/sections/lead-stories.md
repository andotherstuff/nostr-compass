## Top Stories

### Amber 6.5.0 closes a relay-auth confused deputy and encrypts stored secrets

[Amber](https://github.com/greenart7c3/Amber) is an Android signer that holds a Nostr private key on the device and answers signing requests from other apps over [NIP-55](/en/topics/nip-55/), the Android signer intent scheme, and from remote clients over [NIP-46](/en/topics/nip-46/), the remote-signing protocol. [Version 6.5.0](https://github.com/greenart7c3/Amber/releases/tag/v6.5.0) closes four coordinated security gaps disclosed alongside the release.

The most serious fix repairs a [confused deputy in relay authentication](https://github.com/greenart7c3/Amber/security/advisories/GHSA-vx4h-56qj-wcp7): an allowlist meant to record which relays a user had approved for [NIP-42](/en/topics/nip-42/) client-to-relay authentication authorized any requester that asked, so an application could obtain a kind `22242` authentication event for a relay it had never been granted. A separate [NIP-46 replay gap](https://github.com/greenart7c3/Amber/security/advisories/GHSA-h9fv-9247-3582) left remote-signing requests without freshness or replay protection, which let a captured request be presented again later. [Connection secrets and local private keys](https://github.com/greenart7c3/Amber/security/advisories/GHSA-5fjp-ghh8-wch8) had been sitting in the app database as plaintext; 6.5.0 envelope-encrypts them at rest.

An [eight-item hardening batch](https://github.com/greenart7c3/Amber/security/advisories/GHSA-8844-q5vh-9j8f) rounds out the posture change. Amber now authorizes a caller before decrypting anything in its signer provider query path, parses an unrecognized permission-remember type as `NEVER` so an unknown value fails closed, warns when a relay URL uses plain `ws://` outside an onion address, sets the Android secure-window flag on screens that display QR codes, redacts key material from logs and crash reports, loads account keys lazily and zeroes them on logout, and adds an opt-in requirement that the device be unlocked before the Keystore key can be used.

Two follow-ups landed inside the same window. [Version 6.5.1](https://github.com/greenart7c3/Amber/releases/tag/v6.5.1) re-encrypts stored NIP-46 connection secrets when the Keystore key rotates, which had left connections undecryptable after a user toggled the new unlocked-device requirement, and fixes a crash in the permission editor caused by an invalid local key. [Version 6.5.2](https://github.com/greenart7c3/Amber/releases/tag/v6.5.2) stops the applications list from decrypting the secret and local-key columns it never renders, caches the Keystore key handle instead of re-fetching it per decryption, warms the account cache at startup so the account switcher lists every account, and debounces the relay status notification. [Last week's 6.4.0](/en/newsletters/2026-08-12-newsletter/#amber-640-makes-every-grouped-signing-decision-explicit) made grouped signing decisions explicit to the user; this release changes what the signer will agree to do at all.

### Cambium 0.4.0 signs for websites and sheds relay-auth bursts

[Cambium](https://github.com/forgesworn/cambium) is an Android NIP-55 signer that holds no private key. It pairs over NIP-46 with a companion Heartwood hardware signer and proxies every signing request to it, so the key never reaches the phone. Six releases shipped in two days.

[Version 0.4.0](https://github.com/forgesworn/cambium/releases/tag/v0.4.0) extends signing to websites. A page can request a signature through a validated `nostrsigner:` callback without inheriting the permissions granted to native applications, which keeps a browser tab from borrowing another app's approval. The same release fixes the specification's minimal event shape: an event carrying only `kind` and `content` now signs correctly, with Cambium supplying the paired NIP-46 identity, the current timestamp, and an empty tag array before handing the event to rust-nostr. Native rust-nostr instrumentation became a required continuous-integration gate in the same change.

[Version 0.3.6](https://github.com/forgesworn/cambium/releases/tag/v0.3.6) repairs pairing against spec-following signers. Cambium's older rust-nostr build accepted only the literal string `ack` as the result of a NIP-46 `connect` call, so a signer that answers by echoing the bunker URI's secret, which is what the current specification asks for and what Heartwood's firmware does, ended pairing with an unexpected-response error. Moving from rust-nostr 0.44.2 to 0.44.8 makes both forms acceptable, verified against live hardware and against `nak bunker`, which still answers `ack`.

The 0.4.1 through 0.4.3 releases are about admission control under load. [Version 0.4.1](https://github.com/forgesworn/cambium/releases/tag/v0.4.1) gives reactions, posts, deletions, and encryption a reserved queue slot ahead of relay authentication and background decryption, bounds queued calls, discards them once the caller has timed out, and returns a terminal unavailable result on overload instead of opening a foreground signing screen. [Version 0.4.2](https://github.com/forgesworn/cambium/releases/tag/v0.4.2) discards timed-out or long-idle NIP-46 sessions before the next request and lets concurrent copies of the same kind `22242` authentication event share one hardware signature. [Version 0.4.3](https://github.com/forgesworn/cambium/releases/tag/v0.4.3) admits at most one distinct authentication challenge per identity into the hardware worker, never retries authentication internally, and opens a sixty-second per-identity cooldown after a timeout while still answering exact cached duplicates. The measurements in the release notes come from a GrapheneOS phone driving [Amethyst](https://github.com/vitorpamplona/amethyst): a cold-start burst produced thirty-three immediate overload responses and thirteen completed requests with no signer timeouts, and a fresh login during an authentication burst returned 1.254 seconds after approval.

### Citrine 3.1.0 turns a phone relay into a group host and a site host

[Citrine](https://github.com/greenart7c3/Citrine) runs a Nostr relay on an Android phone, which lets a user keep their own events on hardware they hold. [Version 3.1.0](https://github.com/greenart7c3/Citrine/releases/tag/v3.1.0) adds three capabilities that change what the relay can be used for.

Support for [NIP-29](/en/topics/nip-29/), the [relay-based group specification](https://github.com/nostr-protocol/nips/blob/master/29.md) where the relay itself holds membership and moderation state, means a phone can host a group instead of joining one. Support for [NIP-86](/en/topics/nip-86/), the [relay management API](https://github.com/nostr-protocol/nips/blob/master/86.md) that exposes administrative actions over authenticated JSON-RPC, arrives with a settings screen, so allowlists and bans can be driven from the API as well as from the app. Support for [NIP-5A](/en/topics/nip-5a/) [static websites](https://github.com/nostr-protocol/nips/blob/master/5A.md) lets the relay serve nsites to web clients, with a modernized browse list carrying icons, search, sort-by-last-update, install progress, descriptions, and a configurable set of relays for fetching them that defaults to `nsite.run`, `nos.lol`, and `nostr.land`.

The moderation surface grew alongside it in the [same release](https://github.com/greenart7c3/Citrine/releases/tag/v3.1.0). Banning a public key locally now offers to purge that author's stored events, a configurable `REJECTED_KINDS` list blocks kinds the operator does not want to store, and access control can import from existing lists. A rebroadcast tool pushes stored events back out to selected relays, which gives a phone-held archive a way to reseed the network. The release also removes the WebSocket `permessage-deflate` extension, tightens the query hot path, fixes Tor failing to start or stop when the expose-via-Tor setting changes, and moves logs into a local database with logcat limited to debug builds.

### Vector 0.4.2 makes community moderation survive a spam wave

[Vector](https://github.com/VectorPrivacy/Vector) is a desktop and Android messenger built on Nostr direct messages and on [Concord](https://github.com/concord-protocol/concord), the encrypted-community protocol whose membership and moderation state live in signed relay events. [Version 0.4.2](https://github.com/VectorPrivacy/Vector/releases/tag/v0.4.2) is a large release whose most consequential part is moderation under load.

Rapid bans previously overwrote each other. They now queue, stack, and settle as a single operation, so banning a wave of accounts costs one key rotation instead of one per account. Accepting an invitation to a community that has since been dissolved now explains why and removes the invitation from every device the user owns, and dissolving a community the user owns clears it from their community list everywhere, a fix that arrived in [version 0.4.3](https://github.com/VectorPrivacy/Vector/releases/tag/v0.4.3). Community messages that arrive during a background catch-up no longer ring notifications as though they had just been sent, and the typing indicator expires from the moment it was sent so a delayed signal cannot linger in a channel.

The sharded community list defined by [Concord](https://github.com/concord-protocol/concord) took a cross-client review pass with Armada, the other Concord client. Renames no longer inflate the list, ties resolve identically on both clients, and unchanged data is no longer republished to relays. Muting also moved out of the direct-message path: a user can now mute someone straight from a community with no prior message history, and the mute applies to notifications and badges across channels and direct messages while leaving the messages themselves visible. Pinned messages became a shared channel surface with clickable links, and edits to a pinned message follow it wherever it appears. Block lists, mutes, and nicknames now sync between a user's devices, as do pinned chats. Version 0.4.3 also stops Vector from announcing that the user is typing when a different Nostr client is signed in as the same identity, and unblocks Tor bootstrap on Windows, which had frozen at fifteen percent on both x64 and ARM64.

### Sonar brings threaded replies to a mesh messenger with NIP-C7

[Sonar](https://github.com/hedwig-corp/bitchat-to-sonar) is a messenger that carries chat over Bluetooth mesh and over Nostr, so a conversation continues when the network does not. [Version 0.1-alpha.13.1](https://github.com/hedwig-corp/bitchat-to-sonar/releases/tag/v0.1-alpha.13.1) adds replies in the style of Signal, built on [NIP-C7](https://github.com/nostr-protocol/nips/blob/master/C7.md), the chat specification that carries kind `9` messages and their reply references. The same release adds mentions, bounds Bluetooth message reassembly, caps the backup data plan, adds signing verification over the mesh path, and adds a push fallback through Firebase Cloud Messaging.

Two corrective releases followed within a day. [Version 0.1-alpha.13.2](https://github.com/hedwig-corp/bitchat-to-sonar/releases/tag/v0.1-alpha.13.2) fixes an Android crash when opening a chat, stops the iOS keyboard covering short transcripts, and adds scroll invalidation on returning to a conversation. [Version 0.1-alpha.13.3](https://github.com/hedwig-corp/bitchat-to-sonar/releases/tag/v0.1-alpha.13.3) is an Android-only cut for a second chat-open crash triggered by messages carrying empty inline metadata, which is the kind of defect a reply feature surfaces because it puts structured metadata on ordinary messages for the first time.

### Nostria starts publishing podcasts and asks relays to count

[Nostria](https://github.com/nostria-app/nostria) is a web client covering feeds, profiles, and media. [Version 4.1.70](https://github.com/nostria-app/nostria/releases/tag/v4.1.70) adds podcast support built on the Nostr podcast events, with the show and its episodes carried as signed events instead of an external feed, and publishing management offered to premium subscribers, and [version 4.1.71](https://github.com/nostria-app/nostria/releases/tag/v4.1.71) follows with episode durations and further podcast handling.

[Version 4.1.69](https://github.com/nostria-app/nostria/releases/tag/v4.1.69) adds support for [NIP-45](/en/topics/nip-45/) `COUNT`, the relay command that returns how many events match a filter without returning the events, used where a relay advertises it. Nostria uses it to load reaction, reply, and zap totals in feeds, which is the case NIP-45 was written for: a client that wants a number does not need the payload. The same release completes localization across every supported language. [Last week's 4.1.67](/en/newsletters/2026-08-12-newsletter/#nostria-4167-expands-encrypted-community-administration) expanded encrypted-community administration; the podcast and counting work moves into publishing and feed rendering.
