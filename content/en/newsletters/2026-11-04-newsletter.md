An [Amethyst release](https://github.com/vitorpamplona/amethyst/releases/tag/v1.21.0) gives each encrypted direct-message attachment a fresh AES-GCM key and nonce. The [attachment encryption fix](https://github.com/vitorpamplona/amethyst/pull/4701) reports that earlier multi-file batches reused both, which created a tag-forgery risk. Files already sent keep their old encryption. A [Napplet core release](https://github.com/napplet/web/releases/tag/%40napplet/core%400.37.0) binds each verified app identity to a single message port, and its conformance rules require hosts to revoke grants when navigation replaces that document. Later source in [a Napplet preview-host hardening change](https://github.com/napplet/web/pull/305) blocks all framed sources so the preview host cannot run an unverified document before the first load. MDK's testing-only nightlies add [epoch authenticator pins](https://github.com/marmot-protocol/mdk/pull/2819) that reject same-number branch changes, while device-linking code stays behind a development flag that is off in production.

## Top Stories

### Amethyst

Amethyst, the Android client, released [v1.21.0](https://github.com/vitorpamplona/amethyst/releases/tag/v1.21.0), which runs napplets inline in notes on Android 11+ and on desktop. Fixes from an [embed security review](https://github.com/vitorpamplona/amethyst/pull/4710) close a path where any napplet with relay access could read decrypted DMs along with their seal and rumor layers. Decryption now needs a separate user grant, and `nostr.signEvent` needs signer permission. The in-app browser blocks WebRTC on Tor sites, while the desktop Chromium renderer remains unsandboxed. [Per-file attachment encryption](https://github.com/vitorpamplona/amethyst/pull/4701) gives each [NIP-17](/en/topics/nip-17/) (Private Direct Messages) attachment a fresh AES-GCM key and nonce, where unguarded multi-file batches reused both. From code analysis, the upstream change says this exposed the XOR of the plaintexts and allowed tag forgery; it describes no independently reproduced exploit, and files already sent are not repaired. [Picked-file access](https://github.com/vitorpamplona/amethyst/pull/4715) covers only files the user chooses, at most 128 KiB per read or write. [Blossom-only uploads](https://github.com/vitorpamplona/amethyst/pull/4718) go to up to three of the account's servers. Amethyst stops publishing [drss listening progress](https://github.com/vitorpamplona/amethyst/pull/4720) during playback but still reads it, and existing drss preference and list writes stay. The push notification server's [relay pool restart fix](https://github.com/vitorpamplona/amethyst-push-notif-server/commit/74a1aa3eafe9afa1d39547b4580a76307266ba8c) covers restart locking and missed newly configured relays; it is in service source, not the Android release.

In merged source, a [multi-cart player change](https://github.com/vitorpamplona/amethyst/pull/4743) reads plain two-cart pairs or named carts. Extra carts are hash-checked and fetched on Play, and saves are keyed to the declared cart set. Its manual tests predate the final published artifact. Two proposals remain open. One [handles Blossom 409 responses for identical media](https://github.com/vitorpamplona/amethyst/pull/4747) by reusing the existing upload only after hash and local dimension checks. It also reports which server a fallback upload used through account notices on upload screens. The other adds [opt-in NWC wallet backups](https://github.com/vitorpamplona/amethyst/pull/4745) as self-encrypted [NIP-44](/en/topics/nip-44/) (Encrypted Payloads) kind 30078 events, with publish and delete requiring relay acknowledgment. Restore picks the newest event per app and can import a selected wallet. Cross-client restore depends on shared application d-tags, a convention [NIP-78](/en/topics/nip-78/) (App-Specific Data) does not guarantee. A later signer or key compromise would expose the backed-up spending credentials.

### Marmot Protocol (mdk)

mdk, Marmot's MLS-based encrypted messaging kit for Nostr, published testing-only nightly prereleases, with no stable release in that line. The 2 November nightly includes [Sonar-compatible stickers](https://github.com/marmot-protocol/mdk/pull/875): kind 30031 packs plus a kind 10031 installed list that rebases local changes so a stale copy cannot overwrite it. In the same nightly, [new sends wait behind older queued ones](https://github.com/marmot-protocol/mdk/pull/2849) in a group, which keeps encryption generations in order for members catching up on history. That ordering is not a guarantee against lost messages. [Epoch pins now also check the epoch authenticator hash](https://github.com/marmot-protocol/mdk/pull/2819), though a gap between upload and send remains. Merged source changes add more. Reconnects [retry unsent messages held while offline](https://github.com/marmot-protocol/mdk/pull/2860) as the same signed event. Uploaded attachment and reaction references [now carry epoch and branch identity](https://github.com/marmot-protocol/mdk/pull/2891), and stale uploads from the same epoch branch are rejected before sending. Existing references still download, but sending an older or received reference requires a fresh upload, and the imeta wire format is unchanged. [Reaction-specific attachment lookup](https://github.com/marmot-protocol/mdk/pull/2893) lets hosts that adopt lookup by reaction message ID and HostManaged acquisition fetch encrypted custom reaction artwork without timeline rows, keeping its keys across epochs and history. A direct artwork URL is only metadata. [Historical attachment recovery](https://github.com/marmot-protocol/mdk/pull/2614), reported last week as open in issue 46, is now merged. It reports source slot and status with a bounded authenticated digest, then writes a private leased file checked against the verified byte count until the host explicitly releases it. The timeline stays network-free, and recovery respects native policy on expiry and retry. Locators and keys stay behind the API. Directory events [are checked against their ID and signature](https://github.com/marmot-protocol/mdk/pull/2918) before live forwarding and again at raw ingestion before either store changes, so invalid events are ignored without altering the existing freshness projection. [Exact pinned SDK backports](https://github.com/marmot-protocol/mdk/pull/2912) bind content to its event ID and tie the signature cache to the exact verified signature, leaving dependency and workspace versions unchanged.  [Serialized directory updates](https://github.com/marmot-protocol/mdk/pull/2902) are a fix separate from signature checks. They preserve independently published components across concurrent writers and both cache tiers. Callbacks run after the lock is released, and recency rules are unchanged. [Founding-admin references](https://github.com/marmot-protocol/mdk/pull/2587), likewise reported last week as open in issue 46, are now merged. They reach group creation through the app and socket capability, and admins who are invalid or not members are rejected before side effects. Legacy creator-only behavior is preserved, and no shipped Android interface is claimed. [Lost-Welcome resend and manual backup history restore](https://github.com/marmot-protocol/mdk/pull/2905) arrived together, with restore limited to current memberships and importing messages and attachment keys atomically. Membership and preferences stay authoritative. That merged resend code times its ten-minute window from the first native observation. The current Marmot specification has since adopted a newer rule. It keys on target heartbeat activity at least ten minutes after the latest accepted publication. This implementation does not yet match the spec, and a parked follow-up does not implement the newer rule either. [C and UniFFI bindings](https://github.com/marmot-protocol/mdk/pull/2910) expose backup controls and restore status, along with current-chat availability and typed provenance. Host-reported WiFi and charging state gates new background passes, while manual restore runs independently. C consumers need a matching header and library plus a rebuild. Replacement workers default closed while already admitted passes finish, and erasure of strings from memory is limited. Device linking stays off in production. Behind the default-off dev-device-groups feature, [daemon linking commands](https://github.com/marmot-protocol/mdk/pull/2922) cover the existing pairing protocol from start through comparison and approval, plus cancel and list. Ordinary releases leave it off and its bindings are not activated. Testing requires matching persistent dev daemons, and the existing device has no Not now option. The flow has no mobile or physical-device validation. Under the same flag, an eligible sibling device can [fill a missing chat membership](https://github.com/marmot-protocol/mdk/pull/2889) from private stock under an authenticated ten-minute advisory claim, rechecking membership and readiness first. It requires add-to-all, and a known refill limitation remains. Duplicate cleanup and resend are handled separately. An optional [linked-device settings command](https://github.com/marmot-protocol/mdk/pull/2903) reuses edit recovery and preserves unspecified values, and gap-fill claims survive unsettled local edits. Shared history reaches only future Adds and owed transfers, and migration 0171 treats older renames as label-only. An open proposal [would mark a send recipient_confirmed](https://github.com/marmot-protocol/mdk/pull/2899) when a peer reacts to a message whose send failed or reached no accepting relay, without inventing a transport ID. Invalidating that reaction live would retract the confirmation, while a retained receipt survives reaction pruning as long as the send remains. Hosts would have to read recipient_confirmed despite a null source ID. Pending sends would stay pending, and the raw publish-failure fact is preserved.

### Napplets - Web Packages

Napplets, the web packages for sandboxed Nostr applets, released [core 0.37.0](https://github.com/napplet/web/releases/tag/%40napplet/core%400.37.0), [nap 0.36.0](https://github.com/napplet/web/releases/tag/%40napplet/nap%400.36.0) and [shim 0.35.0](https://github.com/napplet/web/releases/tag/%40napplet/shim%400.35.0), which [bind applet identity to a document-specific MessagePort](https://github.com/napplet/web/pull/302). The verified (dTag, artifactHash) identity is tied to the port handed over in the created iframe's hello, and all NAP traffic uses that port. A document loaded by navigation inherits no grants. Shells still using Window messaging must upgrade, as there is no compatibility path. Later source [locks the preview frame to its verified document](https://github.com/napplet/web/pull/305) with frame-src 'none'. [core 0.36.0](https://github.com/napplet/web/releases/tag/%40napplet/core%400.36.0) adds [opt-in maturity metadata](https://github.com/napplet/web/pull/288) that grants no permissions, and [core 0.35.0](https://github.com/napplet/web/releases/tag/%40napplet/core%400.35.0) implements [draft NAP-LLM](https://github.com/napplet/web/pull/284), leaving credentials and inference to the host. The CLI adds [HTTP and SOCKS5 proxy support](https://github.com/napplet/web/pull/297) with redacted credentials. The app store [pages a wider relay pool](https://github.com/napplet/web/pull/296), though truncated or failed requests leave coverage incomplete. It shows Labeling ([NIP-32](/en/topics/nip-32/)) screenshots from trusted signers, [bound to exact revisions with checked bytes](https://github.com/napplet/web/pull/289) and [looked up when a card is visited](https://github.com/napplet/web/pull/294). Open PRs add draft [Soulseek](https://github.com/napplet/web/pull/281), [navigation](https://github.com/napplet/web/pull/280), [torrent](https://github.com/napplet/web/pull/279), [motion](https://github.com/napplet/web/pull/278), [mesh](https://github.com/napplet/web/pull/277), [Blossom](https://github.com/napplet/web/pull/276) and [catalog](https://github.com/napplet/web/pull/275) domains, with only partial reference hosts and real backends left to each host.

### evil-napps tests manifest rollback

An open pull request in evil-napps adds a [manifest rollback harness](https://github.com/sandwichfarm/evil-napps/pull/11) showing that when a relay withholds a newer signed kind 35130 manifest, a miniature launcher installs older package bytes that still carry a valid signature. The harness uses real fixtures and forges no signature. Its result comes from a test launcher, so it does not show that every production launcher is exploitable or that the specification cannot close the gap.

### napplet/evil tests nested WebRTC realms

Merged in napplet/evil, a [grandchild-frame WebRTC probe](https://github.com/napplet/evil/pull/2) tests whether fresh nested realms regain WebRTC when the top realm has it disabled. The harness pairs a Trusted Types policy for string sinks with factory pins and refuses static frame markup. Demo mode configures no ICE servers, and active mode gathers STUN candidates only with explicit authorization. Results are author-reported from Chromium fixtures and do not prove any host secure; document.write is documented as a vector but not executed.

## Tagged Releases

### Marmish

Marmish is an experimental tool for running noninteractive remote commands over Marmot. The [Marmish v0.2.2 corrective prerelease](https://github.com/Epiphytic/marmish/releases/tag/v0.2.2) of the native Rust line adds `marmish --debug keychain-authorize` for an existing, ready macOS Keychain profile. You run it from a foreground terminal with that profile's daemon stopped. It asks for native permission for the two existing items, then checks access noninteractively. It keeps the identity and storage backend as they are and does not regenerate keys, rewrite ACLs or start the daemon. Ordinary daemon operation stays noninteractive. The release notes report that full candidate qualification failed. Interactive macOS consent, whether that consent persists, and recovery from the locked_or_denied error remain unverified. The platform command matrix and lifecycle qualification are incomplete. A Linux installed-command check passed but printed a background transport panic, which the release says may appear at shutdown. Supported targets are Linux AMD64 and ARM64 with glibc 2.39 or later, and macOS 15 or later on ARM64. The macOS build is ad-hoc signed and not notarized. Tor support is optional and experimental.

### Third Ear

Third Ear is a voice recorder and hands-free Marmot client for Android 12+ in an early 0.1 release series. In [Third Ear 0.1.0](https://github.com/jooray/third-ear/releases/tag/v0.1.0), the app uses its own identity to send voice notes and transcripts to groups. It also speaks replies aloud and offers optional on-device transcription. The [Third Ear 0.1.3](https://github.com/jooray/third-ear/releases/tag/v0.1.3) update adds a direct group composer for text and voice, with retry and a waveform player. A fix in [Third Ear 0.1.6](https://github.com/jooray/third-ear/releases/tag/v0.1.6) covers leaving a group as an admin, and a sole admin's group is removed only from the phone. [Third Ear 0.1.7](https://github.com/jooray/third-ear/releases/tag/v0.1.7) adds Android Auto recording as a media app plus playback of recent White Noise messages, and play events never start a recording. Sideloaded installs need the developer Unknown sources option enabled for Android Auto setup.

### Streets

Streets, a column-based web client, released [v1.23.0](https://github.com/eyemono-moe/streets/releases/tag/v1.23.0) to stop reconnect storms against unreachable relays. Failures now carry over between one-shot sessions, and read subscriptions wait out any remaining backoff. User writes still open immediately. [v1.23.1](https://github.com/eyemono-moe/streets/releases/tag/v1.23.1) brings back link cards for people and posts. It also opens Streets URLs that carry [NIP-21](/en/topics/nip-21/) (`nostr:` URI scheme) links. A later [merged change separating the outbox relay budget](https://github.com/eyemono-moe/streets/pull/1238) reserves 30 outbox-selected relays apart from explicit and default connections, under a 60-connection cap. The change does not report its effect on memory and startup.

### Marble

Marble, a beta client built on Cosign threshold signing, turns on a local circle filter by default in [0.12.21](https://github.com/sybenx/marble/releases/tag/v0.12.21). Your circle is the people you follow plus anyone at least two of them follow. Posts from outside it stay out of Following and rank lower in search, and their replies under your posts fold into one More replies line. Marking someone Not spam, or turning the filter off, overrides it. Posts can also be translated on the phone with downloaded language models. [0.12.19](https://github.com/sybenx/marble/releases/tag/v0.12.19) syncs each note field by field across devices and keeps conflicting text and removals.

### Plume

Plume, a Nostr client, received [relay URL and profile fetch fixes](https://github.com/cpkb-bluezoo/plume/commit/57e7f34ec73279e52e46608422230affd615c606) in a source commit. A relay URL with a bare trailing slash now maps to the same relay as its slashless form and shares one connection supervisor, while URLs with non-root paths keep those paths. An in-flight kind 0 profile fetch is now shared per author, so duplicate requests are not started. When media fails to load, the fallback shows the original URL where it used to show an internal torimg URI. That display repair says nothing about whether traffic stayed on Tor, and the commit offers no leak-prevention proof.

### Magnetar

Magnetar, a Nostr torrent discovery client and crawler, published prerelease [v0.3.2](https://github.com/awake-devel/magnetar/releases/tag/v0.3.2) with limits on hostile relay input. Relay messages are capped at 4 MiB. Pages are counted by decoded size with tag caps, and [NIP-77](/en/topics/nip-77/) (Negentropy Syncing) requests are bounded. A valid but oversized event is dropped without failing the relay. The [merged security changes](https://github.com/awake-devel/magnetar/pull/2) also check outbound addresses at connect time. Private and local addresses are refused, as are the server's own public addresses. Tracker redirect hops are checked again. The fixes only apply once the server and every worker are updated.

### Monostr

Monostr, a social client with Monero tipping, added reading for [NIP-23](/en/topics/nip-23/) (Long-form Content) articles in [v0.27.0](https://github.com/schmidt1024/monostr/releases/tag/v0.27.0). Readers can like and repost articles or reply to them. Bookmarks and tips work on articles too, and profiles get an Articles tab. The release also exports password-encrypted ncryptsec keys under [NIP-49](/en/topics/nip-49/) (Private Key Encryption) and accepts them for sign-in. [v0.28.1](https://github.com/schmidt1024/monostr/releases/tag/v0.28.1) fixes following when a user's follow list lives only on other relays, and tip setup no longer publishes a relay list that could hide older notes. The [v0.30.0 release notes](https://github.com/schmidt1024/monostr/releases/tag/v0.30.0) report that sending takes about one second where a silent relay could previously stall it for up to ten seconds. Reposts whose original cannot be read no longer appear as empty notes. Bookmark and mute changes now apply immediately, with rapid taps batched.

### Jumble

Jumble, a Nostr web client, adds Android support in [v26.11.1](https://github.com/CodyTseng/jumble/releases/tag/v26.11.1), according to its release notes. Replies to text notes can optionally use [NIP-22](/en/topics/nip-22/) comment events, and direct messages are now turned off by default. 

### Sidecar

Sidecar, a browser extension for publishing notes and web highlights, removes EXIF and XMP metadata plus IPTC blocks from JPEGs before upload in [v1.16.5](https://github.com/dmnyc/sidecar/releases/tag/v1.16.5). Profile and banner pictures are covered, while image data and color profiles stay intact. The [upload preparation change](https://github.com/dmnyc/sidecar/pull/572) stops a JPEG from uploading when it cannot be cleaned. This stripping applies to JPEG only. Auto-lock now measures computer idle time through a new browser idle permission and keeps the old timing if that API is unavailable. A later, unreleased [fix for encrypted backup sheets](https://github.com/dmnyc/sidecar/pull/583) restores the full 162-character ncryptsec from its two PDF lines. [CLINK offer payments](https://github.com/dmnyc/sidecar/pull/552) were reported last week as an open proposal in issue 46 and are now merged, though still unreleased. Payments now include a signed kind 9734 zap request. Users can switch between Lightning and CLINK when both are available, and a moved offer's successor is followed once.

### NosTube

NosTube, a Nostr video sharing platform, released [v0.2.52](https://github.com/flox1an/nostube/releases/tag/v0.2.52), which looks for videos and shorts on creators' [NIP-65](/en/topics/nip-65/) (Relay List Metadata) write relays in subscriptions and the home feed. That fixes discovery for creators who publish outside the viewer's read relays. Relay-list lookups are batched and cached. Their results are shared across requests. Content requests group authors by relay, with separate pagination for each relay. The viewer's configured read relays remain a fallback. A later source commit [moves homepage and next-video curation to the creator's kind 10001 pin list](https://github.com/flox1an/nostube/commit/5921d1e37e94a815b22df0c9bc4361552129dc2d). That change replaces the local selected-video configuration.

### Roadbeacon

Roadbeacon, a location-based road-reporting client that works over Nostr and MeshCore radio, released [v0.5.2](https://github.com/jooray/roadbeacon/releases/tag/v0.5.2). Radio transport moves to MeshCore's registered Road Events data type, `0x0150`. The development value `0xFF52` is no longer sent or accepted, so this release cannot exchange radio messages with builds that still use it. The publisher says all phones must update and lists other v0.5.2 installs and the matching build of the separate Roadstr radio-test companion app as compatible; these are stated requirements, not an observed exchange between devices. The event format and frame bytes are unchanged.

### eHagaki

eHagaki, a Nostr web client also available as an embeddable Web Component, released [v1.32.0](https://github.com/Lokuyow/ehagaki/releases/tag/v1.32.0). With the [reaction target change](https://github.com/Lokuyow/ehagaki/pull/395), users can reply to a kind 7 reaction with a kind 1111 comment. They can also quote it or repost it as kind 16. The reaction's owner can delete it. Actions never silently switch to the original post. [Animated WebP handling](https://github.com/Lokuyow/ehagaki/pull/396) sends GIF and animated WebP originals uncompressed and unresized, including custom emoji reactions, though upload servers may still convert or refuse them. A further merge lets users [paste a single image URL](https://github.com/Lokuyow/ehagaki/pull/400) in reaction mode to make a custom emoji.

### Feedstr

Feedstr, an experimental RSS reader, published its first public test binaries in [v0.0.1](https://github.com/0n4t3/Feedstr/releases/tag/v0.0.1), including an Android APK and a Linux Flatpak. It syncs feeds along with read state and favorites as [NIP-78](/en/topics/nip-78/) (Application-specific Data) records encrypted with [NIP-44](/en/topics/nip-44/) (Encrypted Payloads). Its author calls it unstable and barely tested. The APK is unsigned, and the Flatpak is not published in a store or repository. Feedstr's web client cannot fetch feeds itself and depends on the desktop or mobile app to cache content.

### XMRadar

XMRadar [0.6.3](https://github.com/KYC-rip/xmradar/releases/tag/v0.6.3) can copy a self-reply thread from an X post page into one Nostr note, in order, with each image kept under its post. Up to 50 posts are selected by default, and any can be unticked. Signing goes through a [NIP-07](/en/topics/nip-07/) extension. Images are reuploaded to Blossom with imeta tags, and notes carry at most five lowercase t tags ([thread copy](https://github.com/KYC-rip/xmradar/commit/ad9cc546426aabfeffaf7b678d35e43d519dcea9), [tag publishing](https://github.com/KYC-rip/xmradar/commit/fc0e59e9ae88c4812cf2c8c90bacc7c24c0823e0)). Optional tag suggestions stay off until you choose a provider. A local model then turns on automatically, while a remote provider stays off until enabled and sees the post text when used.

Newer source commits add a [desktop chat side panel](https://github.com/KYC-rip/xmradar/commit/91b31a7cb407f4aaddeaac3dc57d950da0d533a7) that frames the chat.xmr.club Nostr chat and switches rooms only when the user clicks. It does not send the current tab URL. A NIP-07 identity works there only if the signer functions inside the framed panel, and the panel's anonymous storage is separate from a normal tab. The frame permits popups but grants no top-navigation or modal permissions.

[Posting relay selection](https://github.com/KYC-rip/xmradar/commit/56aa219c449aa3970dc9288693384d630e9c6c00) prefers manually set relays and otherwise uses the account's NIP-65 write list from a one-hour cache. Fallback relays cover the remaining case, and a NIP-65 setting can force them. Lookups still fall back to three defaults. A relay that fails three posts is skipped for 24 hours without any edit to the user's list. If every relay is skipped, all are retried. Republishing stays limited to the original session's relays. These health marks are the extension's own observations and do not show that a relay is down for everyone. Opt-in [tip receipt checks](https://github.com/KYC-rip/xmradar/commit/c92fa42eef095e342dfa9d9431b5cef675b126de) query up to eight relays every half hour for NKIP-0002 kind 9042 receipts and keep a per-account ledger of seen receipts and notifications. A receipt is the tipper's own claim and does not prove a wallet payment, so notifications are worded as the tipper saying they sent a tip. NKIP-0002 has no official NIP status.

### Kithmoot

Kithmoot desktop [0.1.113](https://github.com/forgesworn/kithmoot/releases/tag/v0.1.113) added [delivery receipts](https://github.com/forgesworn/kithmoot/pull/618), on by default. Two ticks mean another person's device received a message, never that it was read, and background list-only rooms confirm only when opened. [0.1.120](https://github.com/forgesworn/kithmoot/releases/tag/v0.1.120) lets the desktop app run a call relay, which stays off until enabled. Hide IP asks before using another member's relay because its operator learns your IP. [0.1.125](https://github.com/forgesworn/kithmoot/releases/tag/v0.1.125) fixes the browser audio autoplay prompt and keeps the restored default TURN service.

The developer-signed [Android 0.6.132 announcement](https://njump.me/nevent1qqs8crua95hhwrw5x4zne3zxqtz070m4frdt75626mgrpvkptmehmzgprpmhxue69uhhyetvv9uju7npwpehgmmjv5hxgetkt95hv5) claims that calls without your own relay request a short-lived ForgeSworn relay login and continue if that fails. It also claims local network addresses are shared again and relay.trotters.cc is again the first default relay. Later web source [restores third-party default relays](https://github.com/forgesworn/kithmoot/pull/663) after relay.trotters.cc closed behind [NIP-42](/en/topics/nip-42/) authentication, and [drops the Google STUN fallback](https://github.com/forgesworn/kithmoot/pull/669) while keeping Cloudflare. Neither change is established in Android 0.6.132 or desktop 0.1.125.

Merged source for a private kithmoot-node now extends the earlier [node admission](https://github.com/forgesworn/kithmoot/pull/673) and [closure receipts](https://github.com/forgesworn/kithmoot/pull/674), which arrived with no UI enabled. [Hosted rooms for web and desktop](https://github.com/forgesworn/kithmoot/pull/675) add explicit pairing and admission with encrypted chat. Relay and call traffic in those rooms uses only the node. Hosts can remove members or close a room, and file sharing is off. Owner pairing is [one-use with no ownership transfer](https://github.com/forgesworn/kithmoot/pull/676). Authenticated TURN credentials carry an issuedAt and expiresAt interval with at most 30 seconds of future skew, and a cached lease lasts at most 300 monotonic seconds. A [private Debian and Ubuntu installer](https://github.com/forgesworn/kithmoot/pull/677) handles update rollback and secret-preserving recovery, and uninstalling requires a signed room closure. [Host-managed TLS and port profiles](https://github.com/forgesworn/kithmoot/pull/678) add descriptor pins, and a durable local deletion intent blocks new enrollment across restarts until it is cancelled.

Call recovery work followed. A network change now [refreshes credentials and relay-only ICE](https://github.com/forgesworn/kithmoot/pull/679). Transient HTTP errors keep a valid admission, while explicit refusal or removal still ends it, as do room closure and the 5 minute expiry. [Healthy media is no longer restarted](https://github.com/forgesworn/kithmoot/pull/680) over a quality estimate or a peer that never connected, and each established failure episode gets one recovery. Recovery [retains the TURN route and reconnects authenticated signalling](https://github.com/forgesworn/kithmoot/pull/681) before ICE recovery, and [registered native node peer receivers](https://github.com/forgesworn/kithmoot/pull/682) let it restore video after a missed track notification. Authenticated room and admission signalling is [probed every 5 seconds](https://github.com/forgesworn/kithmoot/pull/683), with silent sockets replaced independently of HTTP. These changes are merged in private source without a tagged public node release, and their publisher-reported local browser and native results qualify neither physical-phone use nor long public and VPN sessions, leaving capacity and wider deployment unqualified as well.

Two later source commits make subscription retries [wait for relay connection and authentication](https://github.com/forgesworn/kithmoot/commit/8c553672cbb3dcad850a703a151e868a9446763a) and check obsolete bindings before REQ, which avoids bursts of queued pre-auth retries. Idle socket closure and reopened connections [keep subscription refusal backoff](https://github.com/forgesworn/kithmoot/commit/c7db6eff86e91b6e381138bfeffaed8e12ff9cd5), so a reconnect cannot shorten a scheduled retry. Deadlines stay bounded. An open proposal would [make fixed media slots and reliable signalling the default for browser node rooms](https://github.com/forgesworn/kithmoot/pull/685), with pair recovery included. Explicit opt-out and old-peer negotiation remain, and ordinary rooms keep their current default. It depends on pull request 684 and ongoing long qualification, and its public 460 second result used an explicitly selected mode, so it does not prove the default candidate.

### Quartz

Quartz, a Kotlin Multiplatform Nostr library, shipped [live subscription resume after reconnect](https://github.com/vitorpamplona/quartz/pull/82) in release 2.14.0. Each relay resumes from the newest delivered created_at, capped at the device clock. Kind 1059 gift-wrap filters reach back two extra days to cover NIP-59 backdating. Events with older timestamps that a relay stored during an outage can still be missed. The new subscribeEvents flow ends when a relay refuses with a terminal CLOSED. Transient disconnects, rate-limit backoff and successful AUTH do not end it, though AUTH can still fail or time out, for example when there is no responder. Existing callback and list subscriptions stay open.

Merged code that is not yet released adds [count-aware negentropy windows](https://github.com/vitorpamplona/quartz/pull/85). An optional relay [NIP-45](/en/topics/nip-45/) (Event Counting) COUNT is compared with the local count and the larger value is used, so windows can split even when the local store is empty. Relay counts are untrusted. By default 10,000 count requests are allowed, and querying stops after two unanswered counts. After an empty EOSE, resume uses the earliest since value when all filters have one, capped by the clock. It returns null if nothing changed.

### nostrc libvault

### NYM

NYM's [current source](https://github.com/Spl0itable/NYM/commit/ead1401c81160043f0f8770d7d7fe3fa17601ca0) retries closed live subscriptions per target with exponential backoff that starts at 1 second and tops out at 120 seconds. ### Buzz

Buzz merged [relay-signed verified names](https://github.com/block/buzz/pull/8774). With [NIP-FI](/en/topics/nip-fi/) enforced and a stable relay key, the relay publishes kind 30382 records of names verified at sign-in, kept apart from access; bans don't retract them and kind 5 can't delete them. [Mobile displays them](https://github.com/block/buzz/pull/8858) once the ID and signature verify. Schema validation must also pass, and some screens still use kind 0. [Build-time organization sign-in](https://github.com/block/buzz/pull/8700) arrives on mobile as well. The app also [accepts unexpired issuer assertions with lifetimes past 300 seconds](https://github.com/block/buzz/pull/8935), leaving lifetime to the issuer while the relay still enforces maximum_assertion_age, and refreshes cached assertions 30 seconds before expiry; the pull request describes this as NIP-FI assertion handling and reports local tests only. NIP-FI is a Buzz specification, not an accepted NIP.

Open NIP-FI work would [add NIP-FI evidence to CLI requests](https://github.com/block/buzz/pull/8999) alongside [NIP-98](/en/topics/nip-98/) (HTTP Auth) or Blossom authorization on protected routes; remote-signer support there is an architectural capability with no provider delivered. A stacked proposal would [enforce a per-community requirement](https://github.com/block/buzz/pull/8988) on protected routes even when the global mode is off or shadow, with host-specific requires_nip_fi discovery answering 404 for unknown hosts and 503 when policy is unavailable; admission there is not activation, and draining existing sessions remains pending along with production acceptance. Another would [persist a community upgrade operation](https://github.com/block/buzz/pull/8985) bound to a durable generation, returning the same receipt for an identical retry and a conflict for a changed payload. That acceptance is default-off and stays pending until activation; switching the feature off does not undo it, and it creates no issuer trust. On iOS, a proposed notification extension would [mint NIP-FI assertions](https://github.com/block/buzz/pull/8982) only for exactly configured organization relay hosts using a device-only shared credential, so the session never reaches unrelated hosts. Sign-out would wait for that credential's removal, with generic notifications as the fallback on failure.

Relay fixes add [admin-flagged default channels](https://github.com/block/buzz/pull/8594) that don't re-add people who left and [CLOSED on failed history reads](https://github.com/block/buzz/pull/8692), though [NIP-50](/en/topics/nip-50/) search can still send a partial EOSE. Merged rules [refuse case-insensitive duplicate names](https://github.com/block/buzz/pull/8782) among a community's listed open channels. Archived channels count toward that check. Operators may rename only listed channels, archived ones included. Other channel types still need an owner or admin, and operators gain no moderator role. That change depends on a staged rollout with rename-script preconditions, so complete duplicate cleanup is not confirmed. Dropped bridge and profile searches now [cancel their database query](https://github.com/block/buzz/pull/8954) under a session timeout of at most 20 seconds that ends in a terminal 503 or WebSocket CLOSED. Cancellation may miss a replica after three attempts. In that case the timeout serves as fallback. A WebSocket CLOSE also does not stop an in-flight REQ task. Each relay process also [keeps at most four bridge searches in flight](https://github.com/block/buzz/pull/8956) per community and pubkey, superseding the oldest with a 409, though the cap is per process and a superseded search may still return results. A load-generator-only change [signs public https and wss URLs for NIP-98 and NIP-42](https://github.com/block/buzz/pull/8926) while dialing a plaintext address, leaving client and deployed authentication untouched. Banned owners' [workflows are refused at the trigger](https://github.com/block/buzz/pull/8242), and a ban [permanently revokes v2 invites](https://github.com/block/buzz/pull/8237); legacy repair needs operator migration.

Mobile channel lists now [refresh on live notice and metadata changes](https://github.com/block/buzz/pull/8910) in place of a minute timer. Coalesced reads start 2 seconds after the last event and no later than 10 seconds after the first. Reads are spaced at least 10 seconds apart. Each reopened subscription triggers one catch-up. A [follow-up](https://github.com/block/buzz/pull/8958) makes queued reads wait the full gap and skips changes already covered. Deletions or kicks without a notice and unarchived channels still wait for the next lifecycle or manual read, as does a race between metadata and the live filter. An open relay change would [emit membership notices for deletions and moderation kicks](https://github.com/block/buzz/pull/8977), including moderation DMs. [Channel links and search hits](https://github.com/block/buzz/pull/8923) now resolve their own metadata after a local-list miss, previewing unjoined open channels while private or withheld ones stay closed, and a lookup finishing after the user switches context opens nothing. Threads [request auxiliary events](https://github.com/block/buzz/pull/8870) to load edits that predate opening; relays ignoring the flag keep prior behavior.

Onboarding fixes [retry failed open-channel directory searches on reconnect](https://github.com/block/buzz/pull/8968) with the current query. Message search is unchanged. Another fix makes [each starter-setup retry wait on the current connection](https://github.com/block/buzz/pull/8967) with a community check and a 15-second timeout. The original failure remains unexplained. Desktop [skips a permanently unusable starter channel](https://github.com/block/buzz/pull/8911) and still joins the rest, while other refusals still fail. Scanned or pasted invites [open browser consent and resume the join](https://github.com/block/buzz/pull/8952) with the same identity and keep a retry if launch fails; camera scanning is untested. Invite launches [fall back to a Flutter confirmation](https://github.com/block/buzz/pull/8970) when the native presenter is busy, and a UIKit refusal clears the pending join for retry.

Merged push code [journals lease revocation on community removal](https://github.com/block/buzz/pull/8978) using the saved installation id even without a cached grant. Credentials with unknown expiry stay until the relay accepts revocation, and offline retries persist. Older clients expecting an integer expiry reject those pending records. A draft push stack covers [grant tokens](https://github.com/block/buzz/pull/8673) and [bound requests](https://github.com/block/buzz/pull/8703) under [quotas](https://github.com/block/buzz/pull/8704); follow-ups add [revocation capacity](https://github.com/block/buzz/pull/8705) and [cleanup](https://github.com/block/buzz/pull/8706) along with [endpoint rotation](https://github.com/block/buzz/pull/8707) and an [APNs key audit](https://github.com/block/buzz/pull/8708). Its pull requests describe mocked native callbacks, with App Attest and APNs on physical devices still unverified.

Open work adds [consent before cloud key backup](https://github.com/block/buzz/pull/8823), disclosing that Builderlab can decrypt it. An open [NIP-RS](/en/topics/nip-rs/) (Buzz draft: Cross-Device Read State Sync) profile would [sync read frontiers across devices](https://github.com/block/buzz/pull/8998) with a 30-day semantic floor and durable overflow slots holding signed pending envelopes, using identical-byte retries and a complete-snapshot prerequisite to avoid truncation. A draft would [track session boots and sticky community-generation floors](https://github.com/block/buzz/pull/8991). After obligations drain, the acknowledgment must match the exact boot and operation along with the exact generation. Required root and audio sockets close with 1008 on upgrade. Durable reconciliation recovers missed hints or restarts. Its production activation is disabled and baseline authority is unfinished. Unreachable boots stay pending without external discharge, and load testing must precede arming. Proposed mobile access work would [separate reading from contributing](https://github.com/block/buzz/pull/8963) in channels and Solo, requiring fresh signed authorization for access or member changes and recovering unknown writes only by readback; the relay stays authoritative and such writes may not have succeeded. Open [artifact-sync visibility recovery](https://github.com/block/buzz/pull/8933) would journal pending operations transactionally and prove overlap visibility or use the existing policy_changed reset, with reset and certification atomic; wire v1 is unchanged and the gate stays off for mixed writers. [Deletion fences](https://github.com/block/buzz/pull/8658) and [snapshot group state](https://github.com/block/buzz/pull/8898) remain open alongside a draft [guarded task archive](https://github.com/block/buzz/pull/8909).

### Applesauce

Applesauce, a collection of JavaScript Nostr utilities, extended its standalone messaging clients in [source](https://github.com/hzrd149/applesauce/commit/fd4acc5140cbc4e52fe2102c1ab4ffe379a907b8). In a breaking change, prepared message handles and event IDs replace retry scopes. Optional persistent storage can now hold drafts and unpublished legacy publications along with known correspondents. Decryption runs through one queue serialized across readers and conversations, and a [loaded decryption snapshot](https://github.com/hzrd149/applesauce/commit/8055bdc41efbee749396831693b953f3b835f3ce) separates unlocked and locked messages from pending and failed ones. The same commit lets a pending legacy publication retry by stored ID, restoring the signed event and its frozen relay list without a new signer prompt; references the client does not know are not rebuilt from the EventStore.

Apps must keep account and protocol storage separate and encrypt stored plaintext, since optional storage is not secure on its own. Reads observe the event store without network access, and loading and history sync are explicit. Legacy conversation watchers are reference-counted: the last unsubscribe releases only its own work, while an explicit stop cancels all conversation operations. Watching a conversation does not make its history complete. A [history coverage check](https://github.com/hzrd149/applesauce/commit/78285e8d38dc03c8f4d6be1c8f017456ad776925) counts history as covered only when a non-empty set of active sources succeeded across both time bounds; cache-only coverage is not relay success, and the example finishes only for the sources it was given. [Staged draft files](https://github.com/hzrd149/applesauce/commit/8885497c480c19dd9cd8dbdaf4c2423e1dc53414) can persist through an optional draftFileStorage adapter and upload only on send. That adapter receives plaintext files, so at-rest protection needs an encrypting store. Without an adapter, the files stay in memory only.

A new [NdrMessagesClient](https://github.com/hzrd149/applesauce/commit/374feacbc8748c3c3ec3379574d255dfa19fc632) integrates the optional nostr-double-ratchet 0.0.183 package as a separate import. It takes an explicit relay pool and account storage, and keeps a persistent outbox and history plus app-key devices. The host must supply durable encrypted storage and manage the account lifecycle. Its double-ratchet protocol is a project protocol, not an official NIP. No cryptographic audit is claimed. Kehto now [wraps that client](https://github.com/hzrd149/applesauce/commit/0253126b6c058c82f62eeb16633716ecf9432fbb) for routing and normalization with plaintext approval on top, while the client still owns the outbox and history along with device lifecycle. Hosts must start the client and register devices. Kehto's [legacy and NDR adapters](https://github.com/hzrd149/applesauce/commit/102a49862b0be44481904ff03c3563ddec618b8c) can borrow an app-owned client, which they never stop. They can also build a protocol-owned client from options, and that client closes with the protocol. On logout, the app stream becomes undefined.

[Encrypted attachment helpers](https://github.com/hzrd149/applesauce/commit/bb6709fd7e0de43806a92e20ac1ee910b3a3d0b4) upload ciphertext under a random AES-GCM key and deliver the key and nonce privately. NIP-17 sends files as kind 15, while NDR puts files in imeta tags on kind 14 because it uses kind 15 for receipts; both clients read either form. Uploading clients and recipient clients still need to adopt the format, along with host-managed encrypted storage and its adapters. No privacy audit is claimed. For relay AUTH, [shared queued-message batches](https://github.com/hzrd149/applesauce/commit/aec5a1a36fc62a17bc5c587f32dfc858484f7c88) authenticate pending relays one at a time and report each relay's outcome, and stop or dispose cancels the batch. [Queued approvals](https://github.com/hzrd149/applesauce/commit/932021041f0b1bb46b3f29e930b76a177cb1bddc) are keyed to the relay, so a replaced challenge updates the context without discarding an existing approval; failures stay per relay, and the change does not promise that users are never prompted or that authentication succeeds. An [open SerialPortSigner proposal](https://github.com/hzrd149/applesauce/pull/107) would redact RPC parameters and responses in debug logs, except ping and public-key calls, so raw restore keys and ECDH keys do not leak there; it touches only debug logging, and the plaintext serial link to the hardware remains a trust boundary.

### Negentropy

Negentropy, the set-reconciliation protocol and library used for event sync, has [fixed a fingerprint boundary bug](https://github.com/hoytech/negentropy/commit/fc53c6c12db03c0d27abfd1e956ba75c37152821). When the frame size limit stopped range processing, the sender fingerprinted the final open-ended range from the current range's upper index. Receivers read that range as starting at the last bound written. As a result, items between those two points could go unreported when both sides fingerprinted an empty set. The C++ and JS implementations now fingerprint from the last written bound, and a regression test for issue 20 covers the case. The message format is unchanged, and the [README](https://github.com/hoytech/negentropy/blob/2c6c171e10a4e0448c12b8181cbbfdd14190fc36/README.md) shows no new protocol version.

### nsite-template-filter

### nostr-verify

nostr-verify is a new Rust library for batch verification of BIP-340 Schnorr signatures, first tagged in the [0.1.0 release commit](https://github.com/VectorPrivacy/nostr-verify/commit/af9672bfbcae18ee30c2d7646a54682d6c4f2e9c). It caches parsed keys and isolates failures. When a randomized batch check passes, every signature in the batch is accepted without being checked individually. When it fails, the library splits the batch into eighths and then checks signatures one at a time with the reference libsecp256k1 verifier. It checks only signatures, so callers must first check the event id hash defined in [NIP-01 Basic Protocol](/en/topics/nip-01/). According to the [README](https://github.com/VectorPrivacy/nostr-verify/blob/af9672bfbcae18ee30c2d7646a54682d6c4f2e9c/README.md), randomized batching is sound but has a small, nonzero failure probability. The speedup figures are the author's own measurements on two specific machines at chosen batch sizes. The claim that batch results match individual verification rests on the project's own tests.

## Protocol and Spec Work

Except for one open proposal, the [Marmot](/en/topics/marmot/) changes below were merged into draft sections of the [Marmot specification](https://github.com/marmot-protocol/marmot). Draft encodings can change between revisions with no compatibility promise, and a merge does not mean any client ships the behavior.

### Marmot repairs a published sibling Welcome

The original adder keeps its exact Welcome and the private KeyPackage reference until expiry, so it can [resend those bytes in a fresh carrier](https://github.com/marmot-protocol/marmot/pull/493) without another Add or KeyPackage. No repair is sent if the target's matching leaf has moved on through an Update or Commit. A duplicate Welcome can be harmless because joining consumed the KeyPackage. As first specified, repair waited 600 seconds after the first observed authenticated activity from the target following confirmed publication. That older timing has since been superseded, and the current rule is covered under [Marmot makes Leave follow invitation generations](#marmot-makes-leave-follow-invitation-generations).

### Marmot makes Leave follow invitation generations

Marmot, the protocol for MLS-based group messaging over Nostr, merged a [specification change that ties Leave to invitation generations](https://github.com/marmot-protocol/marmot/pull/497). When an account leaves, it records a decline for the generation that admitted it. Its sibling devices from that same generation leave too. An account that is the last admin cannot leave until another admin exists. The decline hold limits only automatic Adds, and devices admitted through separate invitations stay in the group. A device that missed the SelfRemove commit in a generation it has not left may still re-add. Welcome repair now falls due once the target's heartbeat shows last activity at least 10 minutes after the latest accepted publication. Because heartbeats are hourly, repair can be delayed by up to an hour plus the target's clock lag. This heartbeat rule supersedes the older trigger, which waited ten minutes after the first native observation of authenticated activity from the target following confirmed publication. MDK's source still implements that older timing. The parked MDK follow-up does not adopt the newer rule either.

### Marmot synchronizes invitation decisions by generation

Marmot [merged invitation generations derived from authenticated admission](https://github.com/marmot-protocol/marmot/pull/496). Automatic Adds of a user's sibling devices inherit that generation, and kind 475 events synchronize each decision across devices. Accepting resolves how the invitation is presented without joining the group. Declining sends an ordinary Leave and holds further automatic adds. These rules apply to experimental upgraded clients. Separate generations are kept apart. Decisions on legacy invitations with no identified generation stay local.

### Marmot defines history-only backup restore

Marmot [merged a history-only backup restore](https://github.com/marmot-protocol/marmot/pull/494). It applies only to groups where the device is a current member and checks membership before any fetch. Imports then run serially. Imported history keeps its bundle and index binding along with message ordering and attachment keys. Preferences and group membership stay unchanged. Restoring transcripts from before a join and full disaster recovery are left for future work. Cancelling a restore can leave history partially imported.

### Marmot lets users edit linked-device settings after linking

All three device settings can now be [edited after a link, with recovery for lost edits](https://github.com/marmot-protocol/marmot/pull/492). The existing `rename_id` marker, with its encoding unchanged, now tracks every user edit to the label or settings. A lost edit is recovered before a later one is accepted, and non-user updates keep both the id and the values. Turning history on affects only future sibling Adds, with no backfill. Clients that write the earlier draft's settings updates must switch to the new rule, and mixed draft versions are not guaranteed to work together.

### Marmot fills a sibling's missing chat memberships

A linked device can now [add a sibling that is missing from one of its chats](https://github.com/marmot-protocol/marmot/pull/491) using private KeyPackages, rechecking the selected tree when it prepares the Add. A new kind `458` carries a ten-minute advisory claim that makes races between siblings less likely, though it gives no device exclusive ownership and may be forgotten on restart. Gap filling requires "add to all my chats" to be on, and automatic cleanup of duplicate leaves is deferred.

### Marmot includes linked siblings in a chat's founding Add

Chat creators now [include linked sibling devices in the founding Add](https://github.com/marmot-protocol/marmot/pull/490) when they hold private KeyPackages for them, tracking those sibling Welcomes separately from ordinary ones. Requirements for other accounts are never relaxed, and a client implementing this must not use its own account's public KeyPackages for siblings. Devices that are leaving or have no key are skipped. Devices that are removed or pending removal are also skipped. Inactive devices stay eligible. Missing private stock never delays creating the chat.

### Marmot withdraws a sibling Welcome whose Add lost

Before sending a sibling Welcome, a device must now [confirm that the Add behind it was selected](https://github.com/marmot-protocol/marmot/pull/489) in the target chat, keeping that link across restarts. A deferred Add holds delivery because it may still be selected, while terminal ineligibility or a terminal chat ends the obligation. Founding Adds skip this check, and completed joins are not undone. A message already handed to the transport can still arrive after its branch has lost.

### Marmot holds back a new device's chat Adds in two cases

The approving device now [adds the new device to no chat](https://github.com/marmot-protocol/marmot/pull/488) while that device's roster entry has no `tag_signature_key`, for example after branch selection drops the key, since it then cannot tell which chats already hold the device. It also adds nothing once any roster state it applied has held a `removed` record for that slot, even if a later branch lists the device again. It keeps that fact for as long as it keeps the key from that record.

### Marmot drafts how account backups are written

The device named as `backup_writer`, or a device that trusts no device group, now [writes encrypted backups to Blossom](https://github.com/marmot-protocol/marmot/pull/487) once the newest backup is a day old. A backup holds each chat's history bundles (excluding the device group) along with small-state items. It also holds a head sealing the archive key to the recovery key. A kind `30078` pointer lists up to 16 backups on NIP-65 write relays. Its address and encryption both derive from the recovery public key. Retention keeps at least the newest two. Another device takes over when no writer is named, when the writer has left or is leaving, or after the writer lists nothing for 7 days.

### Marmot cleans up after every device the roster stops listing

Removal cleanup now [runs whenever a sibling's slot is gone](https://github.com/marmot-protocol/marmot/pull/486), whether or not the roster still records it as `removed`. Each device keeps slot keys from roster states it applied, including states on dropped branches, for 30 days, so cleanup also covers a dropped `removed` record, a failed link after the key was set, and a link that a later branch dropped. The device removes the slot's tagged leaves in `0x800d` groups and deletes the private KeyPackages it exchanged with that slot. Untagged leaves stay, and cleanup is not reversed if the slot reappears.

### Marmot has the approving device add a new device to existing chats

The device named in a new device's `linked_by` field now [adds that device to the chats it is in](https://github.com/marmot-protocol/marmot/pull/485), including chats it joins later, while the roster lists the device as `active` with "add to all my chats" on. It uses same-account Adds of private KeyPackages and sibling Welcomes. No other device does this under the link. Chats it creates follow the founding-Add rule above. It skips chats that lack `0x800d`, a relay list, room for another leaf, or requirements the new device meets. A leaf from before the link can still leave the device with a second leaf in the same chat.

### Marmot lets a device sign out through its siblings

A device with a tagged roster entry and at least one sibling that is not leaving now [signs out by committing its own entry as `leaving`](https://github.com/marmot-protocol/marmot/pull/484). It then leaves every group except the device group and any chat with the `0x800d` extension where its own leaf is tagged as its own slot and another leaf is tagged as a sibling whose roster status is not `leaving`. A tagged sibling leaf alone, or one belonging to a leaving sibling, does not exempt a chat. It deletes its slot and local state, and siblings remove it after a random delay of up to 30 seconds. If the Commit is not confirmed within about 30 seconds, the device leaves every chat itself. Chats where its account is the last admin keep its leaf, and an unlinked device's sign-out leaves no group and deletes no slot.

### Marmot moves large history bundles to Blossom

A kind `473` history delivery can now [point to an encrypted blob held on one to four Blossom servers](https://github.com/marmot-protocol/marmot/pull/483) in place of an inline bundle, so a bundle can be any size up to the full 8 MiB limit. The sender uploads with BUD-02 first, and the receiver fetches with BUD-01, reads no more than 8,388,624 bytes and checks the SHA-256. Servers keep the blob's size and its upload and fetch times, and every sibling sees which servers hold it. Receivers built before this change drop these deliveries.

### Marmot unlinks a device its device group removes

A device that its device group removes, other than by undoing a failed link, now [treats itself as unlinked](https://github.com/marmot-protocol/marmot/pull/479) once the removing Commit is on the selected branch. It stops committing, messaging, publishing and answering pairing for the account until it deletes its local state, and can return only as a new sign-in with a new slot, while its siblings remove its leaves. Only the removed device enforces unlinking, so it may still hold the account key. A device that misses its removal keeps acting for the account.

### Marmot defines the recovery key that backups are sealed to

A [12-word BIP-39 recovery key](https://github.com/marmot-protocol/marmot/pull/476) now derives an X25519 HPKE key pair, and backup values are sealed to it under the label "Marmot Backup", with test vectors in the spec. Devices store only the public half in the roster's account entry and never keep the words, and turning backups on requires the user to type two of the words back. Account-entry changes use compare-and-set at the selected tip, so an update a fork drops can stay lost until the user makes the change again.

### Marmot adds history keys and history deliveries between devices

Each device now [writes an HPKE history key into its own roster entry](https://github.com/marmot-protocol/marmot/pull/467). When a device's Commit adds a sibling to a chat and that sibling has "bring chat history" on, the adding device owes it the chat's history. History goes out as kind `473` device-group messages carrying JSON bundles of up to 8 MiB, each encrypted with a one-use key sealed to the receiver. Deliveries were first inline-only within 32 KiB and can now use Blossom. Deleted messages are left out, and imported events are judged by their `pubkey` and moderation grant.

### Marmot narrows compromise handling to an own-slot warning

The spec now treats a [stolen account signing key as out of scope](https://github.com/marmot-protocol/marmot/pull/480). If a device finds a valid current-profile KeyPackage in its own slot that it did not make, it replaces it and warns only its own user. It neither tells siblings nor records anything in the roster, and it never claims the key holder was stopped. The rejected-KeyPackage machinery, rejection-based leaf removal and the kind `462` anomaly alert are all removed. Because `0x800e` drops those fields under the same id, existing experimental rosters must be recreated.

### Marmot refills a device's emptied KeyPackage slot

A device SHOULD now [publish a new KeyPackage into an empty slot](https://github.com/marmot-protocol/marmot/pull/477) when a complete, unbounded read from a relay that accepted its latest publication finds nothing there. That covers deletions it never saw acknowledged, including deletions by someone else holding the account key. Failed, truncated or time-bounded reads do not count. A refill waits until the latest publication is a day old, and it is skipped by devices that are signing out or whose slot the roster no longer lists.

### Marmot drafts device renaming, heartbeats and inactive devices

Roster entries now carry a [`rename_id` so that any device can rename any device](https://github.com/marmot-protocol/marmot/pull/462). That marker was later extended to settings edits. Each device keeps its own `client` and `platform` fields current. Each running device sends a kind `457` heartbeat in its device group about once an hour, and heartbeats never trigger push notifications. A sibling with no activity for 30 days is shown as inactive. This is a display-only judgment that must not be written into the roster status.

### Marmot specifies removing a linked device

A user can now [remove a linked device from another device of the account](https://github.com/marmot-protocol/marmot/pull/472). One device-group Commit removes the device's tagged leaf and records a `removed` rejected slot with its `tag_signature_key`, so a device whose entry has no tag key yet cannot be removed this way. The deciding device then deletes the removed device's KeyPackage slot, which is the one case where a device deletes a slot it did not create. Siblings clean up tagged leaves under the wider trigger above.

### Marmot carries private-KeyPackage Welcomes as sibling Welcomes

A Welcome that consumes a private KeyPackage now [travels as a kind `461` sibling Welcome](https://github.com/marmot-protocol/marmot/pull/471) inside the device group. It carries the consumed `KeyPackageRef` and one to 16 chat relays, and it must never go through the ordinary Welcome transport. The receiver joins only if the sender's device tag matches the slot it handed that KeyPackage to, and the join stands even if branch selection later withdraws the Welcome. The newer rules above govern when to send or repair these Welcomes.

### Marmot lets a device delete a far-future publication in its own slot

Sometimes a device's slot serves a publication the device did not make, dated so far ahead that the device's own publication cannot outrank it. The device may now [ask relays to delete that event](https://github.com/marmot-protocol/marmot/pull/468) and then publish into the slot again. On Nostr, the request is a kind `5` event dated at the current time, with exactly one `e` tag naming the event and one `k` tag of `30443`. Receivers that select KeyPackages still ignore `e` tags.

### Marmot proposal explores shared epoch authors in place of routing tags

An [open, non-normative proposal](https://github.com/marmot-protocol/marmot/pull/464) explores replacing routing tags with event authors shared per epoch, which would let clients filter floods from outsiders by epoch author. It defines no interoperable bytes or exporter labels, so interoperability remains undefined. It also depends on [NIP-D9 Deletion Request Protection](#a-proposal-exempts-signed-events-from-their-authors-later-deletion-requests), a separately proposed Nostr NIP that has no assigned number and has not been merged. A removed member still holding old keys could flood catch-up history, and questions about privacy and quotas remain open along with recovery.

### Marmot adds slot announcements, own-slot checks and private KeyPackages

Devices in a device group now [announce each KeyPackage in their roster entry](https://github.com/marmot-protocol/marmot/pull/459) before publishing it. Every device checks its own slot at startup and about once a day, and it replaces any current publication other than its latest. Siblings also exchange private, single-use KeyPackages through new kinds `459` and `460`, topping a sibling's stock up to 10 when it falls below 5. These private KeyPackages are consumed only through sibling Welcomes. Devices without a device group publish as before.

### Marmot syncs read positions, pins, mutes and archives between devices

An account's devices now [share small per-chat state](https://github.com/marmot-protocol/marmot/pull/466) in the device group through new kinds `475` and `476`. That state covers read position, pin, mute and archive. The furthest read position wins, and the other items resolve by highest version, then lowest random change id, then lowest value. Each device broadcasts at startup and at least every 24 hours, and also when the device group's tip moves past the app-payload window. Only chats whose MLS group id is at most 256 bytes have this state.

### Marmot merges draft device pairing with emoji verification

The device pairing proposal covered earlier is now [merged as a draft feature](https://github.com/marmot-protocol/marmot/commit/7b7312e2d96b9f1f6c610fe48f15b03a2133aec2). A new device and an existing device of the same account compare seven emoji from Matrix's `m.sas.v1` verification, exchanged in five rumors that the account gift-wraps to itself. The code binds the session, the account, the new device's `KeyPackageRef`, the answering device's slot and both keys. Existing devices send at most 10 Answers an hour. The merge registers kinds `452` to `456` and reserves `457` to `489` for multi-device use.

### Marmot specifies linking a device into the device group

After a confirmed pairing, the approving device now [adds exactly the confirmed KeyPackage](https://github.com/marmot-protocol/marmot/pull/456) in one Commit that sets the new device's roster entry. If it trusts no device group yet, it founds one first. The new device joins only the Welcome from the named leaf into the named group, which must require `0x800e`. It keeps the link for up to 600 seconds after its Confirm. If the new device's first Commit is still missing 3600 seconds after `linked_at`, the approving device undoes the link. Merging two device groups is not specified yet.

### Marmot asks users about new sign-ins on the account

Clients that support `0x800e` now [treat an unknown slot holding a valid, fresh KeyPackage as a new sign-in](https://github.com/marmot-protocol/marmot/pull/465) and ask the user about it. Slots that already belong to roster devices or rejected slots do not count. Answering "This wasn't me" commits a `not_me` rejected slot, and once one device links or rejects the slot, the question is settled on all of them. A Welcome naming an unfamiliar KeyPackage only triggers a check, and that check is complete only when every KeyPackage relay has returned a full answer.

### Marmot merges the device roster and device tag components

The device roster and device tag drafts covered earlier are now [merged as components `0x800e` and `0x800f`](https://github.com/marmot-protocol/marmot/commit/a3edd1e12432894812409046d04f3a9a7e9af5ba). A group that requires `0x800e` from creation is the account's device group. Its roster is updated by diffs and holds devices, rejected slots and the key that seals device tags. All of the group's leaves share one credential identity. Device tags let siblings tell the account's leaves apart and never make anything invalid. The roster encoding has since changed under the same id.

### Post-quantum event signatures gain exact validation rules

The long-running open post-quantum signature proposal gained [exact ML-DSA-44 validation rules for Nostr events](https://github.com/nostr-protocol/nips/commit/43104cbff30ae006e907d8ee0ec15c4949d0eef6). Keys and signatures must match a fixed pair of lengths. Verifiers recompute the canonical event ID and check the signature over the 32 raw digest bytes with an empty context, and no fallback algorithm is allowed. Long keys need full-length storage and support in author and tag filters. The proposed identity has no NIP-19 encoding or migration binding, and changing the signature does not make NIP-44 or NIP-59 encryption post-quantum safe. An experimental PQRelay adapter built on pinned Stroma primitives does not meet full conformance, and the reviewed implementation and evidence leave its long-key filtering and replacement compatibility unverified.

### Napplet identity moves from reusable windows to private document ports

The OPEN [NIP-5D](/en/topics/nip-5d/) proposal now [binds napplet identity to a private MessageChannel port](https://github.com/nostr-protocol/nips/commit/c041f84667c1781c3c1d5bfbd970943131b38cc9). Bootstrap code creates the channel before any untrusted script runs, and the first validated hello links the verified artifact identity to that port. The iframe Window is excluded from the binding because it survives navigation. A second hello, a window message, a load or a port error closes the port, revokes grants and the session, and removes the frame without rebinding it. Bootstrap must keep the retained port unreachable, since a browser can transfer a reachable port cross-origin and the port can outlive the frame. Data already disclosed can still leak through a navigation URL, and CSP is not guaranteed to block every exfiltration path.

### A proposal gives authors relay-signed visit aggregates

A new OPEN proposal labeled NIP-F8, which is not an assigned or merged NIP number, [defines relay-counted visits with signed aggregates for authors](https://github.com/nostr-protocol/nips/pull/2532). Clients send kind 20918 ephemeral visit events, which relays deduplicate per pubkey and per IP each hour before publishing kind 30918 relay-signed aggregates that only the AUTH-authenticated author receives. Author-only delivery does not make readership private end to end, because the counting relay still handles every visit. A fork implementation exists, but the schema is not an accepted standard.

### Repost attribution gets a proposed via tag

A new OPEN proposal without an assigned number adds [a via tag that credits the repost through which a user found a note](https://github.com/nostr-protocol/nips/pull/2533). The tag holds the repost event ID, a relay hint and the reposter pubkey. It is paired with a p tag for the reposter, so supporting clients can display the activity as a share. The original note target is unchanged, and clients without support may show a plain mention. The final revision dropped an earlier attribution-only, no-copy rule. Attribution reveals how the user came across the note. No released client support is claimed.

### A proposal exempts signed events from their author's later deletion requests

An OPEN proposal labeled D9, with its NIP number still pending, defines [a no_delete marker that shields an event from its own author's deletions](https://github.com/nostr-protocol/nips/pull/2531). Exactly one single-element, case-sensitive no_delete tag marks an otherwise valid regular event, and replaceable, addressable and ephemeral kinds are excluded. Supporting relays and clients ignore NIP-09 and NIP-62 purges signed by the same key, including during backfill and republication. Gift-wrap deletions by recipients, separate delegator authority, expiration and local storage policy still apply. Once signed, the marker cannot be reversed for that ID, but nobody is obliged to keep hosting the event.

### A language-model proposal carries tool calls without executing them

A new OPEN extension to the NAP-LLM proposal adds [typed tool calls and results to model streams](https://github.com/napplet/naps/pull/138), with stable call IDs, content block start, delta and end events, model capabilities and inference controls. Only the authoritative final tool-use result exposes a completed call. Streamed fragments never authorize execution, and truncated or refused calls are discarded. The runtime LLM domain must not execute tools, so a napplet needs separate authority to run them. Thinking output is display-only and left out of replayed input, while opaque continuation is reported as unsupported and never silently substituted.

### Navigation revisits settle by reported location

An OPEN navigation revision [settles pending revisits by reported location](https://github.com/napplet/naps/commit/d929d45b2e83c6e7bb3b21bce4e1832b3dbe27f3) and removes deliveryId. The first accepted location report above the recorded revision settles a pending revisit, and a matching convention and payload selects the existing visit while keeping forward history. Settlement depends on the reported value regardless of cause, so local navigation to the target also counts. Two identical pushes in a row count as a replace, and a null-location mode is invalid. NAP-INTENT is a required capability, and delivery does not mean rendering has finished.

### Contact picking stays separate from address-book browsing

A new OPEN NAP-CONTACTS proposal offers [read-only access to email endpoints and optional Nostr pubkeys](https://github.com/napplet/naps/pull/140). A trusted picker discloses only the selections the user explicitly confirms, while query and get calls need a separately granted browse authority. Handles and scoped cursors are not permission tokens, and email read or send grants do not cover contacts. Revoking access or switching users drops any choices not yet returned. A listed key or address neither proves identity nor grants permission to send, and no runtime implementation has been verified.

### Email readers and composers share scoped messages while the shell keeps credentials

A new OPEN NAP-EMAIL proposal covers [reading and sending through configured SMTP and POP3 accounts](https://github.com/napplet/naps/pull/139), plus retained sent and inbox thread views and locators napplets can share. The shell owns accounts, TLS and credentials. A napplet receiving a locator needs its own read grant, and send-only access is not read permission. SMTP submission is durable per identifier with at most one attempt, so an uncertain outcome stays uncertain and repeating an identical submission creates no duplicate. Contacts integration is optional, and users can still enter addresses by hand. No runtime implementation has been verified.

### Napplets request user-selected language-model inference

A new OPEN NAP-LLM base contract lets napplets [request inference from a model the user selects](https://github.com/napplet/naps/pull/134). The shell owns provider connections, keys and model choice. Each generation sends a complete, stateless conversation. The user authorizes disclosure and charges for each generation before any prompt or image leaves the shell, so a stored key or model selection does not count as consent. A cancellation or timeout does not prove the provider stopped charging, so requests are never retried blindly. Only a provider fixture exists, and nothing is deployed. Tool calling is covered by a separate extension.

### Git operations stay separate from publication and proposals

A new OPEN NAP-GIT contract covers [Git objects, refs and verified byte views](https://github.com/napplet/naps/pull/137), with local compare-and-swap ref updates and explicit fetch, push and propose operations. The shell owns repository selection, signing and credentials. A Git or ngit backend can run behind it without filesystem access or command passthrough. Creating a commit, writing a local ref, pushing to a remote and opening a proposal are separate effects, and the ngit branch convention must not turn a push into a proposal. Network publication with an uncertain outcome is not retried blindly. No NAP implementation has been verified.

### One download-job contract covers native and external NZB engines

A new OPEN NAP-NZB contract [standardizes NZB submission, jobs and controls](https://github.com/napplet/naps/pull/136), while the runtime keeps daemon credentials, configuration and paths. A native engine, or an NZBGet or SABnzbd adapter, must advertise only the features it implements, and a remote-control-only backend need not expose output bytes. Reading completed output is optional and needs separate authorization. Backend history or a file path does not prove that a job completed or that the files are accessible. Native and adapter support are both unverified.

### Intent replay stays bound to the selected running instance

An OPEN intent revision [binds replay to the selected running instance](https://github.com/napplet/naps/pull/128) and removes delivery IDs and the null shell sender. The shell can replay only an invocation the target itself produced earlier, setting the sender to the target's own catalog ID while the ordinary wire format stays the same. If the selected endpoint fails, there is no fallback, restart or substitution. A napplet cannot claim that instance by forging a payload, and ordinary invoke still uses standard catalog resolution. Delivery is not a completion receipt.

### A Soulseek contract separates search, transfer and disclosure

A new OPEN NAP proposal for Soulseek offers [bounded search, peer browsing and endpoint-scoped transfer handles](https://github.com/napplet/naps/pull/135), with downloading, reading bytes and saving each needing separate authorization. A transfer counts as complete once the expected bytes arrive, which says nothing about cryptographic integrity or who wrote the file, and Soulseek accounts are not bound to Nostr identities. Tearing down the endpoint stops the work, and background jobs are not recovered. No NAP implementation has been verified, and the source's backend examples do not show that any domain has adopted it.

### Shell media can play an authorized torrent file

A new OPEN NAP-MEDIA extension accepts [a scoped torrent job and file index as a playback source](https://github.com/napplet/naps/pull/133) for shell-owned playback only. The separate playback grant gives the napplet no raw bytes and no wider file selection, and the shell buffers and seeks only within the selected file using verified metadata and content. Pausing playback does not pause the job or seeding, while revoking the source authorization ends playback and discards buffered bytes. No implementation or deployment is claimed.

### Torrent jobs gain a scoped file workflow

An OPEN revision of the NAP torrent proposal [separates torrent transfer](https://github.com/napplet/naps/pull/72) from [NIP-35](/en/topics/nip-35/) [indexing and signing](https://github.com/napplet/naps/pull/72). It removes search, publish, comment and fromEvent along with the identity and relay dependencies, and adds job file handles, file selection, verified bounded reads and saves, and retention controls. Apps that want Nostr torrent catalogs use the relay and identity domains for that. Control over a transfer grants no authority to export bytes, and host paths and sockets are never exposed. No tested runtime implementation is claimed.

### Concord repairs missing and stale membership records

An OPEN Concord pull request gained [a commit that repairs membership records](https://github.com/concord-protocol/concord/commit/7c64a24fd4f0230392f1183343e2dffb2a592ca9). Lifting a ban now first writes a Kick departure dated at the Ban, so a Join from before the ban cannot reappear once the banlist entry is removed. The departure honors the authority of whoever holds BAN. A member with a complete plane read but no state of its own SHOULD restore its Join at the plane timestamp so all its devices write a single rumor, resending the exact same signed Join on retry and never while its own Join still stands.

### Carried SNO objects become part of the parent payload

The inline-object table is now [merged into the Cyberspace spec with normative privacy and validation rules](https://github.com/arkin0x/cyberspace/commit/9210d6dff16637079c8339a9c957c60cbd3a744e). A root table resolves a-address placements before any relay fetch, with each entry under the carrier author's key. An entry that is present but invalid gets a placeholder and no fetch. Carried objects are sealed inside the bag, and republishing from a bag omits its table unless the user chooses to include it. This adopts the rules into the spec and makes no release claim.

### Doors and chest looks enter the Cyberspace DECK

Doors and chest looks are now [merged into the Cyberspace DECK specification](https://github.com/arkin0x/cyberspace/commit/bd9125eea93274ee589657f0bd23203916ead40f). A kind 3341 door identifies one room at a specific height. Its key comes from the location key plus a door secret, and the room bag is sealed. Multiple and nested doors are supported, and rotating a lock SHOULD rotate the secret and reseal the bag. For each closed or open shape the first well-formed look tag applies, and a failed payload means no look. Test vectors await a first implementation, and no broad client release has been shown.

### Audited legacy-hop IDs preserve movement through cutover

A merged change [fills the header-only legacy compatibility list with audited hop IDs](https://github.com/arkin0x/cyberspace/commit/957021e2138b1477d2255e2678f0de889eb5fcd6), listing 2,658 v1 hop IDs that passed the audit and leaving out 8 that failed. The exemption matches exact IDs only, with no date-based grace period, so listed hops from before the cutover stay valid. The census read only one relay and missed the feeds relay, so the list may not cover every historical hop. These counts come from the published audit and were not independently reproduced.

### The residue revision gains normative signed chain vectors

The residue chain revision now has [158 normative signed movement-chain vectors](https://github.com/arkin0x/cyberspace/commit/3ffa27552a6f65e75f235a6bea93930333b065b1). Of these, 140 were ported and 18 are new. For each case, the vectors fix the expected verdict and position as well as the failure point. The list override they use applies only to the fixture. This required conformance file is separate from the non-normative proof vectors. Its events are synthetic fixtures and do not represent real users.

### Hop-proof test vectors become portable across languages

Merged [machine-readable golden vectors for hop proofs](https://github.com/arkin0x/cyberspace/commit/06c287332651f99b75e609b7b098e165993750fd) tie one reference to 7 prover hops and 26 verifier cases. They also pin edge indices, prices and lengths. Ports in other languages can compare exact encodings and check that they reject malformed or copied proofs. The vectors are non-normative, and the spec text takes precedence if they disagree.

### Cyberspace adopts sampled residue proofs for movement

Cyberspace merged [a chain revision built on sampled residue proofs](https://github.com/arkin0x/cyberspace/commit/8b45430af330f6e93ee763716d33868706cc2879) into its specification. Hop proofs now commit to Merkle-sealed modular residues with 16 sampled openings, so verifiers check word-sized residues without rebuilding giant roots, while trees and location keys are unchanged. The new proof, mn and mp tags are mandatory except for exact audited legacy IDs. The [cyberspace-core 0.2.1 TypeScript library](https://github.com/arkin0x/cyberspace-core/commit/5587818ea0a7bae313b99db2acc5430a2549c609) implements these proofs with an exported prover and verifier and carries the specification's exact census-1 legacy hop list. It uses an embedded WASM word kernel where one can be instantiated and falls back to JavaScript otherwise. It defaults to native BigInt arithmetic. Both are source milestones for the specification and its library, not a client release.

### Buzz adopts complete artifact snapshots over WebSocket

Buzz [merged its WebSocket artifact snapshot implementation](https://github.com/block/buzz/commit/a56966b777278f703040b4686820a201bc278c57), adopting a project-local [NIP-AR](/en/topics/nip-ar/) extension that issue #46 covered while open; it is not an official NIP, and no tagged release is confirmed. A REQ for current artifacts in #h channels returns a consistent database snapshot at EOSE followed by live heads, with no offset or limit and a cap of 4,096 artifacts per set. Access changes, lag, redaction or queue drops trigger an explicit resync CLOSED, never a partial EOSE. A node crash after commit but before publish can still miss a live change, so clients that need a bound must resync on their own schedule.

### Buzz merges incremental recovery for saved artifact stores

Buzz also [merged incremental HTTP recovery for saved artifact stores](https://github.com/block/buzz/commit/a57349b237c67c3983dd7a09af378977ccd1e3f9) under the same project-local NIP-AR extension. After a disconnect, signed queries with checkpoints and cursors replay current upserts and explicit removals, and a known-ID read confirms accepted writes and access state; a record missing from a page never proves deletion. Timestamps come from the database clock with a 120-second overlap, which assumes commits land within that window. The feature is off by default behind BUZZ_ARTIFACT_INCREMENTAL_ENABLED, and migrations 0076 to 0078 and all writers must be upgraded before enabling it. Testing covered local HTTP only, not native clients.

### Buzz proposes a reversible community-wide flat thread policy

An OPEN DRAFT Buzz pull request [proposes a project-local NIP-TP flat thread policy](https://github.com/block/buzz/pull/8841), which is not an official NIP. A kind 9034 command sets a community to nested mode (the default) or flat mode, and NIP-11 advertises the choice. Admins or owners send the command, and in an ownerless open community any authenticated member can. Flat mode changes only display: every reply shows the root as its parent at depth one, and the root's count includes all descendants. Stored signed events and raw queries stay the same, so switching back to nested restores the tree. Policy-aware clients post new replies to the root, while older clients still post and see nested replies.

### Buzz makes assertion lifetime issuer policy

Buzz's project-local [NIP-FA](/en/topics/nip-fa/) (Buzz draft: Federated identity adapter) [specification now treats assertion lifetime as adapter operator policy](https://github.com/block/buzz/pull/8934). An assertion's exp cannot exceed the adapter session expiry or the issuer maximum_assertion_age the relay accepts. Clients must not reject an assertion solely because of its lifetime. The chosen lifetime bounds how long a revoked key could keep reconnecting after a relay restart. NIP-FA is not an accepted NIP, and [NIP-FI](/en/topics/nip-fi/) is unchanged and carries no fixed five-minute rule.

### Buzz proposes consented conversation imports

An open Buzz proposal defines [consented conversation imports](https://github.com/block/buzz/pull/8981): every participant must consent to the same manifest, and each author signs their own imported messages. Kinds 42110 through 42113 carry proposal and consent events along with withdrawal and completion, while the relay tracks a kind 30623 session. Imported kind 9 and kind 7 events carry import and source tags, and relays advertise nip-ci in NIP-11. The relay implementation validates each import session's transactions. This remains a project-local protocol under review, not an accepted NIP.

### A proposed signed precondition prevents lost event replacements

An OPEN Buzz pull request [proposes a project-local NIP-CS signed precondition](https://github.com/block/buzz/pull/8835) that extends Buzz's expected-revision tag for canvases and workflows to replaceable and addressable events; it is not an official NIP. The signed tag names the current head ID or `none`, and the relay checks it atomically under a coordinate advisory lock, answering a stale write with a false OK or HTTP 409 and storing nothing. Tagged replacements must still win NIP-01 ordering, and untagged writes work as before. The tag grants no permissions and gives no compare-and-swap guarantees across relays. Only the relay, SDK and docs are covered so far.

### Cordn makes coordinator retractions converge across devices

Cordn, coordinator-assisted MLS messaging over ContextVM and Nostr and a separate project from Concord, [merged a rule that makes last-resort KeyPackage coordinator claims converge](https://github.com/Cordn-msg/cordn/pull/12). The encrypted multi-device meta document now holds the current set of published claims, no longer an accumulated union. Adopting that set replaces local claims, so linked devices stop resurrecting removed coordinators. An absent field means unknown and must not be read as a retraction, while `[]` means published nowhere. A device with an unpublished retraction waits before adopting older peer claims. An unreachable coordinator may still hold an orphaned copy, which automatic resolution must not re-adopt.

### Chama proposes a block-hash draw to replace grindable arbiter picks

Chama merged [documentation for a drawn-arbiter escrow proposal](https://github.com/jesuspirate/chama/pull/104) marked not in force, with no enforced rule and no client implementation. Today the arbiter is picked from the CREATE ID hash, which a signer can grind by re-signing CREATE. The proposal commits a candidate pool and filter in CREATE and a future Bitcoin block height in JOIN, and after 3 confirmations that block's hash and the trade ID set the arbiter order. Joiners recheck candidate bonds and are warned about omitted keys, though omissions can still narrow the draw. Each principal gets two vetoes before funding, and after LOCK the arbiter is fixed in the key shares and the Taproot address.

### Pubkey-scoped Blossom pinning draft

An unofficial optional draft in nogringo/protocols proposes [pubkey-scoped Blossom blob pinning](https://github.com/nogringo/protocols/blob/0aa454e590c9743ae4e880dbc2da89f55f50179d/bud-blob-pinning.md), with no assigned BUD number. Upload and mirror authorizations can name `p`-tag pubkeys to pin for. Authenticated `PUT` and `GET` pin requests act only on the signer's own pin, as does `DELETE /pin/<sha256>`. Servers MAY delete a blob after its last pin and MAY restrict retrieval to pinners.

### Recipient inbox-server discovery draft

A companion [inbox-servers draft](https://github.com/nogringo/protocols/blob/0aa454e590c9743ae4e880dbc2da89f55f50179d/bud-inbox-servers.md), also unofficial and dependent on blob pinning, proposes a custom kind `11708` inbox server list with `server` tags. Senders upload to recipient servers with a `p` tag and fall back to kind `10063`. Receivers search `11708` then `10063` using get tokens. Private pin visibility hides recipient deletion timing from senders, but pinning provides no encryption.

### Hashtree drafts versioned encryption and references

A [new Hashtree specification draft](https://github.com/mmalmi/hashtree-spec/commit/4811761e9378b1ef877565c47e0f2a428d2a7dbe) describes experimental mutable Nostr references and 33-byte encryption keys that begin with a suite prefix. Its chk-v1 suite derives keys deterministically, while rnd-v1 uses randomized keys. Readers keep accepting legacy 32-byte keys, but new writes use the versioned form. The draft is independent and has not been adopted as a BUD or Nostr standard; its htree and nhash formats remain experimental along with its media handling and kind 30064, so implementations should name the exact specification commit they follow.

## NIP Deep Dive: NIP-31 and NIP-73

Clients often meet content they do not natively understand. [NIP-31: Dealing with Unknown Event Kinds](/en/topics/nip-31/) gives an unfamiliar event kind a readable label, and [NIP-73: External Content IDs](/en/topics/nip-73/) names subjects outside Nostr, such as books or webpages. The two conventions are independent existing specifications ([NIP-31 text](https://github.com/nostr-protocol/nips/blob/master/31.md), [NIP-73 text](https://github.com/nostr-protocol/nips/blob/master/73.md)).

### NIP-31 is marked unrecommended

The current [NIP-31 text](https://github.com/nostr-protocol/nips/blob/master/31.md) opens with a warning that marks it `unrecommended` as "unnecessarily bloated," and its status line reads draft, unrecommended and optional. Events using the convention already exist on relays, so the mechanics below describe how clients read them, with no recommendation for new protocols.

### What an alt tag carries

Under the [spec](https://github.com/nostr-protocol/nips/blob/master/31.md), an author of a custom kind not meant to be read as text adds an `alt` tag with a short plaintext summary. Kind-1-centric clients are not expected to request other kinds, but users can still reference such events from notes, where a summary supplies context. A label cannot cast a vote or act on a wallet request. For richer interaction the spec points to [NIP-89: Recommended Application Handlers](/en/topics/nip-89/).

Because `alt` is a tag, the event ID and signature from [NIP-01: Basic protocol flow description](https://github.com/nostr-protocol/nips/blob/master/01.md) cover it. A valid signature authenticates an author-controlled summary: it shows the author published the label without showing it is accurate, so misleading summaries are possible. Tags are public, so an `alt` on an event with encrypted content exposes its summary and can reveal what the content conceals. These properties come from the [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md) envelope, outside NIP-31's normative text. A top-level `alt` tag is also distinct from the image-description `alt` field inside `imeta`, and renderers parse them separately.

### How two clients read alt

In noStrudel's [unknown-event card at commit 7c68acf](https://github.com/hzrd149/nostrudel/blob/7c68acf4f148260d8e59879975f71c4f1bd004df/src/components/embed-event/card/embedded-unknown.tsx), the first `alt` tag is trimmed and becomes the main label, with an optional `Using <client>` line. A missing or blank value yields `Unknown event (kind ...)`, and up to three lines of content appear independently. The same component resolves the `client` tag through NIP-89 handler templates, showing Open when a shareable address exists and `Open in <client>` when a valid handler link resolves. Explanation and app dispatch are separate controls.

Amethyst's [UnknownEventDigest.kt at commit 553f761](https://github.com/vitorpamplona/amethyst/blob/553f761f22c15e946730d3e76be9487519ebab64/commons/src/commonMain/kotlin/com/vitorpamplona/amethyst/commons/rendering/unknown/UnknownEventDigest.kt#L168-L170) prefers content it classifies as prose and falls back to `alt`. Its parser trims values and takes the first nonblank `alt`, so an event whose first `alt` is blank can be labeled differently here than in noStrudel. Both descriptions reflect source at those commits, not confirmed release behavior.

### NIP-73 subjects and families

The [NIP-73 specification](https://github.com/nostr-protocol/nips/blob/master/73.md) (draft, optional, with no unrecommended flag) puts an external subject in an `i` tag and its identifier family in a `k` tag, so clients can query one exact subject or a whole family. A book uses `["i", "isbn:9780765382030"]` with `["k", "isbn"]`, and a webpage uses its URL with `k` set to `web`. NIP-73 defines no event kind; other events carry the tags.

### Normalization and URL hints

Matching depends on identical strings, so the [spec](https://github.com/nostr-protocol/nips/blob/master/73.md) fixes a form per family: URLs normalized without a fragment, ISBNs without hyphens, geohashes lowercase, ISO 3166 codes uppercase. An optional third array element carries a URL hint for clients with no opinion on the identifier. The author chooses that hint, and it is not part of the identity. It also proves no ownership and names no canonical site.

### What a shared identifier does not prove

Under [NIP-73](https://github.com/nostr-protocol/nips/blob/master/73.md), equal identifiers join conversations and establish nothing else. A signed comment identifies its commentator, and it does not authenticate the book, site or podcast publisher or show who controls them. Aliases, edition-specific ISBNs and URLs that normalize differently can split one subject into several threads. Context matters: [NIP-22: Comment](https://github.com/nostr-protocol/nips/blob/master/22.md) uses uppercase `I`/`K` for root scope and lowercase `i`/`k` for parent, and [NIP-39: External Identities in Profiles](/en/topics/nip-39/) uses `i` for profile identities, so not every `i` tag is a NIP-73 subject.

### NIP-73 in parser and renderer code

rust-nostr's [nip73.rs at commit 4c8099a](https://github.com/rust-nostr/nostr/blob/4c8099aef646dca13a5c402f4d0d77cd792a8390/nostr/src/nips/nip73.rs) parses known prefixes into a typed `ExternalContentId` and turns an optional hint into a typed URL, emitting the third tag element only when a hint exists. Its tests keep hyphenated ISBNs: the parser strips the prefix and stores the rest without applying spec normalization, so typed parsing does not guarantee canonical strings. It separates chain IDs from the family, mapping `ethereum:100:tx:<hash>` to `ethereum:tx`. That revision has no `iso3166` country variant.

Amethyst's [DisplayExternalId.kt at commit 553f761](https://github.com/vitorpamplona/amethyst/blob/553f761f22c15e946730d3e76be9487519ebab64/commonsUI/src/commonMain/kotlin/com/vitorpamplona/amethyst/commons/ui/note/nip22Comments/DisplayExternalId.kt) sends geohash and hashtag identifiers to dedicated displays. URL identifiers also get a dedicated display, while other supported types go to a generic scope chip. A URL opens the app's own thread route for that page. With previews disabled, normal rendering shows a plain link chip and requests no preview. With previews enabled, fetching a missing preview can contact the target site. Turning previews off avoids that request in normal rendering. Neither file establishes release behavior.
