### Mostro

[Mostro](https://github.com/MostroP2P/mostro), the Nostr-coordinated peer-to-peer exchange daemon, [released 0.20.1](https://github.com/MostroP2P/mostro/releases/tag/v0.20.1). It adds [signed identity rebinding](https://github.com/MostroP2P/mostro/pull/1035), which [last week's issue](/en/newsletters/2026-10-21-newsletter/#mostro) described as unimplemented, and ships the previously source-only reputation exports. The bound identity signs a single-use authorization naming the node and new identity, valid for at most an hour. The daemon records the event ID and switches with a compare-and-swap, so a failed signature or lost race changes nothing. Operators also have an audited loopback-only RPC that requires an auth token and a reason. Rebinding does not revoke attestations already issued.

Later merges are not confirmed in a release. An [opt-in fixed USD peg provider](https://github.com/MostroP2P/mostro/pull/1083) adds USDT, USDC and DOC to the Nostr `mostro-rates` feed only when the operator enables it. Network providers and relayed coin quotes do not turn it on implicitly. [A follow-up](https://github.com/MostroP2P/mostro/pull/1091) renames the provider and its config key to `pegged`, replacing the unreleased `stablecoins` key. It also quotes BTC, LBTC and RBTC at a fixed 1:1 in sats and publishes the rates as kind 30078 events. These configured peg assumptions leave the peg and settlement unguaranteed. Live peg checks remain outside this mechanism. The provider is off by default. Accepted currencies still gate orders; client, protocol-book and peg-guard work is separate. [Bond timelocks now run separately from escrow](https://github.com/MostroP2P/mostro/pull/1085). Advertised order expiry is clamped, and the take window on the order book closes before a bond can expire. Existing 144-block maker bonds expire on upgrade, and those orders must be recreated. Running trades and Cashu mode are unaffected, but some operator configurations refuse to start until the bond timelock is adjusted.

### Nostr WoT extension

The [Nostr WoT extension](https://github.com/nostr-wot/nostr-wot-extension), a browser signer with web-of-trust features, released [0.8.15](https://github.com/nostr-wot/nostr-wot-extension/releases/tag/v0.8.15) with an option to create the recovery key from 256 bits of the user's own dice or coin entropy. Dice rolls are hashed with SHA-256 and coin flips are used as raw bits, in an isolated tab that does not show the recovery phrase. Onboarding now times out when relays are unreachable. [Version 0.8.16](https://github.com/nostr-wot/nostr-wot-extension/releases/tag/v0.8.16) added standing grants for [relay authentication (NIP-42)](/en/topics/nip-42/), so users can approve AUTH once for all relays on a site or for every connected site ([relay-authentication implementation](https://github.com/nostr-wot/nostr-wot-extension/pull/47)). Relay or site denials override these grants, and revocations are rechecked before queued requests resolve. Broad scopes are always an explicit user choice and never apply to [HTTP Auth (NIP-98)](/en/topics/nip-98/). The queue cap stays at five, so excess requests still fail and retry. [Version 0.8.18](https://github.com/nostr-wot/nostr-wot-extension/releases/tag/v0.8.18) merges import and recovery into one flow that detects key formats and previews the identity, and compatible Nosskey recovery keeps the same identity, existing accounts and original passkeys.

The separate developer SDK, [nostr-wot-sdk](https://github.com/nostr-wot/nostr-wot-sdk), released [3.0.1](https://github.com/nostr-wot/nostr-wot-sdk/releases/tag/nostr-wot-sdk%403.0.1) with stable identity 1.1 support. Passkey recovery, including through Nosskey, keeps the original pubkey, and provider, recovery and signing code now share one implementation ([SDK recovery and provider source](https://github.com/nostr-wot/nostr-wot-sdk/pull/22)). Deprecated forwarder packages still work, but integrators should move to the maintained entry points.

### Amethyst

[Amethyst](https://github.com/vitorpamplona/amethyst), the Android and desktop Nostr client, released [version 1.20.0](https://github.com/vitorpamplona/amethyst/releases/tag/v1.20.0) with [private polls and other Marmot encrypted group features](https://github.com/vitorpamplona/amethyst/pull/4630). These include replaceable private votes, custom encrypted emoji, admin removal and reports, and media pinned to the group's current epoch. The author did not rerun cross-client interoperability checks after review and did not test the change by hand on Android. Cache keys for competing branches that share an epoch number remain, and encrypted media keys can outlast disappearing messages. [Settings sync](https://github.com/vitorpamplona/amethyst/pull/4613) stores six groups of app settings as encrypted [NIP-78](/en/topics/nip-78/) data. Keys, signers, wallets, notifications, decks and read markers stay on each device. The first settings edit publishes all six groups. A read-only account keeps its settings local, and behavior across two signing devices is unverified.

Desktop system notifications [follow the Notifications filter](https://github.com/vitorpamplona/amethyst/pull/4650) and skip throwaway outer gift wraps and muted DMs. [Untrusted `d` tags over 255 bytes](https://github.com/vitorpamplona/amethyst/pull/4616) no longer cause errors. [Kind lookups](https://github.com/vitorpamplona/amethyst/pull/4600) query only connected and account search relays, up to 200 events each. The apps [use Quartz's Kite JSON handling](https://github.com/vitorpamplona/amethyst/pull/4595) for frames, events, filters, and [NIP-46](/en/topics/nip-46/) and [NIP-55](/en/topics/nip-55/) messages, though signing over those two protocols was not verified on devices. A later [library split](https://github.com/vitorpamplona/amethyst/pull/4654) moves Marmot and cordn protocol rules that other clients would need into shared libraries.

Merged source after 1.20.0, not yet in a release, [runs the app's Marmot receive path on the shared library](https://github.com/vitorpamplona/amethyst/pull/4672). Every decrypted message is persisted idempotently. Joining records a baseline so the first membership change shows its row. A kind 445 message that arrives before its commit is held and replayed later, and admin catch-up commits staged departures. `amy cordn migrate export` disables the old home's session commands until an import or the new resume command. The author ran loopback amy tests and library tests against local checkouts. The author did not manually exercise the live app receive path or run the Marmot interop suite. [A breaking update](https://github.com/vitorpamplona/amethyst/pull/4659) to the proposed [NIP-5D napplet format](/en/topics/nip-5d/) reads a napplet manifest hash as one `/index.html` artifact, replacing the old path aggregate, so legacy bundles need republishing. Required NAP domains that are unavailable fail closed, and optional ones stay absent. Icons get hash and decoder checks, storage is partitioned by manifest kind, artifact and snapshot, and resource blobs use canonical base64. Manual device testing, cross-client testing and live relay publication were not done.

[Refusals in an external signer](https://github.com/vitorpamplona/amethyst/pull/4669) are now handled across coroutines that had no guard, so they no longer crash the app. [PressStr ebooks, magazines and issues](https://github.com/vitorpamplona/amethyst/pull/4662) (kinds 33953, 34609 and 39731) now render. PDFs open in the in-app reader and EPUBs go to the system handler. Cards show file type and size, never download a large PDF just to preview it, and fetch issues only from the magazine's author. The author did not report Android-device testing for this change. When rich previews are off, [invoices and LNURLs appear as compact copyable labels](https://github.com/vitorpamplona/amethyst/pull/4663) without a Pay button, and invoice cards now show expiry times. `amy gift wrap` [now dates the seal and the wrap at separate random times](https://github.com/vitorpamplona/amethyst/pull/4661), each up to two days back. `--no-backdate` turns this off. The regular DM path gets its fix separately in Quartz. On desktop, [each video card owns its playback](https://github.com/vitorpamplona/amethyst/pull/4660), so cards with the same URL no longer take over each other's video. The author tested this on macOS but not with a cold cache. A [proposed Windows link fix](https://github.com/vitorpamplona/amethyst/pull/4666) opens links through rundll32 by its full path and falls back to AWT. The root cause was not reproduced, so this is a likely fix and not a confirmed one.

### Myco adds encrypted napplet storage and signed update notices

Myco, an Android host for Nostr napplets, shipped 0.12.0 and [0.12.1](https://github.com/Origami74/myco/releases/tag/v0.12.1). Napplets can now store [NIP-44](/en/topics/nip-44/) [self-encrypted data](https://github.com/Origami74/myco/pull/152) through the runtime, but apps with relay, outbox or mesh read grants can see the plaintext, so the data is not isolated per app. Users who logged in with Amber earlier must log in again to grant the new encrypt and decrypt permissions. Update notices are signed by a pinned publisher and reach only devices already running 0.12. Online, Myco can check Zapstore daily and Circle, while mesh-only mode asks only Circle, replacing the [initial pause](https://github.com/Origami74/myco/pull/151). An explicitly chosen local Blossom rail keeps files on the device with no server, up to 64 MiB per app per day. Failed uploads to an approved default server also keep a local copy. Neither path strips EXIF metadata. The releases also add Android TV support and a NAPFS file picker where the user chooses the files.

### Sidecar

[Sidecar](https://github.com/dmnyc/sidecar), a Nostr browser extension and signer, [released 1.16.3](https://github.com/dmnyc/sidecar/releases/tag/v1.16.3). The composer and highlight tool now [publish to the account's own relays and count only relays that acknowledge the event](https://github.com/dmnyc/sidecar/pull/545), then link to those relays. An acknowledgment shows the relay accepted the event, not that it will keep it. The expanded composer no longer falls back to the default relays in Settings. Each relay has its own 12-second deadline. Only a publish that fails on every relay is retried, once, on fresh sockets. [Poll results](https://github.com/dmnyc/sidecar/pull/544) also query four public relays for ballots. A change merged after the tag [adds one more relay](https://github.com/dmnyc/sidecar/pull/550) to catch ballots filed outside the usual relays. On one live poll, this raised the count from 21 votes to 23. That is one poll's result and says nothing about completeness across the network. Counting still allows one ballot per person and ignores ballots cast after the poll closes. The earlier [1.16.1](https://github.com/dmnyc/sidecar/releases/tag/v1.16.1) limits standing signing grants to the account and site that approved them, and to a single addressable record when the event has a d tag. Grants never cover encryption or decryption. Profile, follow, mute and relay lists stay outside any grant. Deletions, zap requests, relay AUTH and wallet control are excluded too. A locked extension still asks for the PIN. Revoking a grant or forgetting a site clears its grants and approval windows.

A separate [open pull request](https://github.com/dmnyc/sidecar/pull/552) would make paying a CLINK offer count as a zap. It is queued under Unreleased in the changelog and does not implement Debits. The offer panel would pass a signed kind 9734 zap request with payer_data, so the service can publish a kind 9735 receipt. Receipts would go to the offer's relay first and then the recipient's relays, deduplicated and capped at six. The payer's relays are not used. If an offer replies with code 3 and a successor offer that decodes, Sidecar would follow it once with a new request and a new signature. It would never write to the recipient's profile. The change was still unmerged at the cutoff.

### Chama

[Chama](https://github.com/jesuspirate/chama), an escrow trading client built on Nostr events, [released 6.4.31](https://github.com/jesuspirate/chama/releases/tag/v6.4.31), which checks seed backups before funding. Before this device's on-chain trade key enters signed CREATE, JOIN or deposit terms, a relay must return the signed seed backup the device opened; a missing, retired or conflicting backup stops the trade. Retries resend the exact saved backup without a new seed. The readback shows availability then, not persistence. Multi-unit listings now use quantity orders. [Version 6.4.30](https://github.com/jesuspirate/chama/releases/tag/v6.4.30) counts storefront orders only when buyer-signed terms match the signed listing and guards against late outsider events on trades whose signed CREATE is dated 1 December 2026 or later, while earlier trades keep the old expiry behavior ([trade-expiry and storefront validation](https://github.com/jesuspirate/chama/pull/77)).

An open pull request, unmerged at our source cutoff, would allow [one wallet seed backup per identity](https://github.com/jesuspirate/chama/pull/92). Startup would serialize first creation with an in-page queue and Web Locks, then reread relay state. Separate browsers rely only on that reread. A distributed lock and repair of existing conflicting backups remain outside this change. We did not test any money path.

### Linky

[Linky](https://github.com/linky-fit/linky), a Cashu wallet that syncs through Nostr, added experimental on-chain transfers behind a flag in [version 26.10.7](https://github.com/linky-fit/linky/releases/tag/linky-v26.10.7) and [the Android 26.10.8 build](https://github.com/linky-fit/linky/releases/tag/linky-v26.10.8). A configured human operator completes send and receive requests within 24 hours for a fee, so transfers are neither atomic nor trustless. [The coordination change](https://github.com/linky-fit/linky/pull/637) uses custom Nostr app messages, [NIP-78](/en/topics/nip-78/) operator configuration and a new link sync scope. That scope syncs the operator's pending ecash sends so its other devices cannot pay, refund or settle the same send twice. A receive completes only when the user's wallet gets the matching Cashu amount. Operator and user find each other only on recommended relays, not through [NIP-65](/en/topics/nip-65/) relay lists or DM inbox lists, so losing every shared relay can break coordination.

### LaWallet

[LaWallet](https://github.com/lawalletio/lawallet-nwc), a wallet and account service built on Nostr Wallet Connect, released [version 2.9.0](https://github.com/lawalletio/lawallet-nwc/releases/tag/v2.9.0) and [the Android 1.2.0 beta](https://github.com/lawalletio/android-wallet/releases/tag/v1.2.0), both adding NFC card-assisted recovery to a new Nostr login ([native recovery flow](https://github.com/lawalletio/android-wallet/pull/1)). Recovery needs a fresh, cryptographically verified card tap and a single-use recovery QR code valid for 15 minutes. Assets move in one transaction, roles do not transfer, old OAuth grants are revoked and the old login is left empty. Card recovery is on by default; account holders can disable it in Security settings and revoke outstanding codes. An unreachable wallet now shows a zero balance, which does not mean it is empty. The Android beta forces Sentry error reporting on in builds with a reporting endpoint, even after an earlier opt-out; local and F-Droid builds have no endpoint.

In source merged after the tag, [the card callback can return OK before NWC settlement](https://github.com/lawalletio/lawallet-nwc/pull/385) when the balance covers the payment, so point-of-sale systems must confirm their own invoice. [A fixed payment cap](https://github.com/lawalletio/lawallet-nwc/pull/388) replaces the balance-based limit. An open pull request, unmerged at our source cutoff, would allow sign-in with compatible passkeys from other apps through a configured provider or Nosskey recovery, confirming the account before issuing an expiring temporary session ([#386](https://github.com/lawalletio/lawallet-nwc/pull/386)). A provider can sign without importing the private key, and importing is a separate confirmed choice. Its screenshots show simulated demo responses, not proof of live cross-origin sign-in.

Another merge, also unconfirmed in a release, stops the NWC and Lightning address callback [from replacing a user's remote wallet after a make_invoice error alone](https://github.com/lawalletio/lawallet-nwc/pull/389). A liveness and balance check can keep the wallet and return a 503 instead. The service also remembers balances and protected-fund state, and it adds a Restore option. Its thresholds and the unknown earlier history limit what it can protect, so it does not guarantee that all funds are safe. No deployment or restored user accounts are claimed.

### KithMoot

[KithMoot](https://github.com/forgesworn/kithmoot), a Nostr-based app for room chat and calls, now works without its publisher's public services. Between October 21 and 23 the publisher [retired public meeting codes, the shared TURN service, file uploads and stored file reads](https://github.com/forgesworn/kithmoot/pull/535). Invite links replace meeting codes, and public files default to Yakihonne with a first-send notice, though users can pick their own server. Calls still try a direct connection first, while Hide IP needs a working TURN server and never falls back to direct. In desktop 0.1.102 and Android 0.6.106, [Cloudflare's public STUN replaces the publisher's](https://github.com/forgesworn/kithmoot/pull/548), and users can set their own. [Served backup copies were deleted](https://github.com/forgesworn/kithmoot/pull/543), while [offline encrypted copies remain](https://github.com/forgesworn/kithmoot/pull/545). [Desktop 0.1.109 and Android 0.6.121](https://github.com/forgesworn/kithmoot/pull/596) block chat when device credentials expire while keeping drafts, and [read the user's own profile name separately](https://github.com/forgesworn/kithmoot/pull/594) from optional directory lookups. The ordinary call engine has not switched to the experimental [realtime SDK preview](https://github.com/forgesworn/kithmoot/pull/561), and the [MLS group candidate](https://github.com/forgesworn/kithmoot/pull/583) stays off by default.

[Desktop 0.1.110](https://github.com/forgesworn/kithmoot/releases/tag/v0.1.110) adds [sandboxed attachment viewers](https://github.com/forgesworn/kithmoot/pull/597) for images, audio, video and PDFs on desktop and the web. On desktop they run in a dedicated, non-persistent Electron renderer with no Node access, no application storage and no external network access. Streaming is bounded, and viewers are cleaned up when closed or when a message is retracted. The pull request's WebKit run and an extra packaged hostile-SVG run stalled and are not claimed as verified, and none of this is a security certification. The macOS build is notarized, while Windows remains an unsigned preview.

A later merge, not shown to be in 0.1.110, [renews expired device credentials by wall-clock time](https://github.com/forgesworn/kithmoot/pull/605) after sleep and before sending, keeping the draft while the signer responds. It follows a tester's credential expiring overnight on a sleeping laptop. A signer request that never returns still holds renewal open, and Android has a separate unresolved renewal gap. An open pull request, unmerged at our source cutoff, would [pause Help other people connect](https://github.com/forgesworn/kithmoot/pull/606). The author says the app accepts a peer-assist pair without carrying its media, which can stop the fallback to a forwarder or TURN and leave a silent call. The library default would stay unchanged.

### Marmot TS

[marmot-ts](https://github.com/marmot-protocol/marmot-ts), a TypeScript library for the Marmot encrypted group messaging protocol, shipped [v0.8.0](https://github.com/marmot-protocol/marmot-ts/releases/tag/v0.8.0) and [v0.9.0](https://github.com/marmot-protocol/marmot-ts/releases/tag/v0.9.0) with breaking changes. Encrypted media V2 adds source binding and decrypts delayed media after a restart, and Blossom upload descriptors, destinations and ciphertext are validated before signing. Persisted groups backfill in pages with retry for uncertain commits. Apps must now supply durable ingest and rewind stores whose adapters reject failed or timed-out reads. Legacy V1 groups must be recreated, since V1 helpers remain for history only.

Later merged source [gives the key-package, invite and history watchers an optional AbortSignal](https://github.com/marmot-protocol/marmot-ts/commit/bce57044f91251040807b1c0fd7a739046ee2f4e). Their listeners are cleaned up promptly on return, throw or disposal, even while a storage read is still pending. Changes that arrive while a consumer is paused are latched and merged into one update. The underlying backend read continues after cancellation. Query failures still reject, and the change does not certify runtime interoperability.

### Nostr mail client

[nostr-mail-client](https://github.com/nogringo/nostr-mail-client), a mail client built on Nostr, released [v0.19.0](https://github.com/nogringo/nostr-mail-client/releases/tag/v0.19.0) with one login flow for bunker, nsec and ncryptsec, including approval of a remote signer's auth_url. ### Napplet conformance CLI

[napplet/web](https://github.com/napplet/web), the web packages and tooling for napplets (web apps distributed as signed Nostr events), now ships last issue's verification work in the versioned [@napplet/conformance-cli 0.4.0](https://github.com/napplet/web/releases/tag/%40napplet/conformance-cli%400.4.0). ### napplet-soy

### MDK

MDK, the SDK and runtime for Marmot encrypted groups, released [stable v0.14.0](https://github.com/marmot-protocol/mdk/releases/tag/v0.14.0). It ships media file handoff and storage, ordered offline catch-up, follow-list preservation and raw SQLCipher key rekeying, with MLS and the wire format unchanged. The [0.14.0 release guide](https://github.com/marmot-protocol/mdk/blob/v0.14.0/docs/release/0.14.0.md) and [0.14.0 integration guide](https://github.com/marmot-protocol/mdk/blob/v0.14.0/docs/integration/0.14.0.md) require apps to ship a matching set of bindings, native library and headers, which [MarmotKit 0.14.0](https://github.com/marmot-protocol/mdk/releases/tag/marmotkit-v0.14.0) packages for Apple and Android. On Apple platforms the binary is a raw static XCFramework, so apps pair it with the matching Swift binding and copy its PrivacyInfo.xcprivacy resource into the wrapper product they assign; passing the release's archive checks does not prove an App Store export will succeed. Database and storage migrate one way, rekeying every page once. Downgrades remain unsupported. Account media and handoff data should be excluded from backups. The WN agent remains prerelease, and the crates are not on crates.io. Known limits persist: history arriving more than five epochs late becomes undecryptable without notice. Media lost in flight across an epoch advance is unfixed; a group-context ordering compatibility issue also remains.

Tag ancestry shows the stable tag also carries five sync and media changes. [Group subscription refreshes repack only changed REQ batch families](https://github.com/marmot-protocol/mdk/pull/2583); a failed family keeps its live routes for the next sync while the partial commit still reports a failed sync. [Sends and group changes keep entering the durable queue when a pre-send refresh fails](https://github.com/marmot-protocol/mdk/pull/2567), though completion can stay CompletionUnknown. [An unreachable relay's REQ stays owed under the same ID until reconnect](https://github.com/marmot-protocol/mdk/pull/2572), so degraded coverage is not complete history. [Onboarding repair approval waits for every discovery source](https://github.com/marmot-protocol/mdk/pull/2545) and returns RetryableFailure when a declared source times out. [Opt-in per-account media retention](https://github.com/marmot-protocol/mdk/pull/2541), from Keep forever down to 30 days, cleans media by received time or last explicit redownload, not last view, without deleting message history. Hosts must handle the new CleanedBySetting FFI value.

After the tag, merged source continued multi-device and push work that no release yet claims. [Post-join history requests persist](https://github.com/marmot-protocol/mdk/pull/2635) across commits and restarts, closing a gap between the Welcome and live messages. [Counting members per account](https://github.com/marmot-protocol/mdk/pull/2634) stops false notices about a person when a second device joins or leaves, and [Welcome handling ignores deliveries meant for sibling devices](https://github.com/marmot-protocol/mdk/pull/2633) without failing the join or consuming a key. For push, MDK [gossips owner-signed records and tombstones after commits](https://github.com/marmot-protocol/mdk/pull/2620) on [new push gossip storage](https://github.com/marmot-protocol/mdk/pull/2617), [re-shares tokens after membership adds](https://github.com/marmot-protocol/mdk/pull/2613) and [notifies all of a recipient's devices](https://github.com/marmot-protocol/mdk/pull/2609), though the sender's own devices still get no notification. [Fresh random padding per trigger](https://github.com/marmot-protocol/mdk/pull/2608) keeps deduplication from suppressing wake-ups. [KeyPackage publishing adopts the account's own relay lists](https://github.com/marmot-protocol/mdk/pull/2594) and fails, preserving the stored list, if a list is incomplete or has no usable relay. [Typed stale-epoch and unsettled media statuses](https://github.com/marmot-protocol/mdk/pull/2312) tell apps whether to upload again or sync and resend, and [transfer state changes arrive immediately with byte progress batched](https://github.com/marmot-protocol/mdk/pull/2311).

Newer account-device source is progress toward a later release, not a stable 0.15. Three October 28 nightlies, labeled testing-only, are pinned to commit b8d0a49, which predates later merges, so their assets do not contain all of it. MDK [selects compatible KeyPackages per device](https://github.com/marmot-protocol/mdk/pull/2649) for up to 20 recent devices per account, and [signing out withdraws only this device's publication slot](https://github.com/marmot-protocol/mdk/pull/2654). [Fresh packages last 30 days plus one hour and refresh six to seven days after publication](https://github.com/marmot-protocol/mdk/pull/2643). Discovery seeks every device, but relay failures can omit some; re-inviting may help, with no guarantee of automatic recovery. [Authenticated per-leaf capability checks](https://github.com/marmot-protocol/mdk/pull/2645) replace the per-account cache. [New groups require the account-devices component 0x800d](https://github.com/marmot-protocol/mdk/pull/2656) when every founder supports it, and [upgraded devices now advertise it](https://github.com/marmot-protocol/mdk/pull/2659). Such groups reject older devices lacking it, while existing groups stay unchanged. Under the requirement MDK [rejects component data, unsupported leaves, more than 20 leaves per account and attempts to drop the requirement](https://github.com/marmot-protocol/mdk/pull/2637), leaving legacy and nonrequiring groups as they were. Separately, it [refuses host-supplied initial data for app components whose schema has no data](https://github.com/marmot-protocol/mdk/pull/2662) before any group, Welcome or event is created.

In 0x800d groups the engine gains [own-account add and remove authority with parent-state-aware commit classification](https://github.com/marmot-protocol/mdk/pull/2650), separating self-update, self-remove, same-account and admin commits, with same-account privilege requiring by-value proposals. [Matching Welcome handling accepts same-account Welcomes](https://github.com/marmot-protocol/mdk/pull/2646) only in those groups and only after component state and signature checks; other groups still need an active admin. [Own-account add and remove send intents get a fair scheduler turn](https://github.com/marmot-protocol/mdk/pull/2655), but app APIs do not expose same-account send intents yet. [A device's own leaf removal now decides its local membership](https://github.com/marmot-protocol/mdk/pull/2640), so a sibling's presence no longer keeps a removed device's member actions.

Push gossip adds [durably queued kind 447 announces carrying 8-byte digest prefixes of records and tombstones](https://github.com/marmot-protocol/mdk/pull/2648), sent on join, on record change and on a seven-day message cadence, and peers [repair missing owner-signed records](https://github.com/marmot-protocol/mdk/pull/2658) through ranked, staggered responses with duplicate suppression and a 24-hour bound per leaf. In recovery, [cut and cancel no longer invent fresh loss](https://github.com/marmot-protocol/mdk/pull/2673), and 24 attempts without progress park an obligation behind an incomplete-history warning. The [coverage ledger](https://github.com/marmot-protocol/mdk/pull/2667) runs only as a shadow recorder, while a [time-sliced sweep](https://github.com/marmot-protocol/mdk/pull/2665) resumes oldest-first slices with no production scheduler yet. [Opt-in audit files expire](https://github.com/marmot-protocol/mdk/pull/2664) 30 days after the last write, with cleanup at startup and hourly. Deletion can occur a day later; the separate key-reveal security log is excluded from that expiry.

A [pairing crate](https://github.com/marmot-protocol/mdk/pull/2670) uses ephemeral X25519, a commitment, a seven-emoji comparison the user checks on both screens, and HMAC confirmations ending in a ConfirmedLink. Its wire adapter covers transport only and is off by default pending a spec, the UI and the Welcome and group-link follow-ups are unfinished, and interoperability of this implementation remains unverified. [Device-roster 0x800e source](https://github.com/marmot-protocol/mdk/pull/2666) applies diff updates to a hidden single-account group, but advertising 0x800e requires a test-policy override, so production builds cannot yet create or join a device group.

Other MDK proposals remain open. One would stop treating a [NIP-67](/en/topics/nip-67/) [finish as proof of complete coverage](https://github.com/marmot-protocol/mdk/pull/2674), because the unscheduled sweep offers no completeness guarantee. Others would add [checkpoint replay](https://github.com/marmot-protocol/mdk/pull/2671), [automatic rejoin](https://github.com/marmot-protocol/mdk/pull/2661) and [0x800d activation in existing groups](https://github.com/marmot-protocol/mdk/pull/2668). Three earlier native API proposals are still open in a fresh status check. [Historical attachment recovery](https://github.com/marmot-protocol/mdk/pull/2614) would inspect source slots and check authenticated digest and expiry before writing verified bytes to a private leased file, keeping the timeline network-free; a delivered copy is a snapshot that cannot be revoked. [Filter-wide chat selection handles](https://github.com/marmot-protocol/mdk/pull/2592) would cover every chat matching a filter beyond the loaded page while excluding later arrivals, and [founding-admin selection for wn-agent group creation](https://github.com/marmot-protocol/mdk/pull/2587) would pick invited founding admins and reject non-members before upload.

The app now recognizes the user's own messages by sender ID, not nickname ([sender-identity fix](https://github.com/permissionlesstech/bitchat/pull/1793)). Private groups pin their creator, and the mesh peer ID stays out of geohash DMs. The performance figures are the project's own and unreproduced by us.

An open pull request, unmerged at our source cutoff, would keep geographic chat connected through relay outages by routing over the five nearest relays plus five shared backups, capped at ten connections per route ([#1822](https://github.com/permissionlesstech/bitchat/pull/1822)). Messages would queue before the relay directory loads, and subscriptions and pending writes would migrate without an identity change. Validation is the author's own, and the Android companion change is a separate pull request.

Another open pull request, also unmerged, would add [live video over the iOS and macOS Bluetooth mesh](https://github.com/permissionlesstech/bitchat/pull/1827) using a custom `LIVE_VIDEO_V1` format, not a Nostr transport. Public frames would be signed and freshness-checked. DM frames would travel inside Noise encryption; recordings would be sent as messages. The author reports that an Android-to-iPhone stream was received. Sending from an iPhone, iOS-to-iOS pairs and DM live video are untested.

### ngit

[ngit](https://github.com/DanConwayDev/ngit-cli), the command-line tool for Git collaboration over Nostr, released [v3.0.4](https://github.com/DanConwayDev/ngit-cli/releases/tag/v3.0.4). ### Hasheus

The file verification tool formerly called verify is now [Hasheus](https://github.com/tinfoilhash/hasheus) and released [2.0.0](https://github.com/tinfoilhash/hasheus/releases/tag/v2.0.0). It checks files against hashes published on Nostr, now taking descriptions and URLs from trusted verifiers and hashing large files in chunks. The verified banner appears only on the exact published file. It also handles malformed profiles, deduplicates verifiers and errors on a missing relay. A matching checksum confirms the file, not the publisher's claims about it.

### Alby JS SDK

[Alby's JavaScript SDK](https://github.com/getAlby/js-sdk) released [9.0.0](https://github.com/getAlby/js-sdk/releases/tag/v9.0.0). NWC clients now give each published request a fixed 5-second wait for the relay's OK and fail with Nip47PublishTimeoutError when it does not arrive, while per-method reply timeouts are unchanged. A relay OK means the relay accepted the request, not that a payment succeeded.

### nostr-vpn

[nostr-vpn](https://github.com/mmalmi/nostr-vpn), a VPN that uses Nostr keys for peer discovery, merged [a mobile reconnection fix](https://github.com/mmalmi/nostr-vpn/pull/77). When a discovery probe is already due, the client now re-arms exhausted paths to known peers. It does so only when nothing has been received recently and no connected or pending path exists, and at most once every 300 seconds. Healthy and pending paths are left alone, and the wire format is unchanged. The author tested the fix against an isolated native fixture, not on cellular networks. A second merged change [removes network join secrets from doctor bundles](https://github.com/mmalmi/nostr-vpn/pull/97) by leaving the enrollment join secret and raw daemon state out of diagnostic output. The Nostr private key was already redacted there. Bundles shared before this change stay exposed, so anyone who shared one should rotate the affected join secrets.

Several related changes are still open proposals and have not been merged or released. For stored secrets, one would [keep network join secrets in platform secret storage](https://github.com/mmalmi/nostr-vpn/pull/120) through the existing migration path. Another would [limit Windows machine sidecar secrets to SYSTEM and Administrators](https://github.com/mmalmi/nostr-vpn/pull/101), covering the DPAPI files that hold Nostr node keys. That restriction applies only the next time a file is written, and there is a brief gap between file creation and the ACL. Custom config paths are not covered, and the author did not test on a multi-user Windows machine. For signed membership, one proposal would [reject join approvals whose roster snapshot no longer matches disk](https://github.com/mmalmi/nostr-vpn/pull/117), so the admin reloads and retries while preserving concurrently approved devices. ### nostr-pubsub

[nostr-pubsub TS 0.5.20](https://github.com/mmalmi/nostr-pubsub/releases/tag/nostr-pubsub-ts-v0.5.20) keeps a bounded store of signed events and adds IndexedDB persistence, atomic cross-tab transactions, expiry and local replay for ordinary Nostr REQs. The same source separately describes an optional native Rust file store API with atomic snapshots and an exclusive writer lease, which is distinct from the TypeScript package. In the [durable event-store implementation](https://github.com/mmalmi/nostr-pubsub/commit/0ee66735e248d9b635caa3f44bdf8b23daf59b0d), reloads re-check signatures and NIP-01 replaceable-event winners and reject ephemeral events and timestamps more than five minutes ahead of the current time. Anonymous or private discovery caches have to stay separate from public replay, and a network-fetching router should not be used as a replay source. ### FIPS-TS

[FIPS-TS runtime 0.0.57](https://github.com/mmalmi/fips-ts/releases/tag/runtime-v0.0.57) accepts a durable discovery provider owned by the application, which publishes and subscribes to signed kind 37195 announcements through the existing interface. ## Protocol and Spec Work

### NIP-CD defines commands invoked as plain text

The [NIP-CD specification](/en/topics/nip-cd/), first titled Commands and now titled Slash Commands, was [merged into the NIPs repository on 21 October](https://github.com/nostr-protocol/nips/commit/7b5ea85479c0b4efce3c246abefa1dae8f8f91e4) ([proposal review][commands-review]). An executor advertises a command in a kind 31992 event listing its trigger, title, description, typed positional arguments and scopes. Users invoke it as plain text at the start of event content, optionally qualified by the executor's npub, so no command-specific tags or client support are required. A bare trigger can match several executors. Clients may offer autocomplete but cannot require it.

### Marmot adopts multiple devices per account

[Marmot](/en/topics/marmot/), an MLS-based encrypted group messaging protocol for Nostr, [merged its multi-device account rules](https://github.com/marmot-protocol/marmot/commit/be923c9cad997176cc155d5d851d40d28e19cc6b) ([proposal review][marmot-devices-review]) on 26 October in a form revised from the earlier draft. An inviter may add at most 20 KeyPackages for one account in a Commit. Each device holds exactly one lifelong random publication slot and never copies MLS state or private KeyPackages. Packages should last 30 days with a 7-day refresh. Inviters send each eligible device its own Welcome, and removing an account removes all of its leaves.

### Marmot lets members manage their own account's leaves

Marmot [adopted a same-account membership component](https://github.com/marmot-protocol/marmot/pull/443), `marmot.group.account-devices.v1` (ID 0x800d), which carries no data. When group negotiation requires the component, a member can commit Adds and Removes for their own account without admin authority. Under this component the member cannot remove the committer's own leaf or remove other accounts, and the account's admin standing does not change. Existing groups must activate the component and meet its support invariants.

### Marmot push triggers gain fresh padding

Marmot [now requires fresh padding in every push trigger](https://github.com/marmot-protocol/marmot/pull/445), merged 26 October. Each kind 446 trigger carries at least one fresh 1,084-byte CSPRNG padding chunk, which leaves at most 31 real encrypted tokens within the 32-chunk budget. Without fresh padding, identical token bytes would let content-hash deduplication suppress legitimate later notifications. Servers hash all chunks and must not reject a structurally valid trigger because they cannot detect the padding. Padding hides the token count from relays and observers, but the decrypting notification server can still see it.

### Marmot adds push-token repair for new members

Marmot [merged push-token repair for new members](https://github.com/marmot-protocol/marmot/pull/447) on 26 October, and a [follow-up clarified its final wording](https://github.com/marmot-protocol/marmot/blob/e8e09c822ca1a3874d2bd01c1f332d91e70bc97c/features/push-notifications.md). The owner of the Commit that adds a joiner should send active kind 448 token snapshots and kind 449 removal tombstones. An optional fingerprint set in a kind 447 announce lets peers send only the missing records. The top three ranked leaves respond on staggered timers under a 24-hour rate guard per announcing leaf. Relayed signed records and retained removal tombstones repair missing token state even while the owners are offline.

### Proposal for passkey-held Nostr keys

A [proposal for passkey-held Nostr keys](https://github.com/nostr-protocol/nips/pull/2519) builds on Nosskey, an existing scheme for using passkeys with Nostr keys. Tagged handles separate a PRF/HKDF-derived identity from a stored key, and encrypted kind 31778 relay records bind the relying party, author and credential. Missing or unknown metadata must not silently create a new identity. Relying-party origin authorization still applies, and legacy Nosskey data needs an explicit migration reader. A derived identity is lost with its passkey unless it is backed up separately.

### Proposal for DNS delegation of NIP-05 identifiers

An unmerged [DNS delegation proposal](https://github.com/nostr-protocol/nips/pull/2527) for [NIP-05 DNS-based identifiers](/en/topics/nip-05/) adds a fallback that applies only when the original HTTPS lookup returns 404 or 410. Clients then read a `_nip05` TXT record that points to an HTTPS provider. Timeouts, TLS or CORS failures, redirects and key mismatches never trigger the fallback, and DNS stores no keys. DNSSEC is recommended but optional, so with unsigned DNS the provider's TLS cannot independently authenticate the original domain's authorization. Older clients cannot resolve delegation-only identifiers.

### Software application catalog proposed as NIP-82

A [software application catalog proposal](https://github.com/nostr-protocol/nips/pull/2526) uses NIP-82 as a proposed number in that open, unmerged pull request; the number has not been assigned or adopted. It brings together kinds for apps (32267), releases (30063), assets (3063), curation (30267), certificate ownership proofs (30509) and a catalog relay list (10067). Assets identify their platform and runtime along with a file hash. Android assets add a signing-certificate hash. A proof signature shows that the publisher controls the certificate, and readers must still check its expiry and revocation.

### BIP 321 URIs proposed as NIP-A3 payment targets

An unmerged [proposal adding a bip321 payment type](https://github.com/nostr-protocol/nips/pull/2522) to [NIP-A3 payment targets](/en/topics/nip-a3/) lets a kind 10133 event carry a complete `bitcoin:` URI as static, reusable payment instructions. Because the target is reused, the proposal disallows an amount and a one-shot BOLT11 `lightning` invoice parameter. The payer chooses the amount and the wallet picks a payment method it supports, with Lightning-address fallback retained.

### Proposal for zaps paid through BIP 321 targets

A [proposal for zaps paid through BIP 321 targets](https://github.com/nostr-protocol/nips/pull/2521) has the sender pay a recipient's reusable NIP-A3 bip321 target over Ark (an offchain Bitcoin protocol), Lightning or onchain, then publish a kind 9740 zap. The receipt-key holder confirms settlement with kind 9741. Both kind numbers remain placeholders. The payment reference is encrypted with [NIP-44 versioned encryption](/en/topics/nip-44/) to a receipt key the recipient opts into, and only that key can confirm the payment. Third parties cannot verify payment details, so confirmation depends on trusting the recipient's signature. The proposal does not replace [NIP-57 Lightning zaps](/en/topics/nip-57/).

### Ark payments proposed for Nostr Wallet Connect

An unmerged [Ark extension proposal](https://github.com/nostr-wallet-connect/nwc/pull/11) for [Nostr Wallet Connect](/en/topics/nip-47/), the NIP-47 protocol that lets apps control a remote wallet, adds an Ark instruction to existing BIP 321 pay and receive support and an Ark payment record for `lookup_payment`, with no new methods. A wallet uses the instruction only when it supports the address version and network and shares the same Ark server. Otherwise it tries another URI instruction. Amounts must be whole satoshis with no millisatoshi rounding, and records separate a server-cosigned payment from funds the recipient has collected and can spend.

### Ark payment header proposed for Blossom servers

A [proposal for an Ark payment header](https://github.com/hzrd149/blossom/pull/116) in [Blossom](/en/topics/blossom/), the protocol for storing media blobs on HTTP servers, adds `X-Ark` to BUD-07 HTTP 402 payment-required responses. The header carries a BIP 321 URI holding a fresh per-request Ark address and the amount. Optionally, the URI also carries the same payment as a Lightning invoice. As proof, clients retry with the paid Ark address after settlement. Clients that used the fallback retry with the Lightning preimage. A HEAD request is not retried with proof, and clients proceed to the GET or PUT.

### Cashtag proposal for asset mentions in notes

A [cashtag proposal](https://github.com/nostr-protocol/nips/pull/2528) defines optional tokenization of `$` followed by two to six ASCII letters, excluding code, URLs and Nostr references. A single cashtag tag sets the display mode and can attach an asset ID chosen by the author, since a ticker alone cannot uniquely identify an asset. Readers check that the symbol matches the chain and address and flag mismatches without relabeling them. Optional `t` tags in the form `$ticker` allow standard relay search.

### Napplet gamepad specification withdrawn

The NAPs repository, where Napplet specifications are published, [merged a removal of the gamepad specification](https://github.com/napplet/naps/pull/129) on 27 October. The change deletes NAP-GAMEPAD.md and undoes the earlier adoption. No gamepad NAP is currently adopted.

### Cyberspace height tags avoid group-tag collisions

Cyberspace, a spatial protocol built on Nostr, merged several of its own specifications, called DECKs. These are project specs, not official NIPs. The spec now [renames the height tag on bags and chat from `h` to `H`](https://github.com/arkin0x/cyberspace/pull/73). The lowercase tag clashed with NIP-29 group tags and caused events to be rejected or misfiled. Readers fall back to a legacy `h` only when `H` is missing. This changes only the project spec. It does not amend NIP-29 or prove that deployed clients interoperate.

### Cyberspace hidden audio

[DECK-0007 defines hidden audio](https://github.com/arkin0x/cyberspace/pull/79) as an encrypted Blossom file, referenced by an unsigned rumor inside a signed bag or chest. This means the person who hid it is not attributed through a separately signed public post that can be played. Each placement uses a fresh key and ciphertext, but anyone can still share the key. The spec does not claim that encryption guarantees the finder's privacy or that its URL rules block all SSRF, and reader support is still in progress.

### Cyberspace public models and animation

[Items can now reference public SNO models with bob and spin animations](https://github.com/arkin0x/cyberspace/pull/74), and fall back to the old rendering when a model is invalid or unavailable. Live models can change or disappear, and wide adoption is not claimed.

### Cyberspace item, chat and comment specifications

[Optional DECKs 0004 through 0006](https://github.com/arkin0x/cyberspace/pull/67) document existing code for items, chests, listings, encrypted local chat and sealed comments, with synthetic test vectors. Several issues are still open. Bag and chest signatures differ, and sealed comments expose the parent ID and kind through public tags. Holders can override listings. Chat has replay and context-binding gaps, and chest references are not implemented. The documentation fixes no security issue and is not a deployment.

### Multi-author events proposal

A signed long-form article, [Multi-Author Nostr Events as a Soft Fork](https://njump.me/nevent1qqszlhx6hpwf0th2mk760n7cxqdknglwshgprpupsk4tj0nkr2n66wgzypzcxhpk7swe0x7gz2vrpuh4myjk9af584h7mht0xz48jjq8xrexuxjg87j), proposes events whose ID hash covers several author pubkeys, with each author signing the same ID. Older clients would see a secp256k1-compatible wrapper carrying the new-form data and Q tags as lookup hints. Peers would negotiate the new form per connection. The article generalizes the author's earlier post-quantum proposal, which would add a future key as one more co-author. This is an unnumbered proposal, not an accepted NIP. Coauthored naddr replacement and binary transport remain open questions.

### Buzz NIP-AR sync subscriptions send a complete snapshot before live heads

An open Buzz pull request proposes [NIP-AR](/en/topics/nip-ar/) WebSocket sync subscriptions ([#8522](https://github.com/block/buzz/pull/8522)). The relay would send a consistent artifact set read under REPEATABLE READ and emit EOSE only once that set is complete, then stream live current heads; live Redis registration happens before the initial read. Redis disconnect or lag ends the subscription with CLOSED and requires a resync, and so do access changes, redactions or a full queue. Subscriptions cap at 4,096 artifacts, and the change was unmerged at our source cutoff with no production availability.

### Buzz NIP-AR incremental artifact reads over HTTP

A separate open Buzz pull request adds incremental HTTP reads for NIP-AR artifacts ([#8523](https://github.com/block/buzz/pull/8523)). Clients page by database modified timestamps and stable IDs with a 120-second overlap, and receive either the current revision or a removal. They can recover known IDs. Results use an eventual-consistency model. The proposal does not promise a complete snapshot, and an artifact's absence does not mean deletion or lost access. Its latest revision requires membership or an explicit #h scope for unlisted open channels, and a listing change resets incremental progress. The feature gate, BUZZ_ARTIFACT_INCREMENTAL_ENABLED, is off and requires every writer and migration (now 0074 through 0076) in place. This 120-second delay is an operating assumption. At our source cutoff the change remained open.

### Draft NIP-AM text for delegated metric readers

A draft Buzz documentation pull request specifies delegated readers for [NIP-AM](/en/topics/nip-am/) metrics without changing runtime authorization ([#8582](https://github.com/block/buzz/pull/8582)). The owner-encrypted kind 44200 event stays unchanged, and the agent emits a separate NIP-44 copy for each active grant, bound to the exact owner-authored grant event ID. The proposed grant kind 30180 and reader caps remain open questions, as do history, revocation and public linkage. A signed revocation cannot erase copies a recipient already holds, and the draft was unmerged at our source cutoff.

### DECK-0003 lets a parent carry the objects it places

An open Cyberspace pull request proposes DECK-0003 §1.10, a root table of inline SNO object payloads ([#81](https://github.com/arkin0x/cyberspace/pull/81)). A present entry in the parent's copy wins without a network fetch, even when invalid. Each entry is scoped to the author pubkey with bounded size and depth plus cycle limits. Older readers fetch missing objects and show a placeholder. The proposal describes implementations held pending this change, which was unmerged at our source cutoff.

### DECK-0004 defines height-bound doors with derived room keys

An open Cyberspace pull request adds DECK-0004 §3.6 and §3.7 on looks and doors ([#82](https://github.com/arkin0x/cyberspace/pull/82)). Doors are height-bound, and the room key is SHA-256(domain separator ‖ location key ‖ door secret), with the room's bag encrypted under it. Rooms can have multiple or nested doors, and setting a new lock rotates the key. The text has no test vectors until a first implementation exists, and it was unmerged at our source cutoff.

### nostream NIP-11 peering advertisement extension

An open nostream pull request would extend the relay's NIP-11 document with a peering section ([#999](https://github.com/cameri/nostream/pull/999)). It advertises feed kinds with time bounds and settlement terms, along with a contact endpoint and peering proof-of-work. Only `enabled: false` disables the section, and empty terms mean settlement-free peering. An advertised offer is not an accepted peer. The change implements no peer agreement or paid federation. It was unmerged at our source cutoff.

### NIP-CD adds optional installed command lists

A follow-up to NIP-CD was [merged into the NIPs default branch on 27 October](https://github.com/nostr-protocol/nips/pull/2525) ([merge][cd-installed-merge]), and the specification is now titled Slash Commands. It defines an optional kind 10992 list, following [NIP-51](/en/topics/nip-51/), in which a user keeps address tags pointing to kind 31992 command definitions, each identified by executor pubkey and d value with an optional relay hint. Users may maintain the list, and clients should use it for autocomplete and rendered chips. The list is a display and discovery preference. It does not authorize executors, and plain-text invocation still works without it, with no command-specific tags and no required client support. NIP-CD remains an optional draft, and the merge does not show which clients have adopted the list.

### Marmot narrows its fair preparation rule for account devices

Marmot [merged a correction on 28 October](https://github.com/marmot-protocol/marmot/pull/450) to its scheduling rule for groups that require account devices. After a bounded convergence pass reaches Stable, one queued intent authorized by an admin, or a permitted intent from the same account, gets a preparation attempt before queued inbound work alone can force another pass. SelfUpdate and Leave fall outside this extra fairness guarantee, although any member may still commit them. The change corrects earlier wording that covered every authorized intent, and groups that do not require account devices keep their previous scheduling. There is no wire change, and a preparation attempt does not guarantee a valid, accepted or canonical Commit.

### Marmot proposes a hidden device roster for account groups

An open Marmot proposal, not merged, [would add a device-roster-v1 component](https://github.com/marmot-protocol/marmot/pull/452) with ID 0x800e for a hidden group whose leaves all belong to one account. A group carries the roster from creation or never does. The roster records devices, rejected slots, rejected KeyPackages and leaf maps, and it is the first component to use explicit, order-independent diff updates applied to the candidate parent. Removed slots can keep leaf maps for groups their siblings cannot remove them from. A device trusts a device group only if it created that group or joined through a Welcome authenticated by a confirmed link, so the 0x800e marker alone grants no trust. The founding Add names the exact KeyPackage from the confirmed link. A stolen linked device can edit the roster until it is removed. The device cap applies to devices. Leaf-map and rejected records have per-entry size limits but no record-count cap. Roster data is never copied to other accounts, and the group stays hidden from chats, counts, notifications and destinations. The body says MDK keeps roster bytes behind a test switch with no new ordinary UI.

### Marmot proposes clearer feedback when account-device activation fails

Another open Marmot proposal, not merged, [would let clients explain activation failures](https://github.com/marmot-protocol/marmot/pull/453) for account devices. A client may report that a group cannot activate account devices. That group-level feedback cannot name the members or devices that block it. A member who is not an active admin learns only that it lacks admin status. If a branch selection is lost or a regenerated activation check fails, the user must make a fresh request. The client never retries activation automatically. The existing rule that activation requires a fresh user request from an authorized client is unchanged. This is draft normative text and does not show implemented or deployed behavior.

### Marmot proposes emoji verification for pairing new devices

An open Marmot proposal, not merged, [describes pairing a new device](https://github.com/marmot-protocol/marmot/pull/454) through an exchange modeled on Matrix m.sas.v1, using X25519, HKDF and HMAC. The user compares seven labelled emoji on both screens and does not read or type a code. Possessing the account key never authenticates a device. Five unsigned rumors (Request, Answer, Reveal, Confirm and Cancel) are wrapped to the account pubkey and bind the account, session, new KeyPackageRef, existing device slot and fresh keys. The existing device confirms first and adds exactly the confirmed KeyPackageRef. The new device confirms only after verifying, and it accepts a Welcome only for the group ID authenticated by the confirmed exchange. Kinds 452 to 456 are proposed, with 457 to 489 reserved. An account keyholder can still forge Cancel to deny service, even after confirmation. The hourly Answer limit does not persist across restarts. Relays can see the wrap burst and account address; some merge and Welcome cases remain deferred. Implementations keep these formats off by default, and two author-supplied known-answer vectors are not an independent security or interoperability audit.

### NIP-5D napplet proposal tightens media and source fields

The [open NIP-5D napplet proposal](https://github.com/nostr-protocol/nips/pull/2303) was described previously. Its 28 October changes have now merged into the proposal branch, not into the NIPs default branch, revising optional media and source fields introduced on 17 October. Screenshot and preview tags now reuse [NIP-92](/en/topics/nip-92/) key-value fields, with one required lowercase SHA-256 x value and optional m, dim, size, alt and duration. Readers must verify the hash and decode the actual format before rendering. If a valid m field is present, the decoded format must also agree with that MIME type. Entries with a missing, repeated or bad x are ignored, bad optional fields are dropped without discarding other usable media, and multiple previews are ignored. A source-commit must resolve to an exact full Git ID, and HTTPS source archives need an exact byte-level SHA-256 match. Duplicate or malformed source fields are ignored, and unusable source data must not block HTML playback. A matching commit or archive does not prove a reproducible build, and no client conformance is claimed.

## Six Years of Nostr Octobers

Across six Octobers, Nostr's dated changes moved outward from message framing to the applications built on it. In 2021 the basic specification [settled that client messages are framed as top-level JSON arrays](https://github.com/nostr-protocol/nostr/commit/69509f40cd6a4d5c14a7c402b04495a1de5ab2c2). The following Octobers brought client search and Lightning invoices, timestamp evidence and job requests, media variants and ecash wallets, then code collaboration and private-message metadata. Other changes in the same months made identities and connections easier to carry between programs, from visible relay status to separate signer keys and wallet pairing. This October the same document [defined what an empty filter list matches](https://github.com/nostr-protocol/nips/commit/37db639582d857e12468dcccd99b2c7f1d657da9), so relays that read identical JSON now have a shared rule for which events it selects.

### October 2021: Making the Transport Unambiguous

On October 4, [NIP-01](/en/topics/nip-01/), the basic protocol specification, was [revised so client messages are top-level JSON arrays](https://github.com/nostr-protocol/nostr/commit/69509f40cd6a4d5c14a7c402b04495a1de5ab2c2). The informal EVENT, REQ and CLOSE prefixes became the first element of each array, and the fixed `/ws` path requirement was dropped, so any WebSocket endpoint would do. This clarified a specification that already had code behind it. Independently written clients need exact framing before anything more sophisticated can interoperate.

On October 23, the [relay-to-client direction gained explicit EVENT and NOTICE messages](https://github.com/nostr-protocol/nostr/commit/97786e31423b45239306323a9a297188d20dbf21). A relay EVENT carries the identifier of an existing REQ subscription, so a client running several subscriptions over one connection can match results to requests, and NOTICE carries human-readable text. A vocabulary this small is practical to implement more than once, which suits separately operated relays.

The [October 23 text of NIP-01](https://github.com/nostr-protocol/nostr/blob/97786e31423b45239306323a9a297188d20dbf21/nips/01.md) also shows what a signature covers. An event's ID is a digest of a compact UTF-8 JSON array holding a leading zero, the author's public key, the timestamp, the kind, the tags and the content, and the author signs that digest with a Schnorr signature on the secp256k1 curve. The WebSocket envelope and the subscription identifier sit outside that signed data. It follows from that text that the same signed event can arrive on different subscriptions, or over different connections, without being signed again. A REQ first returns matching stored events and then stays live until the client sends CLOSE, closes the socket or reuses the subscription ID for a new REQ. Every condition within one filter must hold, while several filters in one REQ match events that satisfy any of them. Filter names in that version differ from today's. NOTICE behavior was left unspecified, and nothing promised how long relays keep events or that a query returns all of them. Five years later, the same specification would return to what filters inside REQ mean.

### October 2022: A Feed Becomes Usable on a Phone

On October 8, Damus, an iOS Nostr client, [added search for hashtags, profiles and events](https://github.com/damus-io/damus/commit/2c4c392b76d9ad92b28e71d6d578bdb42c2ac3de). The change touched its search results view and thread model, letting a reader jump to a signed identity or a specific event in addition to scrolling incoming text. This search worked inside the client's own navigation and was not relay-side full-text search.

Eight days later, Damus [replaced the plain rows in its relay configuration with a view showing each connection's state](https://github.com/damus-io/damus/commit/e5e0fb2db279a5a2763d39b15d5fff20bec26fdd). A colored dot reads the client's relay pool. Green means connected and yellow means connecting or reconnecting, with red for anything else and gray before the first reading. The view refreshes when it appears and every two seconds after that. Swipe-to-delete, which already existed, moved into the new view. With the dots visible, a stalled feed no longer had to be read as an author's silence, because a reader could see which of several independent connections was up and which was retrying. A green dot shows an open socket. It does not show that a relay accepted or kept an event. It also does not show that a query returned everything the relay holds. The commit records the implementation in merged source. This source change establishes no App Store release date.

On October 19, Damus [added a parser for BOLT11 Lightning invoices and invoice widgets](https://github.com/damus-io/damus/commit/c6ab1de63926ff7f6e29a260e3e7f2473855c9c7) in posts, chats and direct messages. The widget shows the invoice description and amount in satoshis, and its Pay button passes the `lightning:` URI through iOS to an installed handler. The social client presents the signed post, and a separate wallet pays. These widgets predate the later zap receipt convention, so they are invoice displays, not standardized zaps.

### October 2023: Events Carry Evidence and Requests for Work

On October 11, [NIP-03](/en/topics/nip-03/) OpenTimestamps attestations, which anchor evidence about events in Bitcoin, [moved from an `ots` field on the event to a separate kind 1040 event](https://github.com/nostr-protocol/nips/commit/09ffb951c69343312486aaff2726dca04bc42f6e). That event names the original with an `e` tag and carries the full base64 OpenTimestamps file, with at least one Bitcoin attestation, in its content. The referenced event id is itself the digest the proof attests, so a verifier learns that the event existed by the attested time. That time comes from Bitcoin, not from the author's `created_at`. The proof dates the event and makes no claim about its content.

On October 12, independent of the timestamp change, [NIP-06](/en/topics/nip-06/) key derivation [gained two test vectors](https://github.com/nostr-protocol/nips/commit/202e18f2b256646148805880ed58731c1c8b2b9b). A mnemonic is a sequence of words that encodes a recovery seed, and the vectors cover one 12-word and one 24-word mnemonic, each with its expected private and public keys in hexadecimal and in nsec and npub encodings. NIP-06 already used BIP-39 to turn the mnemonic into a binary seed and the BIP-32 path `m/44'/1237'/<account>'/0/0` to derive a key, with account zero as the basic single-key choice. The October addition supplied known answers, not mnemonic recovery or a new derivation algorithm. A client can now check that its derivation and encodings reproduce the documented identity. Matching the vectors makes implementations comparable. It does not certify any particular implementation or prove that every wallet and client import agrees. Protecting a seed from theft is a separate matter that the vectors do not address.

On October 29, [NIP-90](/en/topics/nip-90/), the data vending machine standard, was [merged into the NIPs repository with fixed job kinds](https://github.com/nostr-protocol/nips/commit/7a2de8ab25ceaa35376e6b7457f08b5bffde70b3). It reserved kinds 5000 to 5999 for job requests and set each result kind at the request kind plus 1000. Feedback used kind 7000. A request can point to text, URLs or earlier jobs. It can also name the expected output and offer an optional bid. The task therefore lives in signed events that any provider can answer, outside any single vendor's API. An earlier draft had used kinds 68001 and 68002.

### October 2024: Media Alternatives and Portable Ecash

On October 15, [NIP-71](/en/topics/nip-71/) video events [adopted `imeta` tags for video variants](https://github.com/nostr-protocol/nips/commit/1cda2dcc594538ea14b88aec7f1f784e06a31bbf). In the then-current addressable kinds 34235 and 34236, each variant's URL, dimensions, MIME type, preview image and fallbacks sat together in one tag. A client picking a resolution needs to know which thumbnail and fallback belong to it, and flattened metadata could not say. Those kind numbers are historical: current NIP-71 uses kinds 21 and 22.

Ten days later, [NIP-60](/en/topics/nip-60/) Cashu wallets and [NIP-61](/en/topics/nip-61/) nutzaps, both introduced in earlier drafts, were [merged together as specifications](https://github.com/nostr-protocol/nips/commit/ba46b23d95b186c9a8fedabf8324af2ae40e8ce4). They build on Cashu, an ecash protocol whose tokens are issued by mints. NIP-60 keeps encrypted wallet proofs on relays, so compatible applications can reach the same wallet state. Under NIP-61, a recipient's kind 10019 event lists trusted mints, relays and a locking key, and a sender's kind 9321 event carries proofs locked to that key for the recipient to redeem. Users still depend on the mints that issue the tokens, and applications must guard against the same proofs being redeemed twice.

On October 29, [NIP-46](/en/topics/nip-46/) remote signing, in which a separate service holds the key that signs on a user's behalf, was [revised so a `bunker://` connection string carries the remote signer's public key](https://github.com/nostr-protocol/nips/commit/f1e8d2c4f764d66996c0c1fb2eeabfbc0c7b2528). The user's identity is obtained separately: the [revised text](https://github.com/nostr-protocol/nips/blob/f1e8d2c4f764d66996c0c1fb2eeabfbc0c7b2528/46.md) requires clients to tell the two keys apart and to call `get_public_key` after connecting. The client generates its own keypair for the conversation and addresses its encrypted requests to the signer's key, while `sign_event` returns an event signed with the user's key. Those two keys may coincide, but they need not. The key in the connection string identifies only the signer service. The user's account is the public key that `get_public_key` returns. NIP-60 had addressed shared wallet state four days earlier; this revision addresses a separate concern, signer identity. The examples at that commit still use the encrypted transport NIP-46 specified at the time, and the change neither makes a remote signer trustless nor proves who holds the user's key.

### October 2025: Collaboration Updates and Private-Message Metadata

On October 8, [NIP-47](/en/topics/nip-47/) Nostr Wallet Connect [gained deep links for pairing an app with a wallet](https://github.com/nostr-protocol/nips/commit/2ace01cf1ad0a68dae6217111c9286e3de759923). A wallet can register `nostrnwc://connect` or an app-specific `nostrnwc+{app_name}://connect`, and a requesting app opens that link with its URI-encoded icon, its name and a callback scheme. Once the wallet has created the connection, it opens the callback with a `value` parameter holding the pairing code, a `nostr+walletconnect://` URI. Three years after Damus handed invoices to a wallet through iOS, pairing on one phone no longer had to mean scanning a QR code shown on the same screen or copying a long string between apps. The addition covers only this handoff. It changes no payment methods and pays nothing by itself. Both apps must implement the handlers, and the specification text is no evidence that every wallet does. Nor does it settle spending budgets, consent screens or which app may safely own a callback scheme.

On October 16, [NIP-34](/en/topics/nip-34/) git collaboration [gained kind 1618 pull request and kind 1619 update events](https://github.com/nostr-protocol/nips/commit/6e6b9877b32b44e84c0f3c3d412d688cf86761b0) beside its existing patch events. A pull request names a commit tip and clone locations, and an update moves that tip. Patches are recommended below 60 kB, with pull requests for larger submissions. This shifted the recommended route for larger submissions from patch bodies carried inside events to signed references to commits, while smaller changes can still travel as patches. Nostr carries the coordination and signed references, and Git servers still supply the commit objects those references point to.

On October 27, [NIP-59](/en/topics/nip-59/) gift wrap [gained guidance to randomize seal and gift-wrap timestamps independently](https://github.com/nostr-protocol/nips/commit/bcaad2957d0e9cec20e4265298d2788be87d3190) when expiration tags are added. Gift wrap encloses a message in those two layers, and giving each layer its own random timestamp reduces how closely the layers' timing can be correlated. Here the attention turned from encrypting content to limiting what metadata correlation can reveal. Encryption hides the message itself, but timing and other metadata around the envelope remain observable, and implementation choices decide how easily they can be linked. The guidance adds no new encryption and does not make participants anonymous.

### October 2026: Shared Query Meanings and Text-Triggered Services

On October 5, [NIP-92](/en/topics/nip-92/) media attachments [extended `imeta` tags to kind 0 profiles](https://github.com/nostr-protocol/nips/commit/a79e21d90fce5465b50ef385dd368bba99ec4a0b), letting a profile describe its `picture` and `banner` with fallback URLs, a blurhash (a compact encoding of a blurred preview), dimensions, alt text and other attachment metadata. NIP-92 existed before this change; what is new is that the grouped metadata NIP-71 applied to video variants in 2024 now reaches profile images. Association is exact. A tag applies only when its URL equals the picture or banner URL, clients SHOULD ignore tags that match neither, and they SHOULD try fallbacks when the primary URL fails. Because a new kind 0 event replaces the earlier profile, a publisher SHOULD carry over metadata for an unchanged image and drop tags for images no longer used, so stale alt text or dimensions do not quietly describe a different picture. That update rule matters as much as the new fields. An `imeta` tag does not guarantee that an image stays available or loads faster. It also provides no privacy protection, and clients need not render every field.

On October 17, [NIP-01 was clarified so an empty list in a filter matches no events](https://github.com/nostr-protocol/nips/commit/37db639582d857e12468dcccd99b2c7f1d657da9), which differs from leaving the attribute out. A [follow-up removed inconsistent "one or more" wording and recommended that clients avoid sending lists that cannot match](https://github.com/nostr-protocol/nips/commit/0b5532c0355ab27f447e071a93c09cf3a2b4aad5). In October 2021 this document agreed on REQ's JSON message framing: the REQ message is an array, and each filter is a JSON object inside it. This October it settled filter semantics, fixing what an empty list inside such a filter means, since relays that parse the same frame identically could still return different results.

On October 21, [NIP-CD, then titled Commands, moved from proposal to merged draft specification](https://github.com/nostr-protocol/nips/commit/7b5ea85479c0b4efce3c246abefa1dae8f8f91e4); it describes slash commands. Kind 31992 events define commands, and an invocation is plain text starting at the first character of an event's content, so clients need no special support to send it. A [follow-up proposal](https://github.com/nostr-protocol/nips/pull/2525), with an [earlier commit](https://github.com/nostr-protocol/nips/commit/0142de0384210d69074c089448ef5bc303faef37) on a separate branch, was [merged on October 27](https://github.com/nostr-protocol/nips/commit/400d157c53264b8e58c7b3cdbd21ef546fb7a157). It retitled the specification Slash Commands and added optional kind 10992 installed-command lists that clients should use for autocomplete and rendering. The lists record a user preference and do not authorize executors or gate plain-text invocation. NIP-90 jobs use structured request and result events, while a command stays readable as ordinary text.
