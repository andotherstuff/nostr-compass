## Top Stories

### Amber shares one relay subscription across signing connections {#greenart7c3-amber}

Newer Amber signing connections could miss requests, even small pings, through a relay that had accepted them. In [issue #644 on missing bunker requests](https://github.com/greenart7c3/Amber/issues/644), pings to `relay.primal.net` returned `OK` with `true`. That meant the relay had accepted the event, but it had refused the subscription that should have delivered the event to Amber. The two Primal endpoints tested run strfry with a cap of 20 subscriptions per WebSocket, and their refusal `NOTICE` names no subscription ID, so Amber still showed the relay as connected.

Amber opened a subscription per signing connection. Its other relay subscriptions counted toward the same cap. [Merged PR #649 for shared subscriptions](https://github.com/greenart7c3/Amber/pull/649), merged November 20 for Android and desktop, uses one [NIP-46](/en/topics/nip-46/) subscription per relay. Its `REQ` filters kind 24133 by `#p` for each key that receives signing requests on that relay. The filters hold up to 100 keys each and travel in one `REQ`. Amber still routes requests by the tagged recipient key. UI reporting of refused subscriptions remains open.

The fix remained untagged on November 25. It landed after 7.0.0-pre5, the newest Android prerelease, as shown in the [prerelease-to-merge comparison](https://github.com/greenart7c3/Amber/compare/v7.0.0-pre5...c154c83f1ca11ca75382b88b6b591257fb6a4a16).

### MDK 0.19.0 counts thread replies as chat activity {#marmot-protocol-mdk}

MDK 0.19.0, released November 22, makes threaded replies count as chat activity in apps using the library. [NIP-22](/en/topics/nip-22/) kind `1111` comments filed under an earlier message as thread root or parent now update previews, ordering, unread counts, mentions and notifications. Inline quoted replies stay kind `9`. MDK 0.18.0, stable since November 20, lets a newly linked device join older chats through a sibling Welcome that keeps the original inviter, and the active approver normally adds the device to avoid competing Messaging Layer Security (MLS) group updates ([MDK 0.18.0 release notes](https://github.com/marmot-protocol/mdk/blob/v0.18.0/docs/release/0.18.0.md), [MDK 0.19.0 release notes](https://github.com/marmot-protocol/mdk/blob/v0.19.0/docs/release/0.19.0.md)).

Both releases migrate the account schema, so the previous version cannot open a migrated account and every process sharing it needs matching artifacts. Custom v2 agent integrations must call `send_final` because 0.19 retires the QUIC live text preview. Each release shipped stable MarmotKit and Marmot C builds, as in the [MarmotKit 0.19.0 release](https://github.com/marmot-protocol/mdk/releases/tag/marmotkit-v0.19.0). The aligned WN Agent tags, such as the [WN Agent 0.19.0 prerelease](https://github.com/marmot-protocol/mdk/releases/tag/wn-agent-v0.19.0), are marked as prereleases.

The November 25 [MarmotKit nightly](https://github.com/marmot-protocol/mdk/releases/tag/marmotkit-v0.20.0-nightly.20261125), [Marmot C nightly](https://github.com/marmot-protocol/mdk/releases/tag/marmotc-v0.20.0-nightly.20261125) and WN Agent nightly are testing builds from one commit and sit outside stable 0.19.0. This nightly cohort limits how much work a history fetch can do at once. When a relay publishes no NIP-11 document, recovery can run [bounded NIP-77 reconciliation](https://github.com/marmot-protocol/mdk/pull/3608) to identify and fetch missing events before it moves past the gap. Large catch-up replies now go into bounded per-request queues outside nostr-sdk's per-connection live reader, and filter, ID and signature checks still apply. The [catch-up queue and its benchmark](https://github.com/marmot-protocol/mdk/pull/3641) cut live-delivery p95 from 129–207 ms to 0.14–0.21 ms in a controlled local workload, with no mobile or production measurements behind the figure.

The same nightly carries an [explicit refusal fallback](https://github.com/marmot-protocol/mdk/pull/3644) that lets newer live messages through when a relay without NIP-11 explicitly reports that it won't support NIP-77. Older history stays outstanding. Authentication challenges and errors during synchronization leave the result unresolved. A relay that silently ignores NIP-77 can still hold live messages for about 15 minutes, as tracked in the [silent relay limit issue](https://github.com/marmot-protocol/mdk/issues/3643).

Chats also start loading sooner after a device links. [Post-link scheduling](https://github.com/marmot-protocol/mdk/pull/3635) starts chat work once pairing is recorded, which ends an empty chat list that could last until an unrelated wake. [Invitation-first ordering](https://github.com/marmot-protocol/mdk/pull/3650) sends shared invitation decisions as soon as a new roster member appears. Chats the account already accepted then normally stop reappearing as invitations, where declining one could have made the whole account leave. An update that gets no relay acknowledgement can still arrive after the Add and leave old chats pending ([acknowledgement window](https://github.com/marmot-protocol/mdk/issues/3648)).

After a restart, WN Agent in the [November 25 WN Agent nightly](https://github.com/marmot-protocol/mdk/releases/tag/wn-agent-v0.20.0-nightly.20261125) resumes stored inbound messages from a cursor saved per account and subscription scope ([WN Agent restart recovery](https://github.com/marmot-protocol/mdk/pull/3639)). Documented exceptions leave exactly-once delivery across crashes unguaranteed ([restart limitations](https://github.com/marmot-protocol/mdk/issues/3638)).

The nightly also changes Welcome delivery for new invites. In its first pass, the app account worker can send a Welcome to each of two to 16 distinct inbox relays independently. Slower sends continue after the first acknowledgement settles the send, and interrupted attempts retry after backoff ([Welcome fanout #3687](https://github.com/marmot-protocol/mdk/pull/3687)). Manual `redeliver_welcome` and the inline runtime keep the earlier behavior. MarmotKit and Marmot C expose durable relay delivery status with device and relay counts per invite, and a relay acknowledgement alone does not show that the recipient received the Welcome ([delivery status #3686](https://github.com/marmot-protocol/mdk/pull/3686)). MDK classifies missing routes and retries them with in-memory backoff, without actively fetching a fresh relay list ([missing routes #3701](https://github.com/marmot-protocol/mdk/pull/3701)).

Two changes merged after the November 25 nightly. One sets the Welcome retry deadline at seven days from staging or the KeyPackage expiration, whichever comes first ([Welcome expiry #3708](https://github.com/marmot-protocol/mdk/pull/3708)). The other lets apps name which accounts may receive a queued send. Just before encryption, MDK refuses the send if the group includes an account the app did not list. Additional devices of an allowed account can still receive it ([member-limited sends #3712](https://github.com/marmot-protocol/mdk/pull/3712)).

### Sidecar v1.19.0 publishes portable articles and recipes {#dmnyc-sidecar}

With Sidecar v1.19.0, published November 24, writers can publish articles and recipes as addressable kind 30023 events. The full-size composer has separate Article and Recipe tabs with a preview and review step. Recipes carry Markdown ingredients and directions, a cover image, a stable recipe identifier, a `zapcooking` `t` tag and `zapcooking-` prefixed title and category tags. Sidecar normalizes topics and categories and asks for confirmation before replacing an existing address. [Sidecar v1.19.0 release](https://github.com/dmnyc/sidecar/releases/tag/v1.19.0), [composer pull request #664](https://github.com/dmnyc/sidecar/pull/664), [tagged article and recipe encoding](https://github.com/dmnyc/sidecar/blob/v1.19.0/longform-events.js)

Replies are NIP-22 kind 1111 comments with an address reference, so they attach to the same piece in clients that support that format ([tagged reply tests](https://github.com/dmnyc/sidecar/blob/v1.19.0/test/comments-and-hashtags.test.js)). Sidecar's recipe tags match Zap Cooking's upstream design. Publishing to a hosted Zap Cooking instance and reading the recipe back remains unverified ([tagged article and recipe encoding](https://github.com/dmnyc/sidecar/blob/v1.19.0/longform-events.js)).

The release also bundles the open nspam model, which runs on the device when the optional sort by people you follow is on. The notification bell can then move likely-human replies from strangers into the main list and mark likely spam in the grouped list, while keeping every notification available. Replies that link to a website cannot be promoted, and the model leaves mostly non-Latin text unscored. [nspam model pull request #670](https://github.com/dmnyc/sidecar/pull/670), [tagged nspam model](https://github.com/dmnyc/sidecar/blob/v1.19.0/nspam.js), [tagged notification bell browser tests](https://github.com/dmnyc/sidecar/blob/v1.19.0/test/nspam-bell.browser.test.js)

Sidecar v1.18.0, published November 19, put into a release the NIP-37 relay drafts and ranked profile search that Compass #49 covered as merged code. It also adds a Saved Drafts entry point that works when no local draft exists and reads drafts written by other clients. [Sidecar v1.18.0 release](https://github.com/dmnyc/sidecar/releases/tag/v1.18.0), [v1.17.2 to v1.18.0 patch](https://github.com/dmnyc/sidecar/compare/v1.17.2...v1.18.0.patch), [Compass #49 Sidecar coverage](https://nostrcompass.org/en/newsletters/2026-11-18-newsletter/#dmnyc-sidecar)

### Marmot Agents connects local coding tools to encrypted chats {#marmot-protocol-marmot-agents}

Marmot Agents puts coding agents running on the operator's own machine into Marmot MLS chats under one shared agent identity and session model. On November 21 it exchanged prompts and replies between a real Codex harness and a chat on [MDK's test relay](https://github.com/marmot-protocol/marmot-agents/pull/49), and it later gained a [shared local socket](https://github.com/marmot-protocol/marmot-agents/pull/55) core. Codex, Pi and ACP-based tools such as OpenCode, Goose and Cursor run as drivers in the Rust core. Claude Code, Hermes and OpenClaw connect over the socket.

The [pinned project README](https://github.com/marmot-protocol/marmot-agents/blob/641d0b9f0f38c325a2c1f2bb58426bd819ae4921/README.md) gives install steps from a source checkout for Linux x86_64 and arm64 and for Apple Silicon. It assumes a harness the operator has already installed and describes the project as working toward replacing the connectors MDK still ships. On November 25 the project still had no tags or packaged releases ([releases page](https://github.com/marmot-protocol/marmot-agents/releases)).

MDK's November 25 nightly, a testing build of the library, carries agent output as kind `1201` items and human answers or controls as kind `1202`. Alerts fire only for a pending approval, a question or a failed turn ([MDK agent item kinds](https://github.com/marmot-protocol/mdk/pull/3613)).

Marmot Agents sends the full activity stream, including reasoning, tool calls, plans and native payloads, only to the owner's exact two-person chat or to groups where it has been explicitly enabled. Other group participants receive replies, approvals, questions, errors and files. The core rechecks membership on every send, so adding a third person to the owner's chat stops full activity there. Hermes tool narration is an exception and still reaches regular chats ([full-activity visibility rules](https://github.com/marmot-protocol/marmot-agents/pull/165)).

Codex subagents first posted flat in the chat where they started ([flat Codex subagents](https://github.com/marmot-protocol/marmot-agents/pull/124)). A November 24 merge puts a Codex subagent's work in its own thread when the task root is available. It falls back to the main chat if the root is unavailable or the thread is gone. A later source merge makes Stop inside a thread apply to that subagent and its descendants ([thread placement #185](https://github.com/marmot-protocol/marmot-agents/pull/185), [thread controls #195](https://github.com/marmot-protocol/marmot-agents/pull/195)).

## Protocol and Spec Work

### NIP-9a verifies webhook subscription callbacks {#nostr-protocol-nips-2194}

Under the open NIP-9a push proposal, a relay checks a webhook before it accepts a kind-30390 subscription. The webhook is the web address that receives notifications. The relay sends it a random challenge, and the callback must answer with a successful HTTP response containing that exact challenge. Optional `ignore_self` asks supporting relays to skip pushes generated over a connection authenticated as the subscriber, which can suppress the sender's own encrypted-message copy. The `relay` payload field names the event's source relay, which helps when an intermediary sends the push ([November 23 revision](https://github.com/nostr-protocol/nips/commit/8034a82bcd6ffa9cb31cbabd06ef520ed954cc16)).

### Nostracle tests the DLC oracle event proposal {#nostr-protocol-nips-2394}

Nostracle, a price oracle for Bitcoin Discreet Log Contracts, merged an implementation on November 20. It publishes commitments for future BTC/USD and BTC/EUR outcomes and later signs the results. A November 21 report found two places where the open proposal's byte format needs clarification. Nostracle's decoded payloads omit a type prefix, and its attestations include an outcome count. The proposal still uses placeholder kinds, and Nostracle uses kormir/DDK's kinds 88 and 89, which are unrelated to the accepted NIP-88 Polls. Using a test key, the reporter checked event round trips through three public relays. Wallet compatibility remains unverified ([implementation and wire-format report](https://github.com/nostr-protocol/nips/pull/2394#issuecomment-7063097193), [November 20 implementation merge](https://github.com/p2pfiat/nostracle/commit/a351f5b3501693c6e6d229536f5fa6aa732d1165)).

### QvaPay publishes the revised non-bitcoin order format {#nostr-protocol-nips-2541}

On November 20, the peer-to-peer marketplace QvaPay said its Nostr offers now follow revision `c76c5c6` of the open draft for non-bitcoin trades. It publishes paused offers as `paused`. Offers that can fill across several trades stay in progress until reserved trades finish. Trade events record executed amounts, and the offer keeps its own available range ([migration statement](https://github.com/nostr-protocol/nips/pull/2541#issuecomment-7049017614), [exact draft](https://github.com/nostr-protocol/nips/blob/c76c5c65a3e5cefdc5c257308101b37261e1bdfb/XX.md), [publishing documentation](https://www.qvapay.com/docs/p2p/nostr)).

### NIP-CA proposes short signed links and text {#nostr-protocol-nips-2553}

An open proposal filed November 20 lets a short signed Nostr identifier carry one link or a brief public message. Cairn events use draft kind 1738, with the link in an `r` tag or short text containing no URL. Supporting relays can resolve an ID prefix of at least 6 bytes (twelve hex characters). Full IDs still work with standard NIP-01 queries. Readers must show all valid matches and wait for a deliberate user action before opening any URL, even when there is only one result ([Cairn proposal](https://github.com/nostr-protocol/nips/pull/2553), [pinned reader rules](https://github.com/nostr-protocol/nips/blob/c6bfea5cc096fa4e5aa136d23bbd34c2f997583a/CA.md#reader-behavior)).

### Bitcoin Cash key bindings propose signed succession {#nostr-protocol-nips-2555}

An open proposal filed November 21 binds a Nostr key to a Bitcoin Cash key, and both keys sign the association. The binding lives in an addressable kind 30078 event with `d` set to `bnd1`. Replacing or revoking it takes approval from two keys, and an optional recovery key can stand in for a lost one. Each successor or revocation carries a bounded signed history, so a reader can check the chain of replacements. If two valid branches stay unresolved, the payable address is disputed ([key-binding proposal](https://github.com/nostr-protocol/nips/pull/2555), [exact draft](https://github.com/nostr-protocol/nips/blob/91c93022b6d0e01d250adf701b04e6bdb23ce4f4/XX.md)).

### NIP-39 proposes a Bitcoin Cash address claim {#nostr-protocol-nips-2556}

A separate open amendment to NIP-39, filed November 21, lets a user link a single-key Bitcoin Cash address to their Nostr identity. The link is a `bch` claim in the kind-10011 identity event, written as a lowercase P2PKH CashAddr without its prefix. The holder proves control by signing the existing verification text. Wallets that sign only transactions can use an optional transaction proof instead. Twinkey has published its verifier and relay-lookup code ([address claim amendment](https://github.com/nostr-protocol/nips/pull/2556), [exact NIP-39 draft](https://github.com/nostr-protocol/nips/blob/07c7933f1b08966edbab676a6c669c602c1ced07/39.md), [Twinkey specification](https://github.com/samizdatproject/twinkey/blob/2182988875de1bb0e3d4ef6a2fd0fdc268672be5/SPEC.md)).

### BUD-13 standardizes upload and mirroring by blob hash {#hzrd149-blossom-100}

[Blossom](/en/topics/blossom/), the file storage layer for Nostr apps, merged BUD-13 on November 22. Uploads and mirrors put the file's SHA-256 digest in the URL, and the server rejects bytes that don't match. `PUT /<sha256>` uploads a file. The optional `POST /<sha256>` copies one from another host and accepts BUD-11 authorization, including an upload token for the same hash. Clients use `OPTIONS` to discover upload and mirror support separately from the download methods on the same URL. The specification is merged, and no server rollout is reported ([merged BUD-13](https://github.com/hzrd149/blossom/pull/100), [merged path-based upload spec](https://github.com/hzrd149/blossom/blob/72ccc5dcce26489ee12dc88c47216a6ebbbb2d07/buds/13.md), [method discovery](https://github.com/hzrd149/blossom/blob/72ccc5dcce26489ee12dc88c47216a6ebbbb2d07/buds/01.md#feature-discovery)).

### Blossom proposes an explicit upload acceptance check {#hzrd149-blossom-119}

An open Blossom proposal filed November 22 lets a client ask whether a file's size and type meet a server's policy before sending the bytes. The optional `QUERY /<sha256>` applies the same authorization and policy as the intended PUT, and the answer is only advisory. If a proxy refuses the newer HTTP method, clients can fall back to PUT or to applicable legacy checks. The proposal also stops recommending the legacy HEAD optimization ([acceptance-check proposal](https://github.com/hzrd149/blossom/pull/119), [HTTP QUERY method](https://www.rfc-editor.org/rfc/rfc10008)).

### BUD-14 proposes a cacheable blob inventory filter {#hzrd149-blossom-120}

Draft BUD-14, opened November 22, adds `GET /inventory`, a public, cacheable snapshot. A client can use it to check many file hashes locally without revealing each lookup. The snapshot is a Bloom filter. A miss means the blob was absent at the snapshot cutoff, and a hit may be a false positive. To learn whether a blob is available now, a client still sends `HEAD` or `GET`. The filter leaves out restricted blobs, though anyone can test guessed hashes against it ([inventory-filter draft](https://github.com/hzrd149/blossom/pull/120), [pinned BUD-14 text](https://github.com/hzrd149/blossom/blob/92c96b11f2f9f1418fd9d843552465608a5dcbc4/buds/14.md)).

### Blossom closes the directory manifest draft in favor of Hashtree {#hzrd149-blossom-105}

On November 22, Blossom closed BUD-16, its draft for naming files and folders by hash, without merging it. The maintainer pointed readers to the independent Hashtree specification. Hashtree's November 13 revision carries the work forward, together with companion ideas for encrypted blobs, indexing large files and folders, and references, all adjusted to its implementation. Compass first covered the manifest on September 23 ([BUD-16 closure comment](https://github.com/hzrd149/blossom/pull/105#issuecomment-7072896555), [September 23 coverage](https://nostrcompass.org/en/newsletters/2026-09-23-newsletter/#bud-16-proposes-deterministic-directory-manifests), [independent Hashtree draft](https://github.com/mmalmi/hashtree-spec/blob/778161107038240ae2fe2c79013b750ce417b966/README.md#status)).

### NAP-SHELL compatibility checks move to review {#napplet-naps-142}

NAP-SHELL would let a host for Nostr web apps check whether it supports the capabilities that a signed app manifest requests. The proposal moved to review on November 23 and remains open. Its draft was last revised November 10. `domains()` lists the capability domains the calling app already has. `check(manifest)` verifies another app's signed NIP-5D manifest and lists any missing required and optional domains. The result can be compatible, incompatible or unknown. App installation and grants remain separate operations ([NAP-SHELL review](https://github.com/napplet/naps/pull/142), [exact shell draft](https://github.com/napplet/naps/blob/b9b0b7e38d99d9e3ad0b79e3de61b349156ee41f/naps/NAP-SHELL.md)).

### Napplet web projection binds privileges to one document {#napplet-naps-158}

An open napplet amendment filed November 23 gives each verified applet document its own `MessagePort` and attaches the app's permissions to that loaded document. The shell checks the initial port handoff. After a navigation or reload, the document needs fresh verification and a new binding. The amendment changes only the specification text, and no runtime release is claimed ([web projection amendment](https://github.com/napplet/naps/pull/158), [document-scoped binding](https://github.com/napplet/naps/blob/02b6f1532daa2f0a8569ba52a9b35c7130e00a71/projections/web.md#identity--trust)).

### Marmot sibling Welcomes preserve the original inviter {#marmot-protocol-marmot-512}

A Marmot spec change merged November 19 adds the original inviter to the sibling Welcome that admits another of a user's linked devices to a chat. In chats with no invitation generation, the Welcome can also mark the chat as confirmed. Chats with a generation still settle through the shared invitation decision. Receivers honor these assertions only in Welcomes from their own account. The spec profiles Welcome v3 as experimental, and v1 and v2 receivers reject it. Stable [MDK](#marmot-protocol-mdk) 0.18.0 implements v3 ([merged sibling Welcome revision](https://github.com/marmot-protocol/marmot/pull/512), [selection and validation rules](https://github.com/marmot-protocol/marmot/blob/04fbdf8a0365184fec569ab90549cb8e844aac1c/features/device-group.md#choosing-the-version), [MDK 0.18.0 wire compatibility](https://github.com/marmot-protocol/mdk/blob/v0.18.0/docs/release/0.18.0.md#compatibility)).

### Marmot retires its QUIC agent text preview {#marmot-protocol-marmot-513}

A Marmot spec change merged November 21 retires the live QUIC agent text preview. Clients stop sending it and stop connecting to advertised preview endpoints, and new groups leave the component out. Many existing rooms list the component as required. Newer clients therefore keep advertising and validating its minimal receive role so they can stay in those rooms. Old tagged messages still arrive as ordinary chat. Stable MDK 0.19.0 implements the retirement ([merged QUIC retirement](https://github.com/marmot-protocol/marmot/pull/513), [compatibility rules](https://github.com/marmot-protocol/marmot/blob/91617ebd6be614dd1ea56830b8bd0c4c7a8e5438/app-components/agent-text-stream-quic-v1.md#retirement), [MDK 0.19.0 agent compatibility](https://github.com/marmot-protocol/mdk/blob/v0.19.0/docs/release/0.19.0.md)).

### Marmot sends shared decisions early to newly linked devices {#marmot-protocol-marmot-518}

Marmot rules merged November 24 change what happens when a user links a new device. The account resends its small settings, including invitation decisions already recorded, before automatically adding the device to the affected chats. The [MDK nightly](#marmot-protocol-mdk) implements this ordering to reduce stale invitation prompts on new devices. Marmot specifies the sending order. Relays can still deliver the chat before the decision ([merged ordering rules](https://github.com/marmot-protocol/marmot/pull/518), [account sync text](https://github.com/marmot-protocol/marmot/blob/0a4466cd41d8e592ecd30146cc23a8c256fd9e8d/features/account-sync.md#broadcasts)).

### Marmot's private relay idea adds parallel paths {#marmot-protocol-marmot-431}

November 22 revisions to Marmot's open, nonnormative accumulation relay idea let a client authorize several relay buffers. Buffers with overlapping coverage serve as fallbacks, and buffers with distinct coverage reach more sources. Each buffer keeps group queries away from upstream relays, though it still sees the queries it handles. Clients bypass the buffers only by explicit choice. Whether a single usable path is enough remains an open design question ([accumulation relay proposal](https://github.com/marmot-protocol/marmot/pull/431), [exact idea text](https://github.com/marmot-protocol/marmot/blob/82012ab31c95bd6f0e5da1bf32d36246251df864/ideas/accumulation-relays.md)).

### Marmot's history purge draft batches signed consent {#marmot-protocol-marmot-419}

Marmot's open history purge draft lets one member carry several separately signed Yes votes into the group's accepted state, so voters don't have to sign again. Votes left on a competing branch can count once they are carried over. Every account in the fixed voting group must still agree. The draft notes that an open purge can block recovery if no capable member can close it. Its tests cover encoding and reference-model transitions, and MLS convergence and actual deletion remain unverified ([history purge proposal](https://github.com/marmot-protocol/marmot/pull/419), [exact component text](https://github.com/marmot-protocol/marmot/blob/a335fac887eb7ba91380b42b0baf603a5b30e3c5/app-components/history-purge-v1.md)).

### Marmot draft keeps completed member requests closed {#marmot-protocol-marmot-432}

Marmot's open draft for member requests to change group settings was revised on November 22. An applied request now stays closed as long as the group change that applied it remains in accepted history, even if someone later restores the previous setting. A retry resends the same signed event. Requests whose expected and proposed values are identical are rejected ([Applied rule revision](https://github.com/marmot-protocol/marmot/commit/3c43c4f8fa94047c39e95276c101b0a489bca466), [pinned group change requests draft](https://github.com/marmot-protocol/marmot/blob/3c43c4f8fa94047c39e95276c101b0a489bca466/features/group-change-requests.md)).

### Marmot invite-link draft guards against repeated admissions {#marmot-protocol-marmot-429}

A November 22 revision to Marmot's open private invite link draft keeps a group from admitting a device again with a key package that has already been used. An admin runs the check before preparing either a manual or an automatic admission. The admin searches the group's accepted membership history for any device key package from the signed offer history, including packages used by devices that have since been removed. Missing evidence or uncertain delivery leaves the request unresolved ([pinned admission revision](https://github.com/marmot-protocol/marmot/commit/33b686eac7e764813249af9c278f4a9969a9265e)).

### Marmot pinning draft limits member changes to the pin list {#marmot-protocol-marmot-434}

A November 22 revision to Marmot's open shared pinning draft requires a member's pin edit to be the only change in its signed group update. The rule applies when group policy lets non-admins pin. Membership changes need separate authorization, and admin updates keep their per-operation checks ([standalone Commit authorization revision](https://github.com/marmot-protocol/marmot/commit/2c80e583fa2a2380f299bce92ee17c79ad7c9e31)).

### Concord specifies which Guestbook snapshot a joiner can trust {#concord-protocol-concord-27}

[Concord](/en/topics/concord-protocol/) calls its membership record the Guestbook. A CORD-02 amendment merged November 25 covers a client that joined with only the current key epoch and never saw the rotation. That client selects the earliest snapshot in that epoch from the owner or a member with ban authority, and the lower public key breaks a tie. A client that adopted the rotation keeps the signer it verified ([Guestbook snapshot rule](https://github.com/concord-protocol/concord/blob/7e4eb233e057d32c7a2dce72abfcac05f54e0692/02.md#L94)).

The formal spec merge follows earlier implementation. The Vector maintainer says Vector already used the Guestbook rule in v0.5.1 and ships the broader changes in v0.5.2 ([merged Concord #27](https://github.com/concord-protocol/concord/pull/27), [Vector v0.5.2 release](https://github.com/VectorPrivacy/Vector/releases/tag/v0.5.2)).

## Six Years of Nostr Novembers

A relay can accept a signing request that never reaches the signer. An `OK` reports one write. The recipient still needs a live subscription, subject to a relay's [subscription limit](https://github.com/fiatjaf/strfry/blob/4cd3cf64850caf47dda46c2a2abbbf3525a64d10/src/apps/relay/RelayWebsocket.cpp#L99).

### November 2021

On November 27, 2021, the Loquaz desktop chat prototype began filing decrypted messages into conversations keyed by contact public key. It subscribed to encrypted direct messages tagged to the user's key and routed each by author after NIP-04 decryption. It tried routing the user’s own messages by the destination `p` tag, as the [Loquaz conversation-model commit](https://github.com/emeceve/loquaz/commit/6de06a9c1b8de1b1feb3417ad646471e72756669) shows.

A day later, go-nostr moved `Event.Kind` and the optional `EventFilter.Kind` from `uint8` to `int`, keeping the JSON field names. An eight-bit unsigned value stops at 255, so code built on the library could not previously publish or query larger kinds. The commit lifted that ceiling without showing which kinds were registered or used that month, per the [go-nostr kind type commit](https://github.com/nbd-wtf/go-nostr/commit/77fa373babd8c42e5b52f588ba6cb0d45f629507).

### November 2022

The NIP-20 draft, merged on November 11, 2022, introduced `["OK", event_id, true_or_false, message]`, which reports one write's outcome under its event ID. Its rationale said clients had no reliable sign a publish reached the database. Stored duplicates counted as successes, and prefixes like `blocked:` and `rate-limited:` explained failures. Successful ephemeral events were exempt, and `NOTICE` remained for malformed commands, per the [NIP-20 command results draft](https://github.com/nostr-protocol/nips/commit/30f1e64e01f3999c8bcfedd0c9de74f8cf77f404).

On November 25, NIP-11 required CORS headers such as `Access-Control-Allow-Origin` on the relay information document, which relays already served as JSON from the WebSocket URI for `Accept: application/nostr+json`. CORS decides whether a browser can read a response from another origin, so web clients hosted elsewhere could read a relay's disclosures once its operator complied, per the [NIP-11 CORS change](https://github.com/nostr-protocol/nips/commit/cf5eaf63607805fb7fa7262de160eacf105c0ffe).

### November 2023

A November 6, 2023 edit to NIP-01 made the fourth element of `OK` mandatory. Success can carry an empty string. A rejection carries a machine prefix and human explanation in the same position, as the [NIP-01 four-element clarification](https://github.com/nostr-protocol/nips/commit/108b7f16f9f75157cffde590a55077e4dfe7c955) records.

On November 19, NIP-11 let clients check for advertised relay write rules before publishing. The `limitation.restricted_writes` flag covered conditions such as a pubkey allowlist, acceptance of specific event kinds, payment or minimum proof of work. Ordinary anti-spam heuristics stayed outside this field. The Boolean signals only that a policy exists and gives no admission answer for any particular event, per the [NIP-11 restricted writes merge](https://github.com/nostr-protocol/nips/commit/ea6d277c7ceaf21aec077e521c2251bb03f6e651).

### November 2024

A NIP-11 change dated November 5, 2024 UTC added `banner` and listed the existing `icon` in the top-level example. It recommended a compact, preferably square icon for client relay lists, while the larger banner accompanies the text description, shown in a Damus mockup. These images help users recognize a relay and carry no authentication, per the [NIP-11 banner and icon change](https://github.com/nostr-protocol/nips/commit/4c0f9632925eb0ffe94453e45a7bed77c0ab1e6b).

A November 22 revision of NIP-29 required relays to reject a kind 9021 join request from a user not yet admitted, recommending replies state whether review is pending or the denial is final. A conditional denial could name a requirement such as payment. The revision first accepted requests from existing members, and a November 23 follow-up rejected them with `duplicate:`, which here reports existing membership, per the [NIP-29 join-feedback revision](https://github.com/nostr-protocol/nips/commit/d09b51246d7d5757b5e78ef1cc18e8925561d42f) and [its follow-up](https://github.com/nostr-protocol/nips/commit/4d47b38dbc0c2e09d235972f59a4338a7bb37cc0).

### November 2025

The November 18 release of nostr-tools v2.17.3 shipped a new NIP-77 reconciliation implementation, letting clients compare their event IDs with a relay's and fetch only what they lack. It routed `NEG-MSG` and `NEG-ERR` to callbacks keyed by subscription ID, and its `NegentropySync` interface reports IDs only one side holds through `onhave` and `onneed`. It needs a compatible relay and leaves fetching to ordinary requests, per the [nostr-tools v2.17.3 release](https://github.com/nbd-wtf/nostr-tools/releases/tag/v2.17.3) and [NIP-77 interface commit](https://github.com/nbd-wtf/nostr-tools/commit/66cc55c7f0f6c7d1466cfa9cefc97b6846e3009a).

On November 25, Go relayer framework commits moved certain `REQ` failures from connection-wide `NOTICE` strings to `CLOSED` envelopes carrying the subscription ID. The first covered unauthorized kind-4 DM filters and dropped that path's `EOSE` (end-of-stored-events) marker. The second covered filter decode failures and request-policy rejections, where `EOSE` can still precede the subscription-specific `CLOSED`. Both are default-branch commits with no verified deployment, per the [relayer DM-filter change](https://github.com/fiatjaf/relayer/commit/fde9a37a290be2fb4c6379104b40c82a30f1f3de) and [filter-failure change](https://github.com/fiatjaf/relayer/commit/81dfb1ace74b643315e0ff68a9a0611bc89634e3).

### November 2026

On November 21, 2026, rnostr merged PR #54, pairing the 2023 policy flag with the 2022 per-event answer. Its opt-in policy extension advertises `limitation.restricted_writes` and checks writes against a configured event kind and, optionally, a `d` tag. When the policy refuses a write, the relay sends an `OK` with `false` and the event ID. Its message starts with `blocked:`. The check runs after authentication and applicable rate limits, and stored events stay readable. Tests cover the ordering and the negative reply, per the [rnostr PR #54 merge](https://github.com/rnostr/rnostr/pull/54) and [policy implementation commit](https://github.com/rnostr/rnostr/commit/0d415cd777daa1a4fea9a346fd289f3570c17e49).

An [Amber](#greenart7c3-amber) report filed November 20 shows why these signals need separate readings. Issue #644 reports that even small NIP-46 pings sent only to one Primal endpoint received an `OK` with `true` from that relay but never reached the newer connection. In strfry, the query worker can refuse a subscription before sending `EOSE`. After the worker sends `EOSE` and hands the request to the live monitor, that monitor can still refuse it with a `NOTICE` lacking a subscription ID. The `OK` described the write and `EOSE` described the stored query. Amber depended on the live subscription to hear the next request, as the [strfry query worker](https://github.com/fiatjaf/strfry/blob/4cd3cf64850caf47dda46c2a2abbbf3525a64d10/src/apps/relay/RelayReqWorker.cpp#L40-L57), [strfry live monitor](https://github.com/fiatjaf/strfry/blob/4cd3cf64850caf47dda46c2a2abbbf3525a64d10/src/apps/relay/RelayReqMonitor.cpp#L48-L52), [Amber issue #644](https://github.com/greenart7c3/Amber/issues/644) and [Amber PR #649](https://github.com/greenart7c3/Amber/pull/649) show.
